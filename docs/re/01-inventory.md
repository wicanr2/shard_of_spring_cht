# 01 — RE-01:十三支執行檔的初始清冊

日期:2026-08-13
輸入:`docs/re/00-inputs.md` 所列 SHA-256
工具:`ida-pro-9.4-idapython:py312-v1` + `tools/ida/export_inventory.py`
原始資料:`workplace/ida/out/*.json`(gitignore,可用下方指令重跑)

## 結論摘要

**IDA 的自動分析只吃到 loader stub,遊戲本體完全沒被反組譯。**
十一支遊戲 EXE 各有 70–93% 的內容落在 IDA 標成 `UNK` 的段裡。
這是目前擋住所有子系統的唯一瓶頸,而且**十一支是同一個問題**,解一次就全解。

## 2. 十一支遊戲 EXE 共用同一份 loader stub

**信心等級:已確認。**

那十一支的**函式大小序列完全相同**:

```
(3, 1, 131, 1154, 112, 372, 55, 17, 50, 55)   ← 10 個函式,總計 3,047 bytes
```

而 `USERLIB.EXE` 是 `(40,)`、`BRUN30.EXE` 是 709 個函式的另一組序列 —— 兩者都不屬於這一族。

十一支的 CODE 段大小**都是 3,047 bytes**,不多不少。一支 3 KB 的 `START.EXE` 與一支
44 KB 的 `CMBT.EXE` 有完全一樣的函式結構,只有一種解釋:那不是遊戲程式碼,是共用的載入前導。

⚠ **它們不是逐位元組相同**(11 支的 CODE 段尾 3,047 bytes 雜湊全不同)。
差異來自重定位修正與嵌入的模組名。**「結構相同」是已確認,「位元組相同」是已否證** ——
不要把前者寫成後者。

### 判別法的由來

最初的徵狀是 `func=10` 出現在十二支大小差十倍以上的執行檔上。
**一個橫跨不同輸入卻紋風不動的數字,是查法壞掉的徵狀,不是結果。**

## 3. UNK 段裡是什麼

**信心等級:證據充分。**

`CMBT.EXE` 的載入映像起點(檔案位移 512,即 `seg000` 起點):

```
00000210: 627a 434d 4254 2020 2020 2b0a 0209 104f  bzCMBT    +....O
...
00000240: e93d 008b 0eca 668b d949 8bc3 bbc4 66ba  .=....f..I....f.
00000250: 0100 cd3d 0a90 908b d38b 1ec8 66cd 3d1b  ...=........f.=.
00000260: 9090 92cd 3f55 9090 83c2 028b c3bb c466  ....?U.........f
```

三項證據指向「明碼 8086 機器碼」:

1. **開頭是模組標頭** `bz` + 模組名(`bzCMBT    `),與其他 EXE 同構(`bzSTART`、`bzTOWN`…)
2. **後續位元組可讀成合理的 8086 指令流**:`8b 0e ca 66`(`mov cx,[66ca]`)、
   `8b d9`(`mov bx,cx`)、`49`(`dec cx`)、`bb c4 66`(`mov bx,66c4`)、`ba 01 00`(`mov dx,1`)
3. **熵值落在程式碼的區間**:

   | 區塊 | 熵 | NUL 比例 |
   |---|---:|---:|
   | `CMBT.EXE` seg000 | 6.39 bits/byte | 6.1% |
   | `MENU.EXE` seg000 | 6.19 | 6.3% |
   | `BRUN30.EXE` CODE(已知是程式碼) | 7.25 | 5.1% |

   壓縮或加密的資料會逼近 8.0。**這些沒有被打包。**

**所以問題不是「程式碼被藏起來了」,是「IDA 不知道那裡是程式碼」** ——
MZ 標頭的 CS:IP 指向 stub,而 stub 到遊戲本體之間沒有靜態可追的參考。

### 觀察到但尚未定案:`INT 3Dh` / `INT 3Fh`

上面那段碼裡 `cd 3d`(INT 3Dh)與 `cd 3f`(INT 3Fh)反覆出現,**後面都跟著 `90 90`**
(兩個 NOP,典型的 linker 就地修補預留)。

**信心等級:假設。** 形狀符合「透過中斷向量呼叫執行期／覆蓋管理員」,
若成立,那就是 §2.2 的 B 項(執行期模組的呼叫介面)要建的那張表。
**但目前沒有任何一條直接證據**,不得寫進規格。裁決方式見下。

依 CLAUDE.md §1.2,這裡只需要解到「每個 INT 呼叫做了什麼」,
**不需要追那兩個中斷向量在 DOS 層怎麼被安裝**。

## 4. 兩支不屬於任何一族的

- **`BRUN30.EXE`** 是唯一一支自動分析正常運作的(709 函式、8% UNK)。
  它是一支結構正常的 EXE,不套用 stub 那一族的問題。
- **`USERLIB.EXE`** 自成一格:13 個段、只有 1 個 40-byte 函式、96% 未分析。
  段數異常多這件事本身是線索(`CLAUDE.md` §5.3 記著它疑似原生組語的 I/O 程式庫)。

## 5. 下一步(RE-01 的直接產出)

**唯一該做的事:讓 IDA 把 `seg000` 當程式碼分析。**
十一支同構,所以做法只要在一支上成立就能套用。

依序試,停在第一個成功的:

1. 讀那份 3,047-byte stub(它已經被完整反組譯了,10 個函式)——
   `start_0`(1,154 bytes)是最大的一支,載入語意應該在裡面。
   **找它算出來的載入位址與進入點**,那就是要告訴 IDA 的東西。
2. 若 stub 讀不出結論,改用 `ida_auto.plan_and_wait` + `create_insn` 從
   模組標頭之後的第一個位元組強制反組譯,看指令流是否自洽(不自洽會在幾十 byte 內散掉)。
3. 兩者都不成立時,才考慮 DOSBox 動態觀察(依 oracle 優先序,實跑高於靜態推論)。

`INT 3Dh` / `INT 3Fh` 的語意在第 1 步之後應該會一起有答案,不必另開一條線。

## 6. 重跑方式

```sh
for e in START MENU TOWN CMBT CAMP MAZEMOVE WRLDMOVE CHARUTIL MTEST USERLIB MIO2 WSIO BRUN30; do
  tools/ida.sh analyze "$e.EXE"
  tools/ida.sh run tools/ida/export_inventory.py "$e.EXE" "/work/out/$e.json"
done
```

輸出 JSON 的欄位:`counts` / `segments` / `entries` / `imports` / `functions` /
`strings_ida` / `strings_raw_ascii` / `far_call_targets`。

⚠ **`strings_ida` 系統性低估**(IDA 只列已定義成字串項的),
所以清冊同時記 `strings_raw_ascii`(獨立掃描,不依賴自動分析)。
兩者差 2–4 倍是正常的 —— 中文化盤點要用後者。

⚠ `far_call_targets` 目前在十二支上都是 0,**這是上述「沒被分析」的直接後果,
不是「沒有跨段呼叫」**。等 seg000 能分析之後這個欄位才有意義。
