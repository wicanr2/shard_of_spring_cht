# 02 — 那份 3,047-byte loader stub 在做什麼

日期:2026-08-13
輸入:`START.EXE`(SHA-256 見 `docs/re/00-inputs.md`)
函式:`start_0` @ `0x10219`–`0x1069B`(1,154 bytes),呼叫端 1 處(`start` @ `0x10180`)
接續:[`01-inventory.md`](01-inventory.md)

## 結論

**那 3,047 bytes 是「載入執行期模組」的前導程式,不是遊戲程式碼。**
它做三件事:配置記憶體 → 依環境變數搜尋並載入 `BRUN30.EXE` → 選擇性載入 `USERLIB.EXE`。
遊戲本體(`seg000` 的 `bz<NAME>` 模組)由**執行期模組**接手,不由這份 stub 直接執行。

## 1. ⚠ 位址換算(先講,因為這裡錯過一次)

`seg005`(CODE 段)的基底是 **linear `0x10180`**,不是 `0x10000`。

```
linear = 0x10180 + 段內位移
檔案位移 = 512 + (linear − 0x10000)        # 512 = MZ 標頭 0x20 paragraphs
```

一開始拿 `0x10000` 當基底去解 `mov dx, 913h` 引用的資料,得到的是**看起來像程式碼的位元組**,
差一點就寫成「那裡不是字串」。

**判別法:用一個已知符號回推基底。** 反組譯裡有 `mov word_10AC5, dx` 而立即數是 `0x945`,
`0x10180 + 0x945 = 0x10AC5` ✓ —— 基底對了,其他引用才可信。

## 2. 執行流程

**信心等級:已確認**(逐條指令讀出,無反編譯器涉入)。

| 位址 | 動作 |
|---|---|
| `0x10220` | 讀 `ds:0`,`cmp ax, 7A62h` —— `0x7A62` 小端就是 **`bz`**,模組簽章檢查 |
| `0x1022E` | `INT 21h AH=30h` 取 DOS 版本,`< 2` 就跳錯誤路徑 |
| `0x1023E` | 讀 PSP:`es:2`(記憶體頂端節區)、`es:2Ch`(environment 節區) |
| `0x10260`– | 四次 `sub_108A6(ax=id, cx=大小, dx=旗標)` —— 配置區塊 id 1／2／6／7／0Ah |
| `0x10295` | `lodsb`/`stosb` 迴圈把 environment 抄進配置好的區塊 |
| `0x102EC` | **`sub_1070B(dx=檔名, si=環境變數名, cx=變數名長度)`** → 開檔 |
| `0x102F6` | `cmp word_10B4C, 2EBh` —— 驗載入目標的標頭 |
| `0x10342` | `INT 21h AH=3Fh` 讀 `0xC28 << 1` = **6,224 bytes** |
| `0x10370` | `INT 21h AH=3Eh` 關檔 |
| `0x10379` | `cmp byte_10AD5, 0` → 為 0 就跳過第二階段 |
| `0x10383` | 第二次 `sub_1070B`,換一組檔名與環境變數 |
| `0x10393` | 驗兩個標頭常數 `16EBh`、`1850h` |
| `0x103A9` | 組出 32-bit 值與 stub 內的常數比對 → 不符跳 `loc_10971` |
| `0x103ED` | `INT 21h AX=4200h`(LSEEK 從檔首)後繼續載入 |

## 3. 載入的是哪兩個檔

`sub_1070B` 的兩次呼叫參數(位址已用 §1 的基底換算):

| 呼叫 | `dx` → 檔名 | `si` → 環境變數 | `cx` |
|---|---|---|---|
| 第一次 `0x102EC` | `BRUN30.EXE` | `PATH=` | 5 |
| 第二次 `0x10383` | `USERLIB.EXE` | `LIB=` | 4 |

**交叉驗證:`cx` 剛好等於環境變數名的字元數**(`PATH=` 5 個、`LIB=` 4 個)。
這兩個數字來自不同地方 —— `cx` 是指令裡的立即數,字串長度是資料段的內容 ——
沒有共同的錯誤來源,所以對得上就不是巧合。

所以 `sub_1070B` 是「**依環境變數列出的目錄搜尋並開啟檔案**」。
`strings` 看到的 `Cannot find $  Enter new path: $` 就是它找不到時的互動路徑。

### 一個順帶解開的小設計

`0x10379` 的 `cmp byte_10AD5, 0` 判的是 **`USERLIB.EXE` 這個字串的第一個位元組**
(`0x10AD5` 就是那個字串的起點)。
換句話說:**檔名欄位本身兼任「要不要載入使用者程式庫」的旗標** ——
把字串清成空的,第二階段就整段跳過。

## 4. 對整體架構的意義

**信心等級:證據充分。**

```
<遊戲>.EXE
├── seg000…seg004   模組本體(bz<NAME> 標頭 + 明碼 8086,含 INT 3Dh/3Fh)
└── seg005 (3,047B) loader stub ← IDA 只分析到這裡
                       │
                       ├── 依 PATH= 載入 BRUN30.EXE   (執行期模組)
                       └── 依 LIB=  載入 USERLIB.EXE  (使用者程式庫,可省略)
```

三件事因此定案:

1. **`USERLIB.EXE` 是「使用者程式庫」**,由 stub 與執行期一起載入。
   這解釋了它為什麼結構特殊(13 個段、只有 1 個 40-byte 函式、96% 未分析)——
   它不是獨立程式,是一包被掛進執行期的常式。
   `CLAUDE.md` §5.3 記的「疑似原生組語的 I/O 程式庫」方向正確,現在有了載入端佐證。
2. **模組本體不由 stub 直接跳進去**。stub 只負責把執行期擺好;
   `bz<NAME>` 那份模組是交給執行期處理的。
3. **十一支遊戲 EXE 共用這一份 stub**(`docs/re/01` §2),所以上面每一條都同時對十一支成立。

## 6. 下一步

模組本體的進入方式在**執行期**那一側,而 `BRUN30.EXE` 是唯一自動分析正常的一支
(709 函式、8% UNK,`docs/re/01` §1)。所以:

1. 在 `BRUN30.EXE` 裡找「檢查 `bz` 簽章 / 處理 `bz<NAME>` 標頭」的常式 ——
   `0x7A62` 這個立即數是最直接的入口,掃它的參考。
2. 從那裡往下找模組本體的重定位與進入點計算。
3. 拿到進入點的算法之後,回到遊戲 EXE 告訴 IDA `seg000` 從哪裡開始是程式碼。

`INT 3Dh` / `INT 3Fh` 的語意預期會在第 1 步一起浮出來(執行期必然是它們的安裝端)。

### 第 1 步已完成:模組標頭處理常式是 `BRUN30.EXE:sub_14BDD`

**信心等級:已確認**(掃 `0x7A62` 立即數,15 處命中)。

十五處裡有十四處是 `cmp word ptr ds:0A18h, 7A62h` 或 `ds:0A5h` —— 固定位址,是自我檢查。
**只有一處用遠指標**:

```
0x14C08   sub_14BDD    cmp word ptr es:0, 7A62h
```

`es` 來自 `es:32h` / `es:34h` 兩個欄位經 `sub_156DD` 換算而來 ——
形狀與 stub 的 `mov ax, ds:0` / `cmp ax, 7A62h` 相同,但檢查的是**別的節區**,
也就是被載入的模組。`sub_14BDD` 只有一個呼叫端(`0x1158B`)。

已讀出的行為(219 bytes,尚未讀完):

| 位址 | 動作 |
|---|---|
| `0x14BE5` | `test word ptr es:54h, 40h` —— 旗標閘門,不成立就整段跳過 |
| `0x14C18` | `INT 21h AX=4200h` LSEEK 到**檔案位移 6** |
| `0x14C2F` | 讀 **2 bytes** 進 `ds:0C56h` |
| `0x14C37` | LSEEK 到**檔案位移 0x1E** |
| `0x14C43` | 讀模組標頭的 `es:12h` 與 `es:16h`(先 push 起來) |
| `0x14C59` | 讀 **4 bytes** 進 `ds:0C52h` |

檔案位移 6 與 0x1E 是 **MZ 標頭裡的欄位**(6 = 重定位項數、0x1E 之後 = 重定位表起點),
所以這一段在做的是**重定位**。模組標頭的 `+0x12` / `+0x16` 是重定位要用的參數。

**下一輪**:讀完 `sub_14BDD` 剩下的部分與呼叫端 `0x1158B`,
把 `bz` 模組標頭的欄位表(`+0x00` 簽章、`+0x12`、`+0x16`、`+0x32`、`+0x34`、`+0x54`)定案,
就能算出模組本體的進入點,回頭餵給 IDA。
