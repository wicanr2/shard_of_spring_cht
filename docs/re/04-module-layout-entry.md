# 04 — EXE 佈局與進入點

日期:2026-08-13
接續:[`03-bz-module-header.md`](03-bz-module-header.md)

## 結論

遊戲 EXE 的佈局是 **`[模組區][loader stub]`**,MZ 標頭的進入點指向 **stub**。
模組區的長度同時寫在三個地方,三者 11/11 一致。
`BRUN30.EXE:sub_14CB8` 是通用的 MZ 載入器,用標頭的 `CS:IP` 加上載入基底算進入點。

## 1. 佈局

```
檔案位移 0         MZ 標頭(0x20 paragraphs = 512 bytes)
檔案位移 512       載入映像起點 ─┐
  +0x00            16-byte 前綴  │ 模組區
  +0x10            bz 標頭 ──────┤ 長度 = +0x16 paragraphs
  …                模組本體      │
  +(+0x16)*16      loader stub ──┘  ← MZ 的 CS:IP 指到這裡(IP 一律 0)
```

## 2. `+0x16` 的三重驗證

| 來源 | 性質 |
|---|---|
| `bz` 標頭 `+0x16` | 資料檔的位元組 |
| IDA 的 UNK 段總和 | 反組譯器的自動分析結果 |
| **MZ 標頭 `+0x16`(CS 欄位)** | 另一份資料檔的位元組,且被 DOS 直接使用 |

| EXE | MZ CS | `bz +0x16` | IDA UNK ÷16 |
|---|---:|---:|---:|
| `START` | `0x018` | `0x018` | `0x018` |
| `MENU` | `0x462` | `0x462` | `0x462` |
| `TOWN` | `0x3B1` | `0x3B1` | `0x3B1` |
| `CMBT` | `0xA2B` | `0xA2B` | `0xA2B` |
| `CAMP` | `0x4C0` | `0x4C0` | `0x4C0` |
| `MAZEMOVE` | `0x4E9` | `0x4E9` | `0x4E9` |
| `WRLDMOVE` | `0x1B8` | `0x1B8` | `0x1B8` |
| `CHARUTIL` | `0x306` | `0x306` | `0x306` |
| `MTEST` | `0x035` | `0x035` | `0x035` |
| `MIO2` | `0x06E` | `0x06E` | `0x06E` |
| `WSIO` | `0x05D` | `0x05D` | `0x05D` |

11/11 × 3 個來源。MZ 的 IP 欄位全部是 0(stub 從其節區位移 0 開始)。

**信心等級:已確認。**

## 3. `BRUN30.EXE:sub_14CB8` —— 通用 MZ 載入器

`0x14CB8`–`0x14E0C`,340 bytes,呼叫端 1 處(`0x1165B`)。

進來時 `bx` 指向**檔名字串**(`ds:0B06h`,由呼叫端在 `0x1164D` 設定)。

| 位址 | 動作 |
|---|---|
| `0x14CC0` | `INT 21h AX=3D00h` 依檔名開檔 |
| `0x14CD8` | 讀 `0x1A` bytes 進 `ds:7Bh` —— 就是 MZ 標頭 |
| `0x14CDF` | `cmp ds:7Bh, 5A4Dh` 驗 `MZ` |
| `0x14CE7` | 用 `ds:83h`(標頭 `+0x08`,標頭大小 paragraphs)LSEEK 到載入映像起點 |
| `0x14CFD` | 再讀 `0x12` bytes,取得模組前綴與簽章 |
| `0x14D41` | `cmp ds:95h, 6D62h` —— `0x6D62` 小端是 **`bm`** |
| `0x14D51` | `cmp ds:0A5h, 7A62h` —— `bz` |
| `0x14D0A` | 兩次 `INT 21h AH=29h`(PARSE FILENAME)填 FCB |

### 進入點算式

MZ 標頭已在 `ds:7Bh`,所以欄位對應:

```
ds:0x8F = MZ +0x14 = IP
ds:0x91 = MZ +0x16 = CS
ds:0x89 = MZ +0x0E = SS
ds:0x8B = MZ +0x10 = SP
```

`0x14D5B` 之後:

```
dx = 載入節區 + 0x40          ; 0x40 paragraphs 的前置區
新 CS = ds:0x91 + dx          ; 0x14D8A: add ax, dx
新 IP = ds:0x8F               ; 原值不動
新 SS = ds:0x89 + dx
新 SP = ds:0x8B
```

也就是**標準的 MZ 重定位**,沒有自訂規則。

⚠ 這代表 `BRUN30` 換模組時,進入的仍然是**該檔的 loader stub**(因為 MZ CS:IP 指向那裡),
不是直接跳進模組本體。stub 會發現執行期已經在了,再把控制交回去。
**這條鏈的最後一段(執行期怎麼跳進模組本體)仍未解。**

### 兩個簽章的分工

| 簽章 | 值 | 出現在 |
|---|---|---|
| `bz` | `0x7A62` | 十一支遊戲模組 |
| `bm` | `0x6D62` | `USERLIB.EXE`(`docs/re/01` §4 觀察到標頭前綴是 `bm`)|

`sub_14CB8` 兩者都檢查 —— 印證了 `docs/re/02` §4 的架構圖:
執行期要能載入這兩種不同角色的模組。

## 4. ⚠ 一個被驗掉的假設

看到 `0x1164D` 的 `mov word ptr ds:0A28h, 0B06h` 時,第一個念頭是
「`0x0B06` 是模組本體的進入點位移」—— 因為它是個固定常數,而 BASIC 編譯器
確實可能用固定的啟動位移。

**追進 `sub_14CB8` 之後發現它是檔名字串的指標**(`mov dx, bx` → `INT 21h AH=3Dh`)。

判準:**一個常數是「位址」還是「指標」,要看使用端怎麼用它,不能從值的樣子猜。**
同 kb `ida-pro-9.4.md`「找到常數只是第一關,讀出來還有第二關」。
