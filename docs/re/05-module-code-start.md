# 05 — 模組程式碼起點,與強制反組譯的結果

日期:2026-08-13
接續:[`04-module-layout-entry.md`](04-module-layout-entry.md)

## 結論

`bz` 標頭長 **`0x30` bytes**,模組程式碼從 **`bz+0x30`** 開始(11/11 驗證)。
但**光知道起點不夠** —— 從那裡強制反組譯,指令流在 271 bytes 內就散掉(涵蓋率 0.7%)。
原因指向 `INT 3Dh`/`3Eh`/`3Fh` 帶內嵌參數,IDA 把參數位元組當成下一個 opcode。

## 1. 程式碼起點 = `bz+0x30`

**信心等級:已確認。** 十一支的 `bz+0x30` 全部是合法的 8086 指令起點:

| EXE | `bz+0x30` 起 | 判讀 |
|---|---|---|
| `MENU` | `e9 46 00` | `JMP` near `+70` |
| `TOWN` / `CAMP` / `WRLDMOVE` / `CHARUTIL` | `e9 33 00` | `JMP` near `+51` |
| `CMBT` / `MAZEMOVE` | `e9 3d 00` | `JMP` near `+61` |
| `START` | `bb ff ff` | `mov bx, 0FFFFh` |
| `MTEST` / `MIO2` | `bb 01 00` | `mov bx, 1` |
| `WSIO` | `c7 06 f6 53 03 00` | `mov word ptr [53F6h], 3` |

七支是**跳過資料的典型開場**(`JMP` 越過一塊常數區再進主流程),
四支直接開始 —— 那四支剛好都是最小的模組(384–1,760 bytes),沒有資料區要跳。

**注意 `START` / `MTEST` / `MIO2` 的第二條指令都是 `INT 3Eh`** —— 這三支幾乎沒有自己的
邏輯,一進去就呼叫執行期,與 `docs/re/03` §3「它們的重定位門檻是 0(全部指向執行期)」相符。
**兩個獨立觀察指向同一件事。**

## 2. 強制反組譯:失敗,但失敗本身是資訊

`tools/ida/unlock_module.py` 從 linear `0x10040`(= `seg000` 起點 + `0x10` + `0x30`)
`create_insn` + `add_func` + `plan_and_wait`,對 `CMBT.EXE`:

| 指標 | 值 |
|---|---:|
| 模組區大小 | 36,752 bytes |
| 新增函式 | 9 |
| 函式涵蓋 | 140 bytes |
| 被判成指令的位元組 | 271 |
| **涵蓋率** | **0.7%** |

指令流沒有連鎖展開,幾十個 byte 就斷。
**起點是對的(第一條指令解得出來),斷在後面** —— 所以問題不在入口,在指令流本身。

## 3. 為什麼會斷:`INT` 帶內嵌參數(假設)

**信心等級:假設。** 證據有二,都還不夠成為「已確認」。

### 證據一:形狀吻合 far call 的大小

`docs/re/03` §3 已確認 linker 會**就地修補**程式碼。而

```
CD 3F nn 90 90     ← 5 bytes
9A oo oo ss ss     ← far call,也是 5 bytes
```

`INT` + 1 個內嵌參數 + 兩個 `NOP` 剛好等於一個 far call 的長度。
這是「先擺佔位、載入時改寫」最自然的做法 —— 佔位與目標必須等長。

### 證據二:密度與比例

七支主要模組(合計 133,376 bytes)的**原始位元組掃描**:

| 中斷 | 出現 | 後接 `xx 90 90` | 比例 |
|---|---:|---:|---:|
| `INT 3Dh` | 941 | 245 | 26.0% |
| `INT 3Eh` | 2,616 | 1,351 | 51.6% |
| `INT 3Fh` | 4,062 | 2,027 | 49.9% |
| 合計 | 7,619 | 3,623 | 47.6% |

⚠ **這是上限不是實數。** 掃描涵蓋整個模組區,而模組區裡有資料;
資料中偶然出現 `CD 3F` 的位元組也會被算進去。
**在能分辨程式碼與資料之前(那正是本文要解的問題),這些數字不能當精確值。**

### 這一條要怎麼裁決

不是繼續掃位元組,而是:

1. 讀 `BRUN30.EXE` 裡**安裝** `INT 3Dh`/`3Eh`/`3Fh` 向量的那段(`INT 21h AH=25h`),
   從處理常式回推它讀不讀 `CS:IP` 之後的位元組
2. 拿到參數長度之後,在 IDA 裡把這些 `INT` 標成「後面跟 N bytes 資料」,再重跑分析

依 `CLAUDE.md` §1.2,這裡只需要解到「**這個 INT 消耗幾個位元組、呼叫了什麼**」,
不追中斷向量在 DOS 層的安裝細節。

## 4. ⚠ 方法上的一個坑(自己踩到)

第一版的密度統計把 `INT 3Fh` 算成 **133,383 處** —— 相當於模組總位元組的 99.7%,
一個 2-byte 樣式不可能有這種命中率。

原因:用 `re.finditer(bytes([0xCD, 0x3F]), body)` 掃描,
而 `bytes([0xCD, 0x3F])` 是 `b'\xcd?'` —— **`?` 在正規表示式裡是量詞**,
整個樣式變成「一個可有可無的 `\xcd`」,於是每個位置都命中。
(`0x3D` = `=`、`0x3E` = `>` 不是 metacharacter,所以那兩個數字沒受影響 ——
**同一次掃描裡只有一部分結果是壞的**,更難察覺。)

**判準:用位元組樣式掃二進位檔時,不要走正規表示式** ——
用 `bytes.find` 或 `re.escape`。而抓到它靠的是**量級檢查**:
命中數不該接近檔案大小。**任何統計出來之後先問一次「這個量級合理嗎」。**
