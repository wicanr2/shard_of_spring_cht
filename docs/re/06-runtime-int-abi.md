# 06 — 執行期呼叫介面(`INT 3Dh` / `3Eh` / `3Fh`)與模組解鎖

日期:2026-08-13
接續:[`05-module-code-start.md`](05-module-code-start.md)

## 結論

模組呼叫執行期用三個中斷,**每一個都帶內嵌參數**。
把參數長度教給 IDA 之後,模組本體的反組譯涵蓋率從 **0.7% 升到 40.8%**,
十一支合計 105,952 bytes 裡只剩 **42 個位元組**解不開。

`docs/re/05` §3 的假設(`CD xx nn 90 90` 是 far call 的佔位形式)**已確認** ——
證據是 `INT 3Dh` 處理常式自己會把那五個位元組改寫成 `9A`。

## 1. 向量安裝

`BRUN30.EXE:0x10526`(另有一組在 `0x10C7A`)用 `INT 21h AH=25h` 裝三支處理常式:

| 中斷 | 處理常式 | 派工表 |
|---|---|---|
| `INT 3Dh` | `CS:0x0048` | `cs:0x171` |
| `INT 3Eh` | `CS:0x00BB` | `cs:0x243` |
| `INT 3Fh` | `CS:0x00E9` | `cs:0x38D` |

CS 基底 `0x10000`,所以三支的 linear 位址是 `0x10048` / `0x100BB` / `0x100E9`。

**信心等級:已確認。**

## 2. `INT 3Eh` / `INT 3Fh`:固定 3 bytes

兩支結構完全相同,只差派工表位址:

```
CD 3E nn        ; nn = 派工表索引
CD 3F nn
```

處理常式的做法:

```
pop bx / pop ds          ; bx = 中斷後的位址,ds = 該節區
inc bx / push bx         ; 返回位址 +1  → 跳過參數位元組
mov bl, [bx-1]           ; 取參數
xor bh, bh / shl bx, 1   ; ×2 = word 索引
push word ptr cs:[bx+<表>]
retn                     ; 跳到表裡的目標
```

**指令總長固定 3 bytes。** 參數是 8-bit,所以每張表最多 256 個進入點。

## 3. `INT 3Dh`:三種情況,長度不固定

參數位元組以**帶號**判讀(`cmp byte ptr [bx], 0` 後 `jle` / `jl`):

| 參數 | 長度 | 行為 |
|---|---|---|
| `> 0` | **3 bytes** | 同 `3Eh`/`3Fh`,索引 `cs:0x171` |
| `== 0` | **5 bytes** | `CD 3D 00 oo oo` → **就地改寫成 far call** |
| `< 0` | — | 直接返回 |

### `== 0` 的自我改寫(`0x10080`–`0x100A5`)

```
add bx, 3                    ; 跳過 00 oo oo
mov si, [bx-2]               ; 取那 2 bytes 當索引
les si, es:[si]              ; 從表裡解出 far 指標
mov byte ptr [bx-5], 9Ah     ; ★ 把 CD 改寫成 9A(far call 的 opcode)
mov [bx-4], si               ; 填 offset
mov word ptr [bx-2], es      ; 填 segment
```

`CD 3D 00 oo oo`(5 bytes)→ `9A oo oo ss ss`(5 bytes)。
**佔位與目標等長,所以可以就地換掉** —— 這就是 `docs/re/05` §3 推測的那個機制,
現在有了直接證據。第一次呼叫走中斷、解析完就把自己變成直接的 far call,
之後每次都是原生速度。這是**延遲繫結(late binding)**。

⚠ 這也表示**執行中的記憶體映像與磁碟上的位元組不同**。
之後若要拿 DOSBox 的記憶體 dump 對照靜態反組譯,這一點必須先扣掉。

## 4. 解鎖結果

`tools/ida/unlock_module.py` 從 `bz+0x30`(linear `0x10040`)線性掃描,
遇到三個中斷就依上表跳過參數:

(BASIC 模組把字串、常數表、陣列直接放在同一個節區)。

### ⚠ 掃描範圍的限制(不要把上表讀成全模組)

腳本掃的是 **`seg000` 一個段**,不是整個模組區:

- `CMBT` 的模組區 41,648 bytes,`seg000` 36,752 → 涵蓋 **88%**
- `START` 的模組區 384 bytes,`seg000` 只有 48 → 涵蓋 **12.5%**

四支小模組(`START`/`MTEST`/`MIO2`/`WSIO`)的內容大半在 `seg001`–`seg004`,
上表沒掃到,所以**它們的 0 個函式不代表沒有程式碼**。
主要的七支遊戲模組不受影響。**下一輪要把掃描擴到全部段。**

## 5. 這一輪打開了什麼

`CLAUDE.md` §2.2 看板上,A 項(執行檔架構)的瓶頸解除:

- 160 個函式可讀了(此前是 0)
- 7,673 個執行期呼叫點有了位置與索引 —— **派工表的索引就是「這裡呼叫了執行期的哪個功能」**,
  把三張表(`cs:0x171` / `0x243` / `0x38D`)解出來,就等於拿到整套執行期 API 的對照表
- D–L 各子系統的資料格式,現在可以從**讀取端**去找(而不是只能猜資料本身)
