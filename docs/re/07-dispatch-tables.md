# 07 — 執行期派工表,與「程式碼／資料尚未分離」這個限制

日期:2026-08-13
接續:[`06-runtime-int-abi.md`](06-runtime-int-abi.md)

## 結論

三張派工表的**位置**已確認,**容量與語意未解**。
容量沒有被量到 —— 處理常式只給了基底沒給上限(§3)。
呼叫統計仍標為含雜訊,因為線性掃描分不出程式碼與資料([`08`](08-code-data-separation.md))。

## 1. 三張表

| 中斷 | 表位址(linear) | 前幾筆目標(BRUN30 段內位移) |
|---|---|---|
| `INT 3Dh` | `0x10171` | `0x0000`, `0xAC92`, `0xACA2`, `0xACB2`, `0xAD0A`, … |
| `INT 3Eh` | `0x10243` | `0x09FA`, `0x0B25`, `0x0B1A`, `0x0B09`, `0x6260`, … |
| `INT 3Fh` | `0x1038D` | `0x9580`, `0x1F86`, `0x45AC`, `0xF92D`, `0xF915`, … |

三張表在記憶體裡相鄰。若照間距推算容量:
`3Dh` 105 筆(`0x171`–`0x243`)、`3Eh` 165 筆(`0x243`–`0x38D`)、`3Fh` 表尾未知。

**信心等級:表位址已確認**(直接讀 §`docs/re/06` §1 的處理常式);
**容量是推算,未確認**。

## 2. ⚠ 本節已被推翻:遊戲模組**有**使用 `INT 3Dh`

> 下面整節的結論與數字都是錯的,成因見 [`44`](44-int3d-is-used-after-all.md):
> 清點時用 `print_insn_mnem(head) != "int"` 過濾,而 IDA 把 `CD 3D` 顯示成 `wait`
> (浮點模擬器向量的慣例),227 處全被濾掉。
> **實際是七支模組合計 909 處、24 個相異索引**;本節撤掉的「346」也是對的
> (= `3D:00`,延遲繫結 far call)。
> 保留原文是為了留下錯誤的形狀 —— 注意下表「227」與內文「沒有一個是指令的起點」
> **在同一節裡互相矛盾**。

## 2.(已推翻)遊戲模組不使用 `INT 3Dh`

**信心等級:已確認**(對 `CMBT.EXE` 的完整清點)。

| 項目 | 數 |
|---|---:|
| 解碼成 `int 3Fh` | 942 |
| 解碼成 `int 3Eh` | 804 |
| **解碼成 `int 3Dh`** | **0** |
| 位元組層的 `CD 3D` 出現次數 | 241 |
| 其中落在程式碼區的位址 | 227 |

227 個 `CD 3D` 落在程式碼區,卻**沒有一個是指令的起點** ——
它們是別的指令內部的位移或立即數位元組。

⚠ **這推翻了 `docs/re/06` §4 表格裡的「`3D` far 形式」欄位**(該欄合計 346)。
那個數字是解鎖腳本在**線性掃描過程中**的中間計數,而線性掃描會把資料當成程式碼掃過去;
最終資料庫裡一個都不成立。**中間產物不是結論。**

`INT 3Dh` 的自我改寫機制(`docs/re/06` §3)本身仍然成立 ——
那是從處理常式的指令直接讀出來的,與模組用不用它是兩回事。
它應該是**執行期內部**或 `USERLIB` 那一側在用。

## 3. 表的容量是推算,不是量出來的

`3Eh` 表若從 `0x243` 到 `0x38D`,容量 165 筆(索引 0–164)。
但模組實際用到索引 `0xA5`(165)。

查證的結果是**兩張表相鄰**:

```
3E[165] = 0x9580
3F[0]   = 0x9580     ← 同一個 word
```

**相鄰只約束位置,不約束長度。** 兩張表可以重疊,
讓後一張的開頭同時當前一張的尾端是省空間的常見做法。
所以「索引 165 非法」推不出來,而**表的容量至今沒有被量到** ——
處理常式只給了基底,沒有給上限。

要定案得從別處來:數 `BRUN30` 裡有多少支常式被這些表指到,或找建表的程式碼。

⚠ 本節第一版曾據此宣告「索引 `0xA5` 是線性掃描造出的假指令」。
訂正過程與判準見 [`08-code-data-separation.md`](08-code-data-separation.md) §3。
