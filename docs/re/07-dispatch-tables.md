# 07 — 執行期派工表,與「程式碼／資料尚未分離」這個限制

日期:2026-08-13
接續:[`06-runtime-int-abi.md`](06-runtime-int-abi.md)

## 結論

三張派工表的位置與內容已取出。但**呼叫統計目前不可信** ——
線性掃描無法分辨程式碼與資料,在資料區造出了假的 `int` 指令,
而且已經有一條**硬證據**證明這件事(§3)。

在把程式碼與資料分開之前,執行期 API 對照表不能定案。

## 1. 三張表

| 中斷 | 表位址(linear) | 前幾筆目標(BRUN30 段內位移) |
|---|---|---|
| `INT 3Dh` | `0x10171` | `0x0000`, `0xAC92`, `0xACA2`, `0xACB2`, `0xAD0A`, … |
| `INT 3Eh` | `0x10243` | `0x09FA`, `0x0B25`, `0x0B1A`, `0x0B09`, `0x6260`, … |
| `INT 3Fh` | `0x1038D` | `0x9580`, `0x1F86`, `0x45AC`, `0xF92D`, `0xF915`, … |

三張表在記憶體裡相鄰。若照間距推算容量:
`3Dh` 105 筆(`0x171`–`0x243`)、`3Eh` 165 筆(`0x243`–`0x38D`)、`3Fh` 表尾未知。

**信心等級:表位址已確認**(直接讀 §`docs/re/06` §1 的處理常式);
**容量是推算,未確認**。

## 2. 遊戲模組不使用 `INT 3Dh`

**信心等級:已確認**(對 `CMBT.EXE` 的完整清點)。

| 項目 | 數 |
|---|---:|
| 解碼成 `int 3Fh` | 942 |
| 解碼成 `int 3Eh` | 804 |
| **解碼成 `int 3Dh`** | **0** |
| 位元組層的 `CD 3D` 出現次數 | 241 |
| 其中落在程式碼區的位址 | 227 |

227 個 `CD 3D` 落在程式碼區,卻**沒有一個是指令的起點** ——
它們是別的指令內部的位移或立即數位元組。

⚠ **這推翻了 `docs/re/06` §4 表格裡的「`3D` far 形式」欄位**(該欄合計 346)。
那個數字是解鎖腳本在**線性掃描過程中**的中間計數,而線性掃描會把資料當成程式碼掃過去;
最終資料庫裡一個都不成立。**中間產物不是結論。**

`INT 3Dh` 的自我改寫機制(`docs/re/06` §3)本身仍然成立 ——
那是從處理常式的指令直接讀出來的,與模組用不用它是兩回事。
它應該是**執行期內部**或 `USERLIB` 那一側在用。

## 3. 硬證據:呼叫統計含假陽性

七支模組的掃描結果顯示 `INT 3Eh` 用到索引 `0xA5`(165)。
但 `3Eh` 表若從 `0x243` 到 `0x38D`,合法索引只到 164。

驗證方法:**如果索引 165 越界,它讀到的應該正好是 `3Fh` 表的第 0 筆。**

```
3E[165] = 0x9580
3F[0]   = 0x9580     ← 相同
```

**確實越界。** 所以 `INT 3Eh 索引 0xA5` 這個「呼叫點」不是真的呼叫 ——
它是線性掃描在資料區把 `CD 3E A5` 這三個位元組解成指令的產物。

這條驗證只花了一次查表,而它擋掉的是「拿一張混著雜訊的表去推 API 語意」——
那會讓後續每一條推論都帶著不知道多大的誤差。

## 5. 下一步:先分離程式碼與資料

在此之前,派工表的語意推不下去。可行的順序:

1. **從進入點做流程追蹤(recursive descent)取代線性掃描。**
   從 `bz+0x30` 沿 `call`/`jmp`/條件跳躍展開,只把真正到得了的位址標成程式碼。
   `INT 3Eh`/`3Fh` 是 3 bytes、不改變流程(`push`+`retn` 到目標後會返回),
   所以可以直接跨過去繼續追。
2. 追完之後重跑 §4 的統計,索引越界的問題應該會自動消失 —— **那就是驗證**。
3. 再從高頻進入點反查 `BRUN30` 的目標函式,推語意。
