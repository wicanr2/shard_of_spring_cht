# 08 — 程式碼／資料分離:兩種方法都不夠,原因是模組由執行期驅動

日期:2026-08-13
接續:[`07-dispatch-tables.md`](07-dispatch-tables.md)

## 結論

從 `bz+0x30` 做流程追蹤只到得了 **5.4%** 的模組區,線性掃描則是 **42.8%** 但含雜訊。
差距不是工具問題:**BASIC 編譯的模組是被執行期呼叫的,不是從進入點一路跑下來的**。
所以「從進入點追」在結構上就到不了大部分程式碼。

下一步不是改進追蹤演算法,是找出**模組把哪些位址交給執行期**。

## 1. 兩種方法的數字(`CMBT.EXE`,模組區 36,816 bytes)

| 方法 | 到得了 | 判成指令 | 涵蓋率 | 函式 | 解不開 |
|---|---:|---:|---:|---:|---:|
| 線性掃描(`unlock_module.py`) | — | 15,722 | 42.8% | 30 | 11 |
| **流程追蹤(`trace_module.py`)** | 5,015 | 1,973 | **5.4%** | 4 | 2 |

**兩者都不是答案:**

- 線性掃描**高估** —— 它把資料當程式碼掃過去
- 流程追蹤**低估** —— 它只到得了從進入點沿控制流可達的部分

真值在兩者之間。**在找到模組交給執行期的進入點清單之前,無法收斂。**

## 2. 為什麼流程追蹤到不了

`docs/re/06` 已確認:模組透過 `INT 3Eh`/`3Fh` 呼叫執行期。
但反過來 —— **執行期也會呼叫模組** ——
BASIC 的事件、副程式、錯誤處理都是執行期在驅動。

那些進入點不會出現在模組自己的 `call`/`jmp` 目標裡,
所以 recursive descent 從定義上就到不了。

這也解釋了 `docs/re/04` §5 掛著的那一項(「執行期怎麼把控制交進模組本體」)——
它不是一個進入點,是**一組**。

## 3. ⚠ 訂正 `docs/re/07` §3

上一輪寫了:「`INT 3Eh` 索引 `0xA5` 是線性掃描在資料區造出的假指令」。

**那個結論不成立。** 保守得多的流程追蹤(只走可達路徑)**同樣產生 `3E:A5`**,
而且範圍一致(`3E` 到 `0xA5`、`3F` 到 `0xC9`)。
一個在兩種獨立方法下都出現的呼叫點,不能當成單一方法的雜訊。

實際成立的只有那條**觀察**:`3E[165]` 與 `3F[0]` 讀到同一個 word(`0x9580`)。
從它推不出「索引 165 非法」——**能推出的只是「表是相鄰的」**。

錯在把「兩張表相鄰」讀成「第二張表的起點就是第一張表的終點」。
相鄰只約束位置,不約束長度;兩張表**可以重疊**,
而在手寫組語的年代,讓兩個派工表共用尾端進入點是省空間的常見做法。

**判準:一個推論若只在某一種測量方法下成立,先換一種方法再下結論。**
這一次換方法只花了一次執行,而錯誤結論會讓整張 API 表的過濾條件失準。

因此 `docs/re/07` §4 的呼叫統計**恢復可用**,但仍標為**含雜訊** ——
線性掃描的假陽性問題本身沒有被否定,只是不能用 `3E:A5` 當證據。

## 4. 兩種方法的正確用法

| 用途 | 用哪個 |
|---|---|
| 找「哪些位址一定是程式碼」(下界) | 流程追蹤 |
| 找「哪些位址可能是程式碼」(上界) | 線性掃描 |
| **交集** | 高信心的程式碼區 |
| **差集** | 待判定,要靠執行期進入點清單收斂 |

`tools/ida/` 兩支都保留,不刪其中一支。

## 5. 下一步

找模組交給執行期的進入點清單。三條線索:

1. **`bz` 標頭尚未解讀的欄位**(`+0x0A`、`+0x18`–`+0x2F`)——
   `+0x0A` 的值與 `+0x16` 相同(十一支皆然),其餘未知。
   進入點表的指標很可能在這裡。
2. **`BRUN30` 呼叫模組的那一側** —— 在執行期裡找「用模組節區當 `CS` 做 far call」的地方。
3. **`docs/re/04` §3 的載入流程** —— `sub_14CB8` 之後,執行期一定要拿到某個位址才能開始跑。

依 `CLAUDE.md` §1.2,只需要解到「進入點清單在哪、有幾筆」,
不需要追執行期內部的排程細節。
