# 09 — `bz` 標頭是一張節區表

日期:2026-08-13
接續:[`08-code-data-separation.md`](08-code-data-separation.md)

## 結論

`bz` 標頭裡有**六個欄位是模組內部的節區邊界**(單位 paragraph),
與 IDA 自動分析出的段起點 **11/11 × 6 = 66/66 完全相符**。

這給出模組的內部佈局:程式碼區、三個小區、一個資料區。
**程式碼只在第一段裡** —— `docs/re/08` 卡住的「程式碼／資料分離」因此有了上界的硬邊界。

## 1. 欄位對應

| 欄位 | 對應 | 說明 |
|---|---|---|
| `+0x24` | 第 2 段起點 | **＝ 程式碼區的結束**(第 1 段 = `[0, +0x24)`)|
| `+0x26` | 同 `+0x24` | 十一支都與 `+0x24` 相同 |
| `+0x28` | 第 3 段起點 | |
| `+0x0C` | 第 4 段起點 | |
| `+0x2A` | 第 5 段起點 | |
| `+0x0A` | **最後一段的起點** | |
| `+0x16` | 模組結束(stub 起點) | 見 [`04`](04-module-layout-entry.md) |

**信心等級:已確認**(66/66,兩個來源:EXE 的位元組 vs IDA 的段分析)。

## 3. ⚠ 訂正 `docs/re/03` §5

該節寫著「`+0x0A` 的值與 `+0x16` 相同(十一支皆然)」。
**`MENU.EXE` 不成立**:`+0x0A = 0x3D3`、`+0x16 = 0x462`。

正確的說法是 `+0x0A` = **最後一段的起點**。十支模組剛好只有六段,
最後一段的起點就等於模組結束,於是兩個欄位看起來一樣 ——
**十一分之十的巧合被讀成了規則。**

判準:宣告「N/N 皆然」之前,先確認那 N 筆裡有沒有結構不同的個體。
`MENU` 的段數在 `docs/re/01` 的清冊裡就寫著 7(其餘是 6),線索一直都在。

## 5. 這一輪打開了什麼

`docs/re/08` 的收斂問題有了硬邊界:**程式碼只可能在 `[0, +0x24)`**。
以 `CMBT` 為例,線性掃描掃的 36,752 bytes 幾乎全部落在程式碼區內
(程式碼區 36,816 bytes),所以那 42.8% 的上界**不會因為掃到資料段而虛高** ——
虛高只可能來自程式碼區內部的常數資料。

後面四個小段與一個大段是模組的資料區。以 `CMBT` 為例最後一段有 4,640 bytes ——
**遊戲的全域變數應該在那裡**,這是 D–L 各子系統要找的東西。
