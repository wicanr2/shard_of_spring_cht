# 10 — 執行期不會 far call 進模組,所以低涵蓋率另有原因

日期:2026-08-13
接續:[`09-bz-segment-map.md`](09-bz-segment-map.md)

## 結論

`BRUN30.EXE` 全檔只有 **13 處 far 轉移,而且 13 處目標全在 `BRUN30` 自己內部**,
**零處間接**。所以 `docs/re/08` §2 的推論——「模組是被執行期呼叫的,
因此流程追蹤到不了」——**不成立**。

模組本身就是主程式,執行期是被呼叫的一方。
流程追蹤只到 5.4% 必然另有原因。

## 1. 證據

| 項目 | 數 |
|---|---:|
| `BRUN30` 裡的 far `call`/`jmp` | 13 |
| 其中間接(運算元帶 `[]`) | **0** |
| 目標落在 `BRUN30` 之外 | **0** |

13 處的目標分別是 `sub_1205E`、`sub_1A98B`、`sub_1A97E`、`sub_1C5FB`、
`sub_1AC92`、`sub_1ACA2`、`sub_1B520`、`sub_1B369`、`sub_1B4A0`、`sub_1A97A` ——
全部是 `BRUN30` 自己的位址。

⚠ 這條證據有一個範圍限制:`BRUN30` 有 8% 的內容 IDA 沒分析到
([`01`](01-inventory.md) §1),那部分裡若有 far 轉移就不會出現在上表。
**結論的正確說法是「在已分析的 92% 裡沒有」,不是「絕對沒有」。**

## 2. 訂正 `docs/re/08` §2

該節寫著:

> BASIC 的事件、副程式、錯誤處理都是執行期在驅動。
> 那些進入點不會出現在模組自己的 `call`/`jmp` 目標裡,
> 所以 recursive descent 從定義上就到不了。

**那是推測,而且與 §1 的證據衝突。** 寫的時候沒有去查執行期到底有沒有這樣呼叫,
只憑「BASIC 執行期通常這樣運作」的類推就當成解釋 ——
違反第一性原理(拆到機制再往上推,不靠慣例搪塞)。

## 3. 重新提出的解釋(假設,未驗證)

`INT 3Eh`/`3Fh` 的處理常式會 `retn` 回 thunk 之後的位址([`06`](06-runtime-int-abi.md) §2),
所以控制流確實會繼續。但 BASIC 執行期有一個常見做法:
**thunk 後面接內嵌參數**(字串常數、變數位址、行號),由被呼叫的常式自己跳過。

若成立,流程追蹤在 `ea+3` 會撞進參數而散掉 —— 症狀與觀察到的完全一致
(追蹤在 5,015 bytes 停下、2 個位址解不開)。

**這只是假設。** 裁決方式:
取流程追蹤實際中斷的那幾個位址,檢查它們前面最近的 thunk 索引,
再讀 `BRUN30` 裡對應的常式看它返回前有沒有調整返回位址。
若某些索引的常式會把返回位址往後推 N,那 N 就是該 API 的內嵌參數長度。

## 4. 這一輪的教訓

`docs/re/08` §2 的錯誤與 [`09`](09-bz-segment-map.md) §3 的錯誤形狀不同但根源相同:

| | 錯法 |
|---|---|
| `09` §3 | 十一分之十的巧合被讀成規則 —— **沒檢查反例** |
| `08` §2 | 用「BASIC 執行期通常這樣」解釋觀察 —— **沒檢查機制** |

兩者都是**在有辦法直接查的時候選擇了推測**。
本例的查證成本是一支掃描腳本、一次執行。
