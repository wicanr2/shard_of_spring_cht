# 108 — 時鐘的哪一級對應哪個標籤:這一輪沒解出來

日期:2026-08-14
接續:[`107-clock-is-four-levels.md`](107-clock-is-four-levels.md)
子系統:**D. 角色/隊伍資料**

## 結論

**沒解出來。** 記錄嘗試與失敗的形狀,免得下一輪重走。

## 1. 做了什麼

`USERLIB` 的狀態列字串是**單一 `<len><ptr>` 描述子**格式
([`63`](63-userlib-strings-and-l-correction.md)),程式碼引用**文字位址 − 4**。
四個標籤的引用點:

| 標籤 | 描述子 | 引用點 |
|---|---|---|
| `Hour:` | `0x3184` | `0x10CD1` |
| ` Day:` | `0x318E` | `0x10D02` |
| `  In the Month ` | `0x3198` | `0x10D34` |
| `Visibility =` | `0x31B8` | `0x10DBC` |

**四個引用點之後 60 bytes 內,一個計時變數都沒有出現**
(掃 `mov ax,ds:xxxx` / `mov ds:xxxx,ax` / `mov bx,ds:xxxx`,
目標是 `ds:3536h`/`3538h`/`353Ah`/`353Ch` 與其他八個已知的 `GROUPS.DAT` 來源變數)。

## 2. 這代表什麼

顯示端**不直接讀計時器**。三種可能,**都沒有證據**:

1. 值先被搬進暫存變數(例如 [`105`](105-visibility-fields.md) 看到的 `ds:3078h`),
   顯示端只讀暫存
2. 用的是 `[reg+disp]` 形式而不是絕對定址,我的掃描抓不到
3. 60 bytes 的窗太小

**第 2 種最值得先試** —— 本專案在 [`73`](73-monster-columns-to-combat-array.md)
就吃過一次虧:陣列存取用 `[reg+base]`,掃絕對位址是零命中。

> **判準:掃描回空時,先問「這個目標會不會用另一種定址形式」。**
> 這已經是同一個坑的第三次([`70`](70-key-chains-all-modules.md) §6 是分母、
> [`102`](102-flee-exists-retracting-j.md) 是查詢式、這次是定址形式)——
> **三次的共同點是「我掃的形狀太窄」,而每次窄的地方都不同。**

**D 不標 RE-DONE。** 明確的缺口清單:

1. `CHARS.DAT` 位移 84(→ 屬性 12)
2. `GROUPS.DAT` 位移 25、31 的語意([`107`](107-clock-is-four-levels.md) 撤回舊判讀後留下的)
3. `GROUPS.DAT` 位移 45、79 需重驗(語境字串法所得)
4. 四級計時器對三個標籤的對應(本篇)
5. 位移 81 僅假設
