# 11 — 追蹤是乾淨終止的,兩個假設都否證

日期:2026-08-13
接續:[`10-runtime-does-not-call-modules.md`](10-runtime-does-not-call-modules.md)

## 結論

流程追蹤只到 5.4% **不是因為解碼出錯**。它乾淨地跑完了所有靜態可達路徑。
從 `bz+0x30` 出發,真正到得了的就只有 **1,973 bytes / 4 個函式**。

模組區內**沒有任何 far 轉移**(0 處),所以模組是單一程式碼節區、全部用 near call。
剩下約 34,000 bytes 的程式碼,一定是**經由某種靜態看不到的方式**進入的。

## 1. 斷點分布(`CMBT.EXE`)

| 斷點原因 | 數 | 性質 |
|---|---:|---|
| `jmp` | 132 | 正常(目標已收進工作佇列繼續追)|
| `retn` | 3 | 正常(函式結束)|
| **解不開** | **2** | 唯一的異常 |

**只有 2 個位址解不開**,而且它們與前一個 thunk 的距離是**負值**
(`−363`、`−376`)—— 根本不在 thunk 後面。

## 2. 否證:thunk 後面接內嵌參數

[`10`](10-runtime-does-not-call-modules.md) §3 的假設是
「`INT` thunk 後接內嵌參數,追蹤撞進參數而散掉」。

**不成立。** 若成立,「解不開」的斷點應該密集出現在 thunk 之後幾個位元組處。
實際上全模組只有 2 處解不開,而且都不在 thunk 後面。

## 3. 模組區沒有 far 轉移

| 範圍 | far `call`/`jmp` |
|---|---:|
| `CMBT` 模組區(`0x10000`–`0x18FD0`) | **0** |
| `BRUN30` 全檔 | 13(全部內部,見 [`10`](10-runtime-does-not-call-modules.md))|

模組內部全是 near call,對執行期的呼叫全走 `INT` thunk。
**兩邊都沒有跨模組的靜態轉移** —— 這是一個乾淨的封閉結果,不是資料不足。

## 4. 那 34,000 bytes 怎麼進去的

剩下唯一沒被排除的機制:**模組把程式碼位址交給執行期,由執行期呼叫回來**。

BASIC 的 `GOSUB`、事件處理、錯誤處理都需要這種形式,
而位址會以暫存器或堆疊參數的形式在 `INT` thunk 前被準備好 ——
**那不是靜態控制流,任何 recursive descent 都追不到。**

⚠ **這是假設,不是結論。** 前兩個假設都是這樣提出、然後被證據推翻的
([`10`](10-runtime-does-not-call-modules.md) §4 記了那兩次的錯法)。

裁決方式:取幾個高頻 thunk 索引(`3F:61` 1,019 次、`3E:44` 520 次),
讀 `BRUN30` 裡對應的常式,看它有沒有把某個參數當成位址去 `call`。
**這是「讀機制」不是「看形狀」** —— 前兩次的錯誤都出在後者。

## 5. 目前的程式碼涵蓋率狀態

| 界 | 值 | 依據 |
|---|---:|---|
| 下界(靜態可達) | 1,973 bytes(5.4%) | 本文 |
| 上界(線性掃描) | 15,722 bytes(42.8%) | [`06`](06-runtime-int-abi.md) |
| 程式碼區硬邊界 | `[0, +0x24)` = 36,816 bytes | [`09`](09-bz-segment-map.md) |

下界已經**確定不會再往上**(靜態路徑走完了)。
要收斂只能靠 §4 —— 找出執行期回呼的進入點。
