# 12 — 第一個解出語意的執行期 API:`3F:61`

日期:2026-08-13
接續:[`11-trace-terminates-cleanly.md`](11-trace-terminates-cleanly.md)

## 結論

`INT 3Fh` 索引 `0x61`(七支模組合計 **1,019 次**,最高頻)對應
`BRUN30.EXE:0x19DAF`。它的行為是**四位元組描述子的複製**,
形狀符合 BASIC 的字串指派。

**它沒有把任何參數當成程式碼位址去呼叫** ——
所以 [`11`](11-trace-terminates-cleanly.md) §4 的回呼假設在這一支上**沒有得到支持**。

## 1. 常式內容(`0x19DAF`–`0x19DE5`)

```
mov  ds:0A08h, sp          ; 存堆疊指標(執行期的慣例前導)
push bx
call sub_1A0C4             ; 進位旗標決定是否走下面那段
jb   略過
  push cx / push dx
  xor  cx, cx
  mov  dx, [bx]
  call sub_1A129
  pop  dx / pop cx
xchg bx, dx
call sub_1A14E
push si / push di
mov  di, bx
mov  si, dx
movsw                      ; ★ 複製 4 bytes
movsw                      ; ★
xchg bx, dx
cmp  word ptr [bx], 0
jz   略過
  mov  di, [bx+2]
  mov  [di-2], dx
  call loc_1A119
```

**兩次 `movsw` = 4 bytes**,而 BASIC 的字串描述子正是
「長度(word)+ 資料指標(word)」這種四位元組結構。
之後的 `cmp word ptr [bx], 0` / `mov di, [bx+2]` 也是在讀同一個結構的兩個欄位。

**信心等級:證據充分**(形狀與呼叫頻率一致,但尚未用實跑或另一份資料印證)。

⚠ 依 `CLAUDE.md` §2.1,這還不到 **RE-DONE** ——
缺條件 3(獨立資料印證)。要補的話:在 DOSBox 裡讓遊戲顯示一段文字,
比對該描述子的內容。

## 2. 對回呼假設的意義

[`11`](11-trace-terminates-cleanly.md) §4 假設「模組把程式碼位址交給執行期、由執行期呼叫回來」。

這一支**沒有任何跡象**:它處理的是資料描述子,不碰程式碼位址。

但這只排除了**一支**。1,019 次呼叫佔七支模組全部 `3Fh` 呼叫的 26%,
而相異索引有 80 個。**不能從單一 API 推廣到整張表** ——
`docs/re/09` §3 的錯誤(十一分之十的巧合被讀成規則)正是這種形狀。

下一個該讀的是 `3E:44`(520 次)與 `3E:42`(502 次)——
它們是 `INT 3Eh` 那一族的最高頻,而 `3Eh` 與 `3Fh` 用不同的派工表,
語意分工可能不同。

## 3. 這是 API 對照表的第一列

| 中斷:索引 | 執行期位址 | 次數 | 語意 | 信心 |
|---|---|---:|---|---|
| `3F:61` | `0x19DAF` | 1,019 | 四位元組描述子複製(疑似字串指派) | 證據充分 |
| `3E:44` | `0x14333` | 520 | 未解 | — |
| `3E:42` | `0x14313` | 502 | 未解 | — |
| `3F:6E` | `0x199C7` | 461 | 未解 | — |
| `3F:55` | `0x19DE5` | 263 | 未解 | — |
| `3F:6A` | `0x199B3` | 258 | 未解 | — |
| `3F:62` | `0x19E1F` | 252 | 未解 | — |

⚠ 次數來自線性掃描的結果,標為**含雜訊**([`07`](07-dispatch-tables.md) §4)。
`3F:55` 的目標 `0x19DE5` 緊接在 `3F:61` 之後,兩者可能是同一族的變體。
