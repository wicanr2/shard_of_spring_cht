# 13 — `3E:42`,以及 `BRUN30` 未分析區擋住 API 對照

日期:2026-08-13
接續:[`12-api-3f61.md`](12-api-3f61.md)

## 結論

`3E:42`(502 次)是一支**把一個 word 附加到緩衝區**的常式,結構單純且完整讀出。
`3E:44`(520 次)的目標 `0x14333` 落在 `BRUN30` **IDA 沒有分析到的 8%** 裡,
倒出來是一整塊未切分的位元組 —— **API 對照要往下做,得先讓 `BRUN30` 全檔可讀。**

## 1. `3E:42` → `BRUN30:0x14313`

```
mov  ds:0A08h, sp        ; 執行期慣例前導(3F:61 也有)
or   bh, bh
jnz  <別的路徑>
push ax / push di
mov  al, 1               ; ← 0x1432D 是同一段但 al = 0
mov  ah, bl              ; 呼叫端的值放高位元組
mov  di, ds:74h          ; 目前的寫入指標
stosw                    ; 寫入 (al, ah) 這個 word,di += 2
mov  ds:74h, di          ; 指標寫回
pop  di / pop ax
retf
```

**行為:把 `(旗標, 呼叫端的 BL)` 這個 word 附加到 `ds:74h` 指的緩衝區,並前進指標。**

`0x1432D` 是同一段程式碼的另一個入口,唯一差別是 `al = 0`。
所以這是**一對變體** —— 兩個派工表索引共用實作,只差那個旗標。

**信心等級:證據充分**(指令流完整、無分支不確定性)。
**語意未定**:`ds:74h` 那個緩衝區是誰在讀還沒查,所以「這是輸出還是記錄」不能斷言。

⚠ 依 `CLAUDE.md` §2.1,這未達 RE-DONE ——
缺條件 2(用 xref 確認 `ds:74h` 的讀取端)與條件 3(獨立印證)。

## 2. `BRUN30` 的未分析區擋住 API 對照

`3E:44` 的目標 `0x14333` **緊接在 `3E:42` 的常式之後**,
但 IDA 在那裡沒有建立指令 —— 該位址落在 `docs/re/01` §1 記的
「`BRUN30` 有 8% 未分析」那一塊裡。

這是一個**方法上的阻塞,不是資料缺失**:
`BRUN30` 是十三支裡唯一自動分析正常的(709 函式、8% UNK),
當初沒有對它做過 `docs/re/06` 那種強制反組譯。

**下一步很明確:把 `unlock_module.py` 的手法套到 `BRUN30` 自己身上。**
它同樣有 `INT 3Dh` 的 5-byte 形式要處理([`06`](06-runtime-int-abi.md) §3),
而且 [`07`](07-dispatch-tables.md) §2 已經確認**遊戲模組不用 `3Dh`,
所以 `3Dh` 的使用者很可能就是 `BRUN30` 內部** —— 兩件事會一起解開。
