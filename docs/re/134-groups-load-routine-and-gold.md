# 134 — `GROUPS.DAT` 的載入常式:16 個欄位 → COMMON 變數,外加**金幣在位移 19**

日期:2026-08-15
子系統:**D. 角色／隊伍資料與存檔**
輸入:`MENU.EXE`、`CHARUTIL.EXE`(SHA-256 見 [`00-inputs.md`](00-inputs.md))

## 結論

1. **`GROUPS.DAT` 位移 19–22 是金幣**,4 bytes、**MBF 單精度浮點**(`CVS`)。
   [`formats/02`](../formats/02-groups-dat.md) 原本沒有這個欄位。**已確認**。
2. `MENU.EXE` `0x11830`–`0x119EC` 是**完整的載入常式**:
   把記錄的 16 個欄位一次搬進 COMMON 變數。整張對照表在 §2。
3. 這張表**逐條印證**了 [`101`](101-groups-record-status.md)、[`107`](107-clock-is-four-levels.md)、
   [`109`](109-clock-labels-resolved.md)、[`114`](114-maze-coordinates.md) 分別解出的變數身分 ——
   它們原本是四輪各自推的,現在是同一段程式碼一次列出。

## 1. 金幣為什麼不是整數欄

手冊 p.31 的截圖顯示 `Gold:63447`,而 **BASIC 的整數是有號 16-bit(上限 32,767)**。
所以金幣不可能用 `CVI`。

`MENU.EXE` `0x1185C`:

```
01185C  mov  bx, 34DCh      ; GROUPS.DAT 的記錄字串變數
01185F  mov  dx, 13h        ; 位移 19
011862  mov  cx, 4          ; 長度 4
011865  INT  3D:0A          ; MID$(rec$, 19, 4)
01186A  INT  3D:19          ; CVS —— 轉單精度
01186F  mov  di, 34C0h      ; 目標:金幣變數
011872  INT  3F:7D          ; 指派
```

### 三條互相獨立的證據

| # | 來源 | 內容 |
|---|---|---|
| 1 | `MENU` 載入常式 | 位移 19、長度 4、`CVS` → `ds:34C0`(上面那段)|
| 2 | `MENU` 狀態欄 `0x11A10` | 印 `'Gold:'` 後,`bx = 34C0h` + `INT 3F:6B`(**傳位址**,不是傳值)|
| 3 | `CHARUTIL` `0x11889` | 印 `'Gold:'` → `MID$(rec,19,4)` + `CVS` → 印 → 再印 `'Provisions:'` → 位移 23 |

第 3 條特別強:**同一個畫面上,金幣走位移 19 + `CVS`、補給品走位移 23 + `CVI`**,
兩者相距 15 行指令。這排除了「讀錯欄位」與「型別看走眼」。

⚠ 第 2 條的 `INT 3F:6B` 與第 3 條的 `INT 3F:6D` 是**不同的列印常式**:
`6D` 收 `bx` = 數值(整數),`6B` 收 `bx` = 位址(4-byte 浮點)。
**「傳值還是傳位址」本身就是型別證據**,不需要另外找型別標記。

> **判準**:一個欄位在畫面上顯示得出來、在記錄裡卻找不到,
> 先看它**用哪一支列印常式** —— 傳位址的那些不是 2-byte 整數,
> 而所有「找 2-byte 整數欄位」的掃描都會漏掉它們。
> [`89`](89-record-offset-census.md) 的 39 個位移全部來自 `ds:66D0h`(整數路徑),
> 金幣結構上不可能出現在那張清單裡。

## 2. 載入常式的完整對照表

`MENU.EXE` `0x11830`–`0x119EC`。形狀固定:

```
mov bx, 34DCh / mov dx, 66CCh / INT 3F:61     ; 綁定記錄字串
mov word ptr ds:66D0h, <位移>                 ; 設定位移
call sub_1008C                                ; CVI(MID$(rec, 位移, 2))
mov ds:<變數>, ax
```

| `GROUPS.DAT` 位移 | 目標變數 | 語意 | 先前出處 |
|---:|---|---|---|
| **19**(4B,`CVS`)| `ds:34C0` | **金幣** | **本篇** |
| 23 | (即時讀,不快取)| 補給品 | [`formats/02`](../formats/02-groups-dat.md) |
| 25 | `ds:3658` | 遭遇倒數 | [`107`](107-clock-is-four-levels.md) |
| 27 | `ds:3536` | 時鐘:月 | [`109`](109-clock-labels-resolved.md) |
| 29 | `ds:3538` | 時鐘:日 | 同上 |
| 31 | `ds:353A` | 時鐘:時 | 同上 |
| 33 | `ds:353C` | 時鐘:時以下 | 同上 |
| 35 | `ds:3518` | **世界 x** | [`43`](43-common-block-and-array-indexing.md) 訂正 |
| 37 | `ds:351A` | **世界 y** | 同上 |
| 41 | `ds:3520` | 朝向 | [`70`](70-key-chains-all-modules.md)、[`131`](131-world-passability.md) |
| 45 | `ds:365A` | 光源剩餘回合 | [`formats/02`](../formats/02-groups-dat.md) |
| 59 | `ds:35B2` | 有光時的能見度 | 同上 |
| 61 | `ds:35B2` | 無光時的能見度(**同一個目標,二選一**)| 同上 |
| 79 | `ds:351C` | 迷宮 x | [`114`](114-maze-coordinates.md) |
| 81 | `ds:351E` | 迷宮 y | 同上 |
| 83 | `ds:3534` | **當前迷宮編號**(99 = 不在迷宮)| [`169`](169-encounter-zone-selects-the-monster.md) §4、[`204`](204-light-burns-per-turn-and-offset-83.md) §1 |
| 85 | `ds:3532` | 逃跑旗標 | [`102`](102-flee-exists-retracting-j.md) |

**59 與 61 寫進同一個變數**,由一個分支二選一 —— 這正是
「有光/無光的能見度」這個語意的直接形狀:記錄裡存兩個常數,
載入時依當前光源狀態挑一個當**生效值**。

`ds:3534`(位移 83)載入後立刻與 **99** 比較(`0x119ED`),兩條分支挑的是
**下一支要 `CHAIN` 的模組名**:相等 → `WRLDMOVE`、不等 → `MAZEMOVE`
(那兩個字串在 `ds:77EA` / `ds:77F6`)。`WRLDMOVE` 自己也有
`mov word ptr ds:3534h, 63h`(= 99),與 `ds:365A = 0` 寫在一起 ——
回到地面時「迷宮編號歸哨兵、火把熄掉」。

**所以位移 83 是當前迷宮編號,99 = 不在迷宮**
([`204`](204-light-burns-per-turn-and-offset-83.md) §1)。
99 與 `CHARS.DAT` 位移 34/36 的「未裝備」剛好同值,但那是哨兵慣例相同,
不是同一件事。

⚠ [`118`](118-daylight.md) 寫的「在地面用天色、進迷宮用火把」是這一欄的
**消費端**,那條機制沒有改變;改變的只有欄位的名字。

## 3. 位移 19 補上了記錄開頭的缺口

[`formats/02`](../formats/02-groups-dat.md) 的第一個已知欄位是 23。
19–22 是金幣之後,`1`–`18` 仍然未知,而 `19`–`23` 連續。

| 範圍 | 狀態 |
|---|---|
| 1–18 | 未知 |
| **19–22** | **金幣**(4B 單精度)|
| 23–45 | 已知(見 §2)|
| 39、43 | 未知 |
| 47–57、63–77、87–90 | 未知 |
