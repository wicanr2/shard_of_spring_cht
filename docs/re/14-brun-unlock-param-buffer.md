# 14 — `BRUN30` 補齊分析,`ds:74h` 是參數累積指標

日期:2026-08-13
接續:[`13-api-3e42.md`](13-api-3e42.md)

## 結論

對 `BRUN30` 補做強制反組譯後,程式碼涵蓋率 **34.9% → 44.0%**、函式 **709 → 770**。
`3E:44` 因此可讀,而它揭示了 `3E:42` 的真正用途:
**那兩支不是輸出,是參數傳遞** —— 呼叫端一次推一個 word 到 `ds:74h` 指的小緩衝區。

## 1. 補齊結果

| 指標 | 之前 | 之後 |
|---|---:|---:|
| 判成指令的位元組 | 22,582(34.9%) | **28,462(44.0%)** |
| 函式 | 709 | **770** |
| 新建指令 | — | 5,880 |
| 解不開 | — | 338 |

做法與 [`06`](06-runtime-int-abi.md) 相同,但**不 `del_items`** ——
只在目前未定義的位址上補,既有分析全部保留。

**`INT 3Dh` 的使用點:0 處。** 所以 `BRUN30` 自己也不用 `3Dh`
(遊戲模組不用已見 [`07`](07-dispatch-tables.md) §2)。
剩下的候選是 `USERLIB.EXE`(`bm` 簽章那一支)。

## 2. `3E:44` → `BRUN30:0x14333`

```
call sub_11F6B
or   bh, bh / jnz ...
mov  al, 1
mov  ah, bl
mov  di, ds:74h
stosw                    ; 與 3E:42 完全相同的附加動作
cmp  di, 0C30h           ; ★ 上界檢查
jb   ...
mov  di, 0C26h           ; ★ 重設到下界
mov  ax, [di+4] / xchg ah, al
mov  bx, [di+6] / xchg bh, bl
mov  cx, [di+8] / xchg ch, cl
```

前半與 `3E:42` 逐條相同。後半多了**邊界檢查**:
指標到 `0xC30` 就重設回 `0xC26` —— 那是一塊 **10 bytes(5 個 word)** 的小緩衝區。

接著它從 `[di+4]`、`[di+6]`、`[di+8]` 讀三個 word,每一個都 `xchg` 高低位元組。

## 3. 重新解讀:`ds:74h` 是參數累積指標

**信心等級:證據充分。**

`3E:42`([`13`](13-api-3e42.md))與 `3E:44` 共用同一個附加動作,
而 `3E:44` 在緩衝區滿了之後**回頭把累積的值讀出來使用**。

合起來的讀法:**呼叫端一次推一個 word,累積在 `0xC26`–`0xC30` 這塊 10-byte 區,
湊齊之後由某一支把它們取出當參數。**

這解釋了為什麼這兩支的呼叫次數這麼高(502 + 520 = 1,022)——
它們不是「做一件事」,是「傳一個參數」。

⚠ 這同時修正了 [`13`](13-api-3e42.md) §1 的措辭。
該節寫「把 word 附加到緩衝區」在**動作層面正確**,
但沒有看出那是參數傳遞,於是把它歸類成疑似輸出。
**動作看對了,用途看錯了** —— 判準:一支常式頻繁被呼叫且只做一個小動作時,
先問「它是不是別人的前置步驟」,不要單獨解讀它。

`xchg` 高低位元組表示取出時要做位元組序轉換,
代表**存進去與用出來的位元組序不同** —— 但那三個值是什麼,尚未解。
