# 144 — 讓原版造一個角色,`CHARS.DAT` 的四個未解欄位一次現形

日期:2026-08-15
接續:[`143-character-creation.md`](143-character-creation.md)、[`133-chars-offset-1-is-party.md`](133-chars-offset-1-is-party.md)
子系統:**D. 角色資料**
輸入:`CHARS.DAT`(出貨)、DOSBox 實跑造出的 `CHARS.DAT`

## 結論

在 oracle 裡走完 `C)reate` 並回答 `Do you wish to keep this character (Y/N)?` = `Y`,
原版就把一筆全新的記錄寫進 `CHARS.DAT` 的第 6 槽。
拿它與出貨檔逐位元組相比,**四件事一次解決**:

| # | 結果 | 信心 |
|---|---|---|
| 1 | **背包是 10 格(位移 54–72),空格的哨兵是 `99`** —— 不是 15 格、不是 `0` | 已確認 |
| 2 | 位移 **74–83 是第二串十個旗標**,不是背包的後五格 | 已確認 |
| 3 | 位移 **89 = 剩餘技能點數** | 證據充分 |
| 4 | 位移 1:**`'0'` = 有角色但無隊伍、`'*'` = 空槽** —— 兩種語意分得開了 | 已確認 |

⚠ 第 1 項是**現行實作的 bug**:`EmptyPackSlot` 找的是值 `0` 的格子,
而每一格都是 `99` → **買東西永遠回「背包已滿」**。
畫面上那句話完全合理,所以這個 bug 不會被當成 bug。

> **判準**:一份定長記錄如果有「從沒被寫過」的欄位,
> **讓原版自己寫一筆**是最便宜的解法 ——
> 出貨資料只給你一個已經填好的狀態,而新記錄給你**創造時寫了哪些位移**,
> 那是兩份不同的資訊。這一步花了四次實跑,解掉了躺很久的四個未解項。

## 1. 做法

```
C)reate → T)roll → ESC ×4(跑完調整回合)→ 打名字 → Enter
        → Do you wish to keep this character (Y/N) ? → Y → E)xit
```

⚠ **`Y/N` 那一問是關鍵**。先前兩次實跑都停在名稱那一步就 ESC 掉了,
所以 `CHARS.DAT` 一個 byte 都沒變 —— 而「檔案沒變」看起來就像「創造沒有寫檔」。

⚠ 寫的是 `workplace/dosbox/game/` 的複本,**沒有碰 `game/sharspri/`**(`CLAUDE.md` §8)。

## 2. 新記錄逐欄

```
位移  1      '0'                     ← 不是 '*'
      2–11   'zztEst    '
      12     6                       角色編號
      14/15  'T' / '1'               巨魔 / 戰士
      16–24  5 / 13 / 3 / 12 / 5     速 力 智 體 技(已含種族修正)
      26/28  12 / 12                 最大/當前生命 = 體質
      30/32  0 / 0                   戰士沒有法力
      34/36  99 / 99                 未裝備
      38/40  0 / 1                   狀態正常 / 等級 1
      42–51  '0000001000'            技能旗標:第 7 格 = Armored skin
      52     0
      54–72  99 ×10                  **背包十格,全空**
      74–83  '0000000000'            第二串旗標
      84     0
      86–88  0x20 0x20 0x20          **創造也沒有寫這三個**
      89     3                       剩餘技能點數
      90–94  00 00 00 40 00          全部記錄都一樣
```

## 3. 背包是 10 格,哨兵是 99

[`formats/01`](../formats/01-chars-dat.md) 原本寫「位移 54 + 2i,15 格」。實際:

```
位移 54,56,…,72   十個 word,新角色全是 99
位移 74,76,…,82   讀成 word 是 12336 = 0x3030 = "00" —— 那是**字串不是數字**
```

出貨的五個角色**也全是 99 ×10 + "0000000000"**,零例外。
手冊 p.39 早就寫著「每個人身上只能帶 **10** 件東西」——
兩個獨立來源一致。

> **判準**:一串定長欄位要決定「有幾個」時,
> **看它在哪裡變成別的東西**,不要從記錄長度回推。
> 這裡 `12336` 三個記錄裡都一樣,而 `0x3030` 是兩個 ASCII `'0'` ——
> 「這個 word 的兩個 byte 都是可列印字元」就是欄位換型別的訊號。

⚠ **空格的哨兵是 `99`,與「未裝備」同一個值**。
先前實作用 `0` 當空格,於是 `EmptyPackSlot` 掃不到任何空位。

## 4. 位移 89 = 剩餘技能點數

| 角色 | 智力 | 位移 89 |
|---|---:|---:|
| 新造的巨魔(一點都沒花)| 3 | **3** |
| `Hard Axe` | — | 1 |
| 其餘四位 | — | 0 |

創造畫面右下角印 `Skills left:N`([`143`](143-character-creation.md) §3),
而新角色沒花任何點 → 剩餘 = 智力 = 3,**與位移 89 相同**。

這同時把 [`143`](143-character-creation.md) §3 的「技能點數 = 智力」升到**已確認**:
兩個樣本,智力 3 → 剩 3(未花)、智力 6 → 剩 6(未花),另有智力 3 花掉 2 → 剩 1。

## 5. 位移 1:`'0'` 與 `'*'` 是兩件事

[`133`](133-chars-offset-1-is-party.md) §3 把
「`'*'` 究竟是『無隊伍』還是『空的角色槽』」列為未解,理由是
**出貨資料兩者重合**。

新角色給了第三種值:**`'0'`**。它有名字、有屬性、不屬於任何隊伍。

```
'*'      空槽(從來沒有角色)
'0'      有角色,但不在任何隊伍
'1'–'5'  在第 n 隊
```

> **判準**:兩種語意在現有資料上重合時,**去製造第三個樣本**,
> 不要在同一份資料裡繼續找差別。這一項擱了很久,
> 而拆開它只需要讓原版造一個角色。
