# 15 — 模組轉交的檔名是誰填的,以及一次反組譯錯位

日期:2026-08-13
接續:[`14-brun-unlock-param-buffer.md`](14-brun-unlock-param-buffer.md)

## 結論

1. **找到填 `ds:0B06h` 的程式碼** —— 那是模組轉交(CHAIN)的檔名來源,
   從 [`04`](04-module-layout-entry.md) §5 起就掛著的未解項。
2. **[`14`](14-brun-unlock-param-buffer.md) §3 的「參數累積指標」結論不成立** ——
   它建立在一段**反組譯錯位**的程式碼上。

## 1. `ds:0B06h` 的寫入端(`BRUN30:0x10C25`–`0x10C31`)

```
mov  cx, [bx]            ; 描述子的長度欄位
mov  si, [bx+2]          ; 描述子的資料指標
mov  di, 0B06h           ; ★ 模組轉交用的檔名緩衝區
rep  movsb               ; 把字串抄進去
mov  [di], cl            ; 收尾
```

`ds:0B06h` 就是 [`04`](04-module-layout-entry.md) §3 裡
`sub_14CB8`(通用 MZ 載入器)拿去 `INT 21h AH=3Dh` 開檔的那個檔名指標。

**所以模組轉交的流程是:**

```
模組把檔名放進一個字串描述子
   → BRUN30:0x10C25 把它抄進 ds:0B06h
   → sub_14CB8 依該檔名開檔、驗 MZ、載入
   → 新模組的 MZ CS:IP(= 它自己的 loader stub)接手
```

**信心等級:證據充分。** 兩條互相獨立的線索在這裡交會:

- `mov cx,[bx]` / `mov si,[bx+2]` 的形狀,正是
  [`12`](12-api-3f61.md) 從 `3F:61` 解出的**四位元組字串描述子**(長度 word + 指標 word)
- `0xB06` 這個位址則是從 [`04`](04-module-layout-entry.md) 的載入流程獨立得到的

兩者沒有共同的錯誤來源。

⚠ 這段程式碼來自對 `BRUN30` 的**強制反組譯**([`14`](14-brun-unlock-param-buffer.md) §1),
不是 IDA 自動分析的結果,所以指令邊界有可能是錯的(見 §2 的教訓)。
不過這一段的指令流前後自洽、語意連貫,錯位的機率低。

## 2. ⚠ 訂正 [`14`](14-brun-unlock-param-buffer.md) §3

該節從 `3E:44` 的這幾行推出「`ds:74h` 是參數累積指標、`0xC26`–`0xC30` 是 10-byte 緩衝區」:

```
014348  cmp  di, 0C30h
01434C  jb   short near ptr loc_14346+1      ← ★
01434E  mov  di, 0C26h
```

**`loc_14346+1` 是一個落在指令中間的跳躍目標。** 那是反組譯錯位的典型徵狀:
真正的指令邊界與我強制建立的邊界差一個位元組,於是後面幾條全部是虛構的。

而 §1 的 xref 掃描給了獨立的反證:`0xC26`–`0xC32` 這一段
**每一條 xref 的型別都是「順序流」(來源是前一條指令)** ——
它是**程式碼**,不是可以拿來累積參數的緩衝區。

所以:

| [`14`](14-brun-unlock-param-buffer.md) §3 的說法 | 實際 |
|---|---|
| `ds:74h` 是參數累積指標 | **未證實**。依據的那幾行是錯位產物 |
| `0xC26`–`0xC30` 是 10-byte 緩衝區 | **不成立**。那個範圍是程式碼 |
| `3E:42` / `3E:44` 是參數傳遞 | **退回未解**。兩者的共同前半(附加 word 到 `ds:74h`)仍然成立 |

`3E:42` 的前半段([`13`](13-api-3e42.md) §1)是**自動分析**的結果,不受這次錯位影響。

## 3. 教訓:強制反組譯的產物要當「候選」不是「事實」

[`06`](06-runtime-int-abi.md) 的強制反組譯把涵蓋率從 0.7% 拉到 40.8%,很有用 ——
但它**沒有辦法保證指令邊界正確**,而錯位的產物讀起來完全像正常程式碼。

**判準:讀強制反組譯出來的程式碼時,先掃一遍有沒有「跳進指令中間」的目標。**
`loc_XXXX+1`、`loc_XXXX+2` 這種寫法就是徵狀,IDA 會照實印出來。
這一次是靠 xref 掃描獨立反證才發現,但那是運氣 ——
主動檢查只要一個 grep。

同一份教訓在 [`07`](07-dispatch-tables.md) §2 出現過一次
(線性掃描的中間計數當結論),形狀相同:**工具的中間產物不是證據。**
