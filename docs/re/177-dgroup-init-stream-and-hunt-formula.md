## 1. DGROUP 初始資料的格式

[`162`](162-eldron-clan-riddle.md) §4 認出字串常數的樣式是
`<長度><位址><間距><位址><文字>`。那個樣式**是兩個區塊相接**,而真正的格式更簡單:

```
<總長度:word> <DGROUP 位址:word> <初始內容:總長度 − 4 bytes>
```

字串因此佔兩塊:先 4 bytes 的描述子(`<長度><文字位址>`),再文字本身。

```
08 00 22 73 | 0c 00 26 73        → ds:7322 ← 描述子 <長度 12><文字@7326>
10 00 26 73 | 'The hunt was'     → ds:7326 ← 文字
```

**這一條是本篇最有用的東西**:[`42`](42-module-ds-and-the-66dc-boundary.md) §3 的
「模組的變數大半不在檔案裡,靜態看得到存取、看不到內容」對**沒有初值**的變數仍然成立,
但**編譯期常數全部在檔案裡**,而 BASIC 把運算式裡的每一個數字字面值都放成 DGROUP 常數。
所以 `mov di, 731Eh / INT 3F:81`(加 `ds:731E`)這種先前只能標「未解」的運算元,
現在可以直接讀出那個數字。

工具:[`tools/dgroup_init.py`](../../tools/dgroup_init.py)。

```
python3 tools/dgroup_init.py CAMP.EXE --at 731E
731E+0  檔案 14186  00 00 c0 83  MBF -6
```

> 而真正的主串有 316 塊。局部解不會自己承認自己是局部解。

## 2. `INT 3F:AD` = 乘 2ⁿ,n 是內嵌位元組

`BRUN30` `0x1AC66`:

```
01AC66  mov ds:0A08h, sp          ; API 開場白([`37`](37-api-3e79-3e83.md) §3)
01AC6A  mov ds:226h, si
01AC6E  pop si / pop ds           ; 取回呼叫端的回傳位址 → ds:si
01AC71  lodsb                     ; ★ 讀內嵌位元組,si 前進(所以回去時會跳過它)
01AC72  cmp byte ptr es:1Dh, 0    ; 累加器是 0 就別動
01AC78  jz  → 略過
01AC7A  add es:1Dh, al            ; ★ 指數 += n
```

`ds:1Ah`–`ds:1Dh` 是浮點累加器,`0x1D` 是**指數位元組**
([`152`](152-experience-settlement-formula.md) §3:`INT()` 只碰 `0x1C`/`0x1D`)。
指數加 n 就是**乘 2ⁿ**,而「值為 0 就跳過」正是這種捷徑需要的守衛
(MBF 的零是指數為 0,直接加會把它變成一個非零的數)。

打獵那一處的內嵌位元組是 `04` → **× 16**。

⚠ **IDA 沒有把內嵌位元組吃掉**,所以它後面那幾行反組譯是錯位的:
`cd3f ad` 之後的 `04` 被解成 `add al, 0BBh` 的開頭,連帶把
`bb 1a 00`(`mov bx, 1Ah`)吃掉。**看到 `INT 3F:xx` 之後的指令長得很怪,
先問這個索引會不會讀內嵌參數**(同 [`161`](161-maze-event-dispatch.md) §3 的 `3F:5E`)。

## 3. `INT 3D:33` = `RND(x)`

派工表 `cs:0x171` 的第 `0x33` 項是 `0xB2C7`,而 `3D:34`(`RND`)是 `0xB2C2`
—— **同一支常式,入口差 5 bytes**。`0x1B2C2` 起的那 5 bytes 是前置,
`3D:33` 跳過它,所以差別在於**引數怎麼進來**:呼叫端 `mov bx, 72CEh` 給的是位址,
而 `ds:72CE` 的初值是 **1.0** → `RND(1)`。

BASIC 的 `RND(x)`:`x > 0` 取下一個亂數。**所以 `RND(1)` 與 `RND` 等價**,
差別只是原始碼寫法。

## 4. 打獵公式

`CAMP.EXE` `0x112D8`–`0x11303`,把上面三件事套上去:

```
0112D8  mov bx, 72CEh / INT 3D:33   ; RND(1)          ds:72CE = 1.0
0112DE  INT 3F:AD, 04               ; × 16
0112E5  mov bx, 1Ah   / INT 3D:03   ; INT()
0112E8  mov di, 731Eh / INT 3F:81   ; + ds:731E = -6.0
0112EE  INT 3F:77                   ; → 整數
0112F1  ds:731C = ax
0112F6  ax < 0 → ds:731C = 0        ; ★ 只夾負數,0 保持 0
011328  ds:731C == 0 → 'The hunt was not successful.'
01134D  補給品 ← min(補給品 + ds:731C, ds:6F10)
```

```
收穫 = max(0, INT(RND × 16) − 6)
```

| 擲出(0–15) | 收穫 | 機率 |
|---|---:|---:|
| 0–6 | **0(失敗)** | **7/16 = 43.75%** |
| 7–15 | 1–9 | 各 1/16 = 6.25% |

## 5. 訂正 [`176`](176-hunt-yield-first-measurement.md) §3.2:塞 `wait:` 不夠

那一節寫「要取樣不同亂數,在 timeline 裡塞不同長度的 `wait:` 就夠了」。
**平行執行時不成立** —— 12 個只差 `wait:` 的執行分成三批同時啟動,
每一批內部的結果完全相同(全 20 / 全 25)。

有效的做法是**讓每個執行走不同的步數**(`key:Down` 重複 n 次,n 各不相同):

```bash
BOOT="wait:8;key:Return;wait:3;key:Return;wait:3;type:L;wait:4;type:5;wait:6"
# n = 1,3,5,… 每個執行不同
tools/dosbox_run.sh "$BOOT;$(重複 n 次 key:Down;wait:1)type:C;wait:4;type:H;wait:3;type:1;wait:4;shot:hs$n"
```

16 個不同步數的執行取到 20/23/24/25/27/28/29 七種結果 —— 解相關成功。

⚠ **為什麼會這樣沒有讀到**。線性同餘產生器的種子在 `ds:234/236`
([`152`](152-experience-settlement-formula.md) §3),而種子的**初始化**時機未解。
觀察相容於「開機時用計時器種子、之後純遞推」——那樣的話同一秒啟動的執行序列完全相同,
而多走幾步會多消耗幾個亂數(遭遇判定),序列就錯開了。**這是推測,沒有驗。**

> **判準**:平行取樣之前先跑一個**全同的批次**看結果會不會全部一樣。
> 三批各自內部一致而批間不同,是共用種子最清楚的指紋 ——
> 而若只跑一批,12 個相同的數字看起來會像「分佈很集中」。
