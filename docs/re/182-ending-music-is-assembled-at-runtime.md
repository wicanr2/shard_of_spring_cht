## 1. `INT 3F:61` 的方向

[`12`](12-api-3f61.md) 解出它是「四位元組描述子複製」,但**沒有講哪邊是來源**。
讀 `BRUN30 0x19DAF`:

```
xchg bx, dx
mov  di, bx        ; di ← 原本的 dx
mov  si, dx        ; si ← 原本的 bx
movsw / movsw      ; [si] → [di]
```

`movsw` 是 `[si]` 複製到 `[di]`,所以**原本的 `bx` 是來源、原本的 `dx` 是目的**。

正對照:[`134`](134-groups-load-routine-and-gold.md) §的
`mov bx, 34DCh / mov dx, 66CCh / INT 3F:61 ; 綁定記錄字串` ——
記錄字串(`34DC`)是來源、服務呼叫的引數槽(`66CC`,[`167`](167-record-field-accessor-and-identified-flags.md) §1)是目的 ✓。

## 2. 那 18 次複製在做什麼

`0x131D0`–`0x132D2` 是 18 次 `INT 3F:61`,**目的**是 `ds:92F2 + 4k` 的連續陣列,

| 1 | `92F6` | `9400` | `G` |
| 2 | `92FA` | `935A` | `MB T108 O3 L16` |
| 3 | `92FE` | `9406` | `GA` |
| 4 | `9302` | `940C` | `L8` |

| 8 | `9312` | `942C` | `L2` |

交錯 —— 那正是 BASIC 的 `PLAY A$ + B$ + …` 的用法。

## 3. 這推翻了本輪稍早的一個判斷

那一段先前被判成「**結局文字**的排版」。**錯的**,它是**結局配樂**。

錯法值得記:我當時查了來源陣列 `ds:92F2 + 4k` 的初值,發現**全部沒有編譯期初值**,
就推論「執行期從 `DT51TEXT.DAT` 載進來的文字」。

> **判準**:`INT 3F:61` 這種**兩個運算元都是位址**的 API,查初值之前要先確定**哪邊是目的**。
> 我查的是**目的端**(當然沒有初值 —— 它是要被寫入的),而**來源端就寫在同一行的另一個暫存器裡**。
> 「沒有初值」在這裡不是線索,是**問錯了位址**。

⚠ 它**不影響** [`180`](180-scripted-fight-monster-list.md) 的結論 ——
「這一段不是怪物設定」仍然成立,怪物清單在 `ds:372C`。

## 4. 「這是通關曲」現在有呼叫端了

[`spec/13`](../spec/13-sound.md) 與 `internal/music/score.go` 都寫著
「『這是通關曲』是**位置上的推測**(緊鄰結局文字),不是讀到呼叫端」。

**現在讀到了**:組裝這首曲子的就是目標 533 的處理常式,而 533 = 最終戰
([`180`](180-scripted-fight-monster-list.md))。位置推測升成**已確認**。

## 5. 引擎現有的 `Ending` 是不完整的

`internal/music/score.go` 的 `Ending` 有 **10 段**,來源是「`0x04CBC`–`0x04DB0` 的位元組範圍」。
與本篇的 18 段比對:

| 問題 | 例 |
|---|---|
| **少 8 段** | `G` / `GA` / `L8` / `BG` / `AG` / `F#D` / `L2` / `A` 全部不在 |
| **多讀字元** | 引擎 `MB T108 O3 L8a` ← 實際是 `MB T108 O3 L8`;`MB T108 O4 L4 EC` ← 實際是 `MB T108 O4 L4 E` |

**用位元組範圍讀會把相鄰的資料一起吃進來,也會漏掉不相鄰的片段。**
描述子給的是**每一段的確切長度**,而且 §2 那張表給了**順序**。

> **判準**:資料是「一批描述子指到的片段」時,不要用位元組範圍去撈 ——
> 範圍讀出來的東西看起來完全正常(是合法的 `PLAY` 語法),
> **只有跟描述子逐段比對才看得出多一個字元、少八段**。
