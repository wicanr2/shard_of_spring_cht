## 1. 兩條分支

`0x110D1` 依職業分岔,兩條的形狀完全相同,只差係數:

```
巫師 0x110D6:                        戰士 0x11117:
  ds:66D0 = 16h ; call loc_10079       同左        ; 讀 CHARS.DAT 位移 22 = 體能
  INT 3F:57                            同左        ; 整數 → 浮點
  mov di, 71B0h / INT 3F:91            同左        ; × 亂數因子(§2)
  mov di, 71BAh / INT 3F:91            mov di, 71C2h / INT 3F:91   ; × 係數 ★唯一的差別
  INT 3F:85                            同左
  mov di, 71BEh / INT 3F:81            同左        ; + 1
  INT 3F:77                            同左        ; → 整數
  mov ds:71B8h, ax                     同左
```

⚠ **IDA 在 `0x11102`–`0x1110F` 與 `0x110ED` 附近切錯指令**
(把 `INT 3F` 的內嵌位元組併進下一條,產生 `cmp word ptr [bx+71BEh], 3FCDh`
這種不存在的指令)。上面的還原是逐位元組重切的結果 ——
**不要拿 IDA 那一段的助憶碼當證據**。

係數的初值(用 [`tools/dgroup_init.py`](../../tools/dgroup_init.py) 查):

```
71C2  ab aa 2a 80  MBF 0.666667   戰士        (≈ 2/3,但**比 2/3 大**)
71BA  d4 9b 5e 7f  MBF 0.434783   巫師        (≈ 1/2.3)
71BE  00 00 00 81  MBF 1          加項
```

法力那條在 `0x11221`–`0x11277`,同樣的形狀,係數 `ds:6D98` = 0.5、加項 `ds:722E` = 2。

## 2. 亂數因子是「兩次取大」

```
011221  INT 3D:34                    ; RND
011224  mov di, 71B0h / INT 3F:7D    ; ds:71B0 ← R1
01122A  INT 3D:34                    ; RND
01122D  mov di, 71B4h / INT 3F:7D    ; ds:71B4 ← R2
011235  mov si, bx ; INT 3F:9F       ; 比較,CF = [si] < [di]
01123A  jb → xchg di, si ; INT 3F:7B ; R1 < R2 時把 R2 抄進 71B0
```

`si` = `71B0`(R1)、`di` = `71B4`(R2),`jb` 成立時複製 —— 所以
**留在 `71B0` 的是大的那個**。期望值 **2/3** 而不是 1/2,平均成長量看得見差別。

## 3. 總量上限

```
010306  mov word ptr ds:6D8Ch, 0FFh   ; 255
01030C  mov word ptr ds:6D8Eh, 14h    ; 20 = 等級上限
...
011157  mov ax, ds:6D8Ch              ; 生命:夾總量
0112C8  cmp ax, ds:6D8Ch              ; 法力:同一個變數
```

⚠ **生命與法力共用同一個上限**,而且夾的是「舊值 + 成長」的**總量**。

## 4. 手冊那兩張表不在程式裡

全 100 個檔案掃過,**沒有對應的資料表** —— 手冊那兩張表是設計者用
`INT(屬性 × K) + 加項` 紙筆算出來的。

決定性的證據是 **SP 表自己在智能 11 換了公式**(3–10 用 `INT(I/2)+2`,
11–19 用 `INT((I+1)/2)+2`)—— 量出來的表不會中途換規則。

這推翻的是 `rules.MaxHPGain` / `MaxSPGain` 的**存在理由**。因為實際取整是
四捨五入(§5),兩張表與程式的差異是**有結構的**:

| 表 | 與程式的關係 |
|---|---|
| HP 戰士欄 | 體能 ≡ 1 (mod 3) 的六格(4/7/10/13/16/19)程式比手冊**多 1**,其餘吻合 |
| SP 欄 | 偶數智能吻合;奇數智能 ≥ 11 的五格程式比手冊**少 1** |

正確的修法是換掉整條算式,不是留著查表再修幾格。

## 5. 取整是四捨五入,不是截尾

`INT 3F:77`(浮點 → 整數)有兩條路徑,由 `ds:1Fh` 分流:

| `ds:1Fh` | 行為 | 位址 |
|---|---|---|
| `== 4` | 純 `shr` → **截尾** | `BRUN30 0x1A8FF` |
| 其餘 | `shr` + `adc` → **四捨五入** | `BRUN30 0x1A942` |

`ds:1Fh` 的載入初值**是 `0x00`** → 走四捨五入。

### 怎麼讀出來的

`BRUN30` 的 `DS` 是 `seg002`,線性 `0x1FE00`、大小 `0x1420`([`41`](41-ds-base-solved.md) §1)。
扣掉 MZ 標頭 512 B 之後 **`ds:XXXX` 的檔位移 = `0x10000 + XXXX`**。

三個正對照(我自己重跑過):

| 對照 | 預期 | 實得 |
|---|---|---|
| `seg002` 大小 | `0x1420` | 檔案從 `0x10000` 到檔尾 = 5,144 B ✓ |
| 非零比例 | [`41`](41-ds-base-solved.md) §2 記 **37%** | **37.2%** ✓ |
| `ds:0A3A`/`0BE8`/`0B8E`/`10F0`(BSS)| 全零 | 四個都全零 ✓ |

```
ds:00  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
ds:10  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00   ← ds:1F 在這一列的尾端
ds:20  00 00 00 00 00 00 00 00 00 68 0a 00 00 f0 13 00   ← 初始資料從這裡才開始
```

寫入端:13 支 EXE、273,301 bytes 逐 byte 掃過所有 disp16 直接定址的寫入編碼,
**`ds:1Fh` 零命中**;71 處「把 `1Eh`/`1Fh` 載進暫存器」逐一看過,全是整數常數 30/31
(後接 `imul`/`mul`),沒有一個當指標用。

⚠ **信心是「證據充分」不是「已確認」**,兩個洞明講:

1. 「沒有寫入端」是**負面斷言** —— 執行期算出來的指標寫入結構上掃不到。
   (減輕的理由:`ds:1F` 緊接在 8-byte FAC 之後,唯一掃過那一帶的
   `movsw ×2`/`×4` 都停在 `0x1E` 之前。)
2. 「執行期沿用載入映像」是推得的,沒有動態證據。

### 獨立佐證:42 個多餘的 `INT()`

全 8 支模組共 **72 個 `3F:77`**,其中 **42 個(58%)**前面配了顯式 `INT 3D:03`
(CMBT 25/38、TOWN 9/13、CAMP 5/7)。**若 `3F:77` 本來就向下取整,那 42 個 `INT()` 全是白打的**,
而原始碼作者也不會去打那個 `INT(`。

本篇自己就是一個例子:屬性成長那條(`0x11340`)**有** `mov bx,1Ah / INT 3D:03`,
而 HP 這條**沒有** —— 兩條路徑刻意不同。

### ⚠ 手冊裁決不了這件事(而且拿它裁決是循環論證)

手冊的數字是設計者**紙筆算的 `INT(屬性 × K) + C`**,不是量出來的。
證據:**SP 表自己在智能 11 換了公式**(3–10 用 `INT(I/2)+2`,11–19 用 `INT((I+1)/2)+2`)
—— 量出來的表不會中途換規則。

而紙筆的 `INT(x) + C` 與「截尾」只在 `x` 剛好整數時才有差,所以**拿手冊去對截尾預測幾乎必然高分**。

### 一次就能定案的實測(第 1 級證據)

最靈敏的是 **SP**(它沒有「加上舊值」把小數吃掉):

| 智能 | 截尾上界 | 四捨五入上界 | 單次出現上限值的機率 |
|---|---|---|---|
| 10 | 6 | **7** | 19% |
| 16 | 9 | **10** | 12% |
| 20 | 11 | **12** | 9.8% |

**智能 10 的巫師連升 10–15 級**:看到過一次 `+7` 就是四捨五入(截尾為真時機率是 0);
全程 ≤ 6 就是截尾。

## 7. ⚠ 連鎖影響:`INT 3F:85` 與「沒配 `INT()` 的 `3F:77`」

### `3F:85` 是「取內嵌運算元」那一族

`BRUN30 0x11EC3` 是公用常式(14 處呼叫):`pop` 出呼叫端的 IP:CS →
`lodsb` 讀 `CD 3F xx` **後面那個 byte**(順便讓返回位址跳過它)→ ×8 查符號表 →
位址同時放進 `si` 與 `di`。

| 索引 | 語意 |
|---|---|
| `3F:81` | `FAC + [di]`(`di` 由呼叫端給)|
| `3F:85` | `[si] + FAC`(`si` 由**內嵌編號**指定)|
| `3F:71` | `[內嵌變數] ← FAC` |

配對不是靠相鄰推的,是**兩端的內嵌編號相同**:
巫師 `0x110EA CD 3F 71 81` ↔ `0x11102 CD 3F 85 81`;戰士 `0x1112D …81` ↔ `0x11145 …81`。
所以 §1 的算式不變,只是機制的說法從「壓進浮點堆疊」改成「存進具名暫存」。

⚠ **`3F:71`/`3F:85`/`3F:9D`/`3F:A5` 等至少 14 個索引是 4 bytes 不是 3** ——
這就是 IDA 在這一段切錯位、`int_seq.py` 印 `?? 81` 的根因。
[`77`](77-runtime-arithmetic-api.md) §1 那句「兩個進入點差在第二運算元在不在累加器裡」
要改成「差在運算元從 `di` 來還是從內嵌 byte 來」。

### 沒配 `INT()` 的 `3F:77` 要重新檢視

`docs/re/` 裡有一批算式寫成 `INT(…)`,而那個 `INT` 是**當時假設 `3F:77` 截尾**才寫上去的。
`3F:77` 既然是四捨五入,**那些沒有顯式 `INT 3D:03` 的地方要重讀**。
本篇沒有重讀那些段落,只是形狀上的連鎖 —— 另開一輪處理。
