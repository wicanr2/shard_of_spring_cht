## 0. 先修一個讓人讀錯的工具問題

`INT 3F` 有 18 個索引多帶一個運算元位元組([`185`](185-int3f77-rounding-audit.md) §1.2),
而 CMBT 的擺法是 `CD 3F nn` + `90 90` + **運算元**(在 +5)。
`tools/ida/unlock_module.py` 原本不吃那一個位元組,於是它被當成下一條指令的開頭,
**接下來整段錯位** —— 而錯位的反組譯讀起來很通順(`or bp, 343Dh` 之類),
沒有任何錯誤訊息。補上之後 CMBT 的 undecodable bytes 從一堆降到 **9**,
多認出 81 處 thunk。

⚠ **這一篇的所有結論都建立在補完之後的反組譯上。** 補完之前讀同一段會得到別的答案。

## 1. 出場位置(D2):8 個錨點 + 抖動 + 重擲

錨點表是**字面常數**,就寫在擲骰迴圈正上方(`0x115B1`–`0x11611`):

| i | 欄 `ds:79A4+2i` | 列 `ds:798E+2i` |
|--:|--:|--:|
| 1 | 6 | 6 |
| 2 | 11 | 6 |
| 3 | 16 | 6 |
| 4 | 6 | 11 |
| 5 | 16 | 11 |
| 6 | 6 | 16 |
| 7 | 11 | 16 |
| 8 | 16 | 16 |

**那是 3×3 的格局,中間那格空著** —— 中間 (11,11) 正是隊伍所在的區塊
(隊伍基準 13,13,[`164`](164-board-stride-31-and-base-13.md) §2)。

流程(`0x1161E`–`0x116D2`):

```
repeat:
  i  = INT(RND × 7) + 1                    ; ds:94B4 = 7.0、ds:9464 = 1.0
  欄 = round( 錨欄[i] + INT(RND × 5) )      ; ds:94B8 = 5.0
  列 = round( 錨列[i] + INT(RND × 5) )
until 格值[列 × 31 + 欄] == ds:92F6         ; 空地(初值 2)
```

`0x116B9`–`0x116D2` 就是那個判斷:`mov dx, 1Fh`(31)、`imul`、`add ax, bx`、
`mov dx, [di+6AD4h]`、`cmp dx, ds:92F6h`、不合 `jmp 0x1161E`(回去重擲)。

### 1.1 兩個推得出來的結果

- **錨點 8 永遠挑不到。** `INT(RND×7)+1` 的值域是 1…7,而表有 8 列 ——
  第 8 列 (16,16) 是死資料。⚠ 這是**推論**:常數 `ds:94B4 = 7.0` 是讀出來的
  (`00 00 60 83` = MBF 7),但「原版是不是本來想寫 8」無從得知。
- **戰場的可用範圍是 6…20**:錨點 6/11/16 各加 0…4 的抖動,剛好接成 15 格。
  這與手冊 p.33 的「15×15」對得上,而且說明那**不只是畫面**,
  也是怪物實際會出現的範圍。

## 2. 目標鎖定(D1):死了才換,換是隨機挑一名隊員

戰鬥屬性的定址是 `di = 單位 + 15 × 屬性` → `shl di, 1` → `[di+6822h]`
(所以 `add di, 0E1h` = 屬性 15、`0D2h` = 屬性 14、`78h` = 屬性 8、`69h` = 屬性 7)。

**屬性 15 = 目前鎖定的目標單位編號。** 六個存取點全部讀完:

| 位址 | 動作 |
|---|---|
| `0x14687`–`0x146C4` | 讀目標 → 檢查它的屬性 8(狀態 == 5 陣亡)與屬性 10(朝向 ≤ 0 離場) |
| `0x146CB`–`0x146FE` | **兩者之一成立才重挑**:`round(INT(RND × ds:34F8) + 9)` |
| `0x1458F` / `0x14764` | 寫入 |
| `0x157DD` / `0x15806` / `0x1582F` | 讀目標 → `add di, 0Fh` 讀它的座標 → 朝它移動 |

`ds:34F8` 是隊伍人數(上限 5,[`43`](43-common-block-and-array-indexing.md)),
`ds:94D2 = 9.0` 是隊員的起始索引(`00 00 10 84` = MBF 9)——
所以重挑的結果是 **9…13 之間的一個隊員,均勻隨機**。

> **這就是手冊 p.35 的 `TACTICS`**:「看得出怪物正追蹤哪一位同伴」——
> 追蹤的對象是真的存在的欄位,而且**在目標倒下或逃走之前不會變**。

⚠ 另一個寫入點 `0x1458F` 走的是別的路:`0x1451C`–`0x14577` 的迴圈用
**座標**去找「誰站在這一格」(比對屬性 0/1 與 `ds:9346`/`ds:9348−1`,
再要求屬性 8 < 5),找到才寫。那是「**這一格上的人是誰**」的查詢,
不是「挑一個人來追」——同一個欄位、兩種用法。

## 3. 施法時機(D3):法力夠 + (第二回合 或 30%)

`0x12472`–`0x124B2`:

```
bx = (屬性 7 法力 > 1)
dx = (RND ≤ ds:941E)          ; ds:941E = 0.3 → 9a 99 19 7f
cx = (ds:9314 回合數 == 2)
if (cx OR dx) AND bx  → 0x15534(施法,選招在 170)
                      → 否則 0x13E5F(一般行動)
```

所以:**法力 > 1 是硬門檻**;過了之後,第二回合**必定**施法,其餘回合 **30%**。

這與 [`170`](170-monster-ai-casts-by-spell-family.md) 接得上:那一篇讀到「第一回合在系別內隨機、
第二回合起固定放 FIRE STORM / TEMPEST / HAIL STORM」——**第二回合的必定施法就是這裡**。
