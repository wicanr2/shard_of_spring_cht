# 204 — 火把每個動作燒一回合;順帶訂正:位移 83 是**當前迷宮編號**

> 輸入:`USERLIB.EXE`、`MENU.EXE`、`WRLDMOVE.EXE`(SHA-256 見 [`00-inputs.md`](00-inputs.md))。
> 反組譯前先跑 `tools/ida/unlock_module.py`。
> 信心:**已確認**(推進常式逐行讀出;位移 83 的訂正有三條互相獨立的證據)。

關掉 worklist 的「`LightTurns` 只寫不減」:照明法術把回合數寫進 `GROUPS.DAT`
位移 45([`196`](196-weapon-skill-gate-train-cost-light-spells.md) §3),
而引擎裡沒有任何地方遞減它 —— 點一次燈就永遠亮著。

**遞減不在九支 BASIC 模組裡,在 `USERLIB`。** 這是找不到它的原因:
`ds:365A`(位移 45 的記憶體副本)在 `MAZEMOVE` 裡**一次都沒有出現**
(位元組層級掃過,`tools/ida/find_bytes.py`),而走迷宮正是火把該燒的時候。

## 1. 訂正:位移 83 不是「光源選擇」,是**當前迷宮編號**

`MENU` 的載入常式把位移 83 搬進 `ds:3534`([`134`](134-groups-load-routine-and-gold.md) §2),
而 `ds:3534` 的語意在 [`169`](169-encounter-zone-selects-the-monster.md) §4 已經定案:
**當前迷宮編號,99 = 不在迷宮**。兩篇各自成立,合起來就推翻了
[`formats/02`](../formats/02-groups-dat.md) 的「選自然光還是攜帶光」。

決定性的一條在 `MENU` `0x119ED`:

```
0119ED  cmp word ptr ds:3534h, 63h   ; 99 ?
0119F7  bx = ds:77EA  →  ds:6E22     ;   是
011A05  bx = ds:77F6  →  ds:6E22     ;   否
```

那兩個字串是 **`WRLDMOVE`** 與 **`MAZEMOVE`**
(`translations/source/module-MENU.tsv` 第 102/103 列)——
**這一格決定下一支要 `CHAIN` 到哪個模組**。「光源選擇」放不進這個位置。

另外兩條:

| 證據 | 內容 |
|---|---|
| `WRLDMOVE` `0x10F6B` | `ds:365A = 0` 緊接著 `ds:3534 = 99` —— 走回地面時**兩欄一起寫**:火把熄掉、迷宮編號歸哨兵 |
| 出貨存檔第 5 筆 | 位移 83 = **99**,而 [`139`](139-dosbox-runs-to-the-world-map.md) 實跑載入 PARTY #5 **出現在世界地圖** |

⚠ **機制沒有錯,錯的是欄位的名字。** [`118`](118-daylight.md) 寫的
「在地面用天色、進迷宮用火把」正是這一欄的**消費端** ——
那句話裡已經有正確答案了,只是欄位被登記成「光源選擇」。
`USERLIB 0x1080D`(狀態列印能見度,[`105`](105-visibility-fields.md))也是同一個判斷。

> **判準**:一個欄位如果**只在一個 `if` 裡出現**,很容易被命名成那個 `if` 的用途。
> 要問的是「還有誰讀它」—— 這一欄的另外兩個讀端(選模組、選遭遇區域)
> 一出現,「光源選擇」就站不住了。

## 2. 推進一個動作要做的事(`USERLIB` `0x10437`–`0x10577`)

```
01043A  inc ds:353C                  ; 位移 33,時以下
01043E  > 10 → = 1、inc ds:353A      ; 位移 31,時
010452  時 > 26 → = 4、inc 日、時以下 = 1
01046C  日 > 34 → = 1、inc 月
010480  月 > 21 → = 1
010490  dec ds:3658                  ; ★ 位移 25,遭遇倒數
010494  在地面?
   是 → 0104A2  ds:35B4 = 天色(見 §2.1)
        010502  ds:3050 = ds:35B4    ; 生效能見度
        010508  ds:365A = 0          ; ★ 地面上火把不燒也不留
   否 → 010511  cmp ds:365A, 0
        ≤0 → 01051B 讀位移 61 → ds:35B2、ds:365A = 0
        >0 → 010539 讀位移 59 → ds:35B2、01054E **dec ds:365A**
        010552  ds:3050 = ds:35B2
010558  把 ds:365A 寫回記錄位移 45   ; 每一步都寫回,不是離開才存
010578  ds:35CC = (4 − ds:3050) × 17 ; 17 = 圖塊邊長 → 能見度換算成畫面尺寸
```

**每個動作燒一回合,而且先取能見度再遞減** ——
回合數從 1 走到 0 的那一次仍然算「有光」。

⚠ `0x10578` 的 `(4 − 能見度) × 17` 反過來確認了**數值越大越亮**:
4 是最亮(margin 0),1 最暗。位移 59(有光)= 3、61(無光)= 2 的量級因此合理。

⚠ `MENU` 載入常式 `0x119B2` 的同一個二選一**方向相反**(`< 1` 讀位移 59)。
兩者不可能都對;以 `USERLIB` 為準,因為它是遊玩中每一步都跑的那一份,
載入時算錯的值在第一個動作就被覆蓋掉。**這個矛盾沒有解釋**,列在 §4。

### 2.1 天色由「時」決定,四段

```
0104A2  ds:35B4 = 4
0104A8  時 ≤ 5  或 時 ≥ 14 → 3
0104CD  時 ≤ 2  或 時 ≥ 17 → 2
0104F2  時 ≥ 19            → 1
```

四條**由上而下覆蓋**,不是互斥分支。時的值域是 4–26
([`107`](107-clock-is-four-levels.md)),所以實際只走得到:

| 時 | 4–5 | 6–13 | 14–16 | 17–18 | 19–26 |
|---|---|---|---|---|---|
| 能見度 | 3 | **4** | 3 | 2 | 1 |

「≤ 2」那一條在遊戲裡到不了。⛔ **照原版留著** ——
刪掉之後就沒有人記得它存在過。

## 3. 順帶:遭遇倒數的載入補值是 **25**

`MENU` `0x1199C`–`0x119AC`:讀位移 25 → `ds:3658`,
**`≤ 2` 就填回 25**(`c706 5836 1900`)。

⚠ 這**不是**「每次遭遇之後填什麼」—— 那一個(worklist 的 E6)仍然未解。
兩者是不同的量:這一條只保證「讀檔之後不會立刻踩到遭遇」。
出貨存檔第 5 筆的位移 25 = 54,那是玩到一半的值,不是任何一個重置值。

## 4. 對 remake 的影響

規則寫在 `internal/world`,與時鐘同一支(`State.tick` → `State.light`)——
**原版就是同一支常式**,拆成兩處遲早有一邊漏掉。

引擎另外補上兩個先前沒有的接線:

- **迷宮裡走一步會推進時鐘**。先前迷宮移動完全不動時鐘,
  所以就算加了遞減也不會燒 —— 兩個缺口疊在一起,症狀是「什麼都沒發生」。
- 生效能見度改為每步重算(`g.party.Visibility`),
  先前迷宮畫面固定用位移 59,**火把燒完視野也不會變**。

⚠ 讀檔時**迷宮編號要取自記錄的位移 83,不是取自「現在載入了哪一層」** ——
讀檔的當下迷宮還沒重新載入,拿執行期狀態去判斷會得到「不在迷宮」,
於是火把當場被歸零。原版的載入常式做的是同一件事:先讀位移 83,
**再**決定要 `CHAIN` 到哪一支模組(§1)。
**這個 bug 只在地城裡存檔才會發作**,在地面上存檔的往返完全正常。
