# 21 — 圖塊格式定案:BASIC `GET`/`PUT` 陣列,17×17

日期:2026-08-13
接續:[`20-cga-layout.md`](20-cga-layout.md)
子系統:**H. 圖形格式**

## 結論

九個 98-byte 圖塊檔的內容是 **BASIC `GET`/`PUT` 陣列**:
4-byte 標頭(寬以 bit 計、高以列計)+ 逐列的 CGA 2bpp 像素。
尺寸 **17 × 17**,九個檔**全部**畫出與檔名相符的圖案。

## 1. 結構

```
BSAVE 標頭(7 bytes)          ← docs/re/19
  +0x00  word  寬度,單位 bit(= 像素 × 2)
  +0x02  word  高度,單位列
  +0x04  ...   逐列像素,每列 ceil(寬bit / 8) bytes
0x1A                           ← 檔尾
```

九個檔的標頭**完全相同**:`寬 = 34 bit`、`高 = 17`。
34 ÷ 2 bpp = **17 像素**;每列 `ceil(34/8) = 5` bytes;`5 × 17 = 85` bytes 像素資料。
扣掉 BSAVE 標頭(7)、`GET` 標頭(4)、EOF(1)後剩 86 bytes,
與 85 差 1 —— 一個填補位元組。

## 2. 驗證:九個檔各自畫出自己的名字

**信心等級:已確認。** 這是九個互相獨立的檢查,不是一個。

| 檔案 | 畫出來的東西 |
|---|---|
| `MAZEWALL.BIN` | **磚牆** —— 上下列的磚縫互相錯開(標準的順砌)|
| `DOOR.BIN` | **拱門** —— 有門框、上緣是弧線 |
| `EXITSPOT.BIN` | **四角星／羅盤** —— 上下左右四個尖端 + 中央十字 |
| `BORDER.BIN` | **菱形** —— 上下對稱、逐列增減 |
| `WATER.BIN` | 散布的短橫 —— 波紋材質 |
| `LAVA.BIN` | 同樣的散布短橫,**用另一個顏色索引** |
| `FIRESTRM` / `HAILSTRM` / `WINDSTRM` | 法術動畫格 |

`WATER` 與 `LAVA` 的圖案密度接近而**顏色索引不同**,
與「同一種材質、不同配色」相符 —— 這是第二層的自洽。

**為什麼這個驗證強**:錯誤的寬度會讓圖案逐列斜移,
九個檔會**同時**變成斜線雜訊。
而正確的寬度讓九個檔**各自**出現自己名字所描述的東西 ——
`MAZEWALL` 的磚縫錯開、`DOOR` 的拱、`EXITSPOT` 的四角對稱,
這些是彼此無關的結構,不可能靠同一個巧合一起成立。

## 3. 修正 [`20`](20-cga-layout.md) §2 的預設

該節寫「小圖通常是連續存放(不交錯),而且可能自帶尺寸欄位」,
並列出十個候選要靠九檔互證來挑。

**實際上不必猜** —— 尺寸就寫在資料裡,是 BASIC `GET` 的標準標頭。
方向是對的(「先扣 BSAVE 標頭,再找尺寸」),
但**低估了資料自我描述的程度**。

判準:**看到「扣掉容器標頭後,前幾個 byte 是小整數」時,先假設那是內容的標頭,
不要直接把剩餘長度拿去做因數分解。** 因數分解是沒有標頭時才用的手段。

⚠ 這與 [`19`](19-bsave-container.md) §3 的教訓**方向相反**:
那次是把容器標頭誤當尺寸欄,這次是差點忽略真正的尺寸欄。
兩者的共同解法是同一個:**先把層次分清楚**(容器 → 內容標頭 → 資料),
再問每一層各自說了什麼。

## 4. 套用到其他素材

| 素材 | BSAVE 後的 bytes | 前兩個 word | 推得尺寸 |
|---|---:|---|---|
| 98-byte 圖塊 ×9 | 90 | 34, 17 | **17×17** ✅ |
| `MONST1`–`22.BIN` | 734 | 待讀 | 待驗 |
| `PICT1/2/6/7/8.BIN` | 5,972 | 待讀 | 待驗 |
| `DE*EFF.BIN` ×10 | 1,060 | 待讀 | 待驗 |

同一套讀法應該直接適用,**但要逐組驗過再宣告** ——
`FASTCMBT.BIN` / `RNDMONST.BIN` / `MAZEDATA.BIN` 這些名字不像圖的檔案
很可能不是 `GET` 陣列。
