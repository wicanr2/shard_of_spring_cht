# 227 — `FASTCMBT.BIN` 與 `FASTWRLD.BIN` 同格式;戰場地形是從周圍地圖鋪出來的

> 輸入:`FASTCMBT.BIN`(836 bytes)、`FASTWRLD.BIN`(836 bytes)、`CMBT.EXE`
> (SHA-256 見 [`00-inputs.md`](00-inputs.md))。
> 信心:§1 **已確認**、§2 **已確認**、§3 **未解**(明列缺什麼)。

[`21`](21-tile-format.md) §4 把 `FASTCMBT.BIN` 列成「名字不像圖的檔案…很可能不是
`GET` 陣列」,而 [`spec/14`](../spec/14-remake-worklist.md) §12.4 第 9 項一直掛著
「要新 RE」。這一篇把格式那一半關掉。

## 1. 格式:9 張 17×17,與 `FASTWRLD` 逐項相同

兩個檔都是 836 bytes = BSAVE 標頭 7 ＋ 本體 828 ＋ EOF 1,而 828 = **9 × 92**。
按 92 bytes 切開之後,**九塊的前兩個 word 全部是 (34, 17)** ——
也就是 BASIC `GET` 陣列的寬(bit)與高([`21`](21-tile-format.md) §3)。

| 檔 | 九塊的標頭 | 每塊非零位元組 |
|---|---|---|
| `FASTWRLD.BIN` | 全部 (34,17) | 10–45 / 88 |
| `FASTCMBT.BIN` | 全部 (34,17) | 16–85 / 88 |

⚠ **「九塊的標頭全部對」正是 [`53`](53-world-tiles-towns-and-draw-renderer.md) §1
用來裁決 `FASTWRLD` 排法的判準**(連續 vs 交錯,只有連續讓九組都是 (34,17))。
同一個判準在這裡直接成立,所以 `original.DecodeFastWorld` 那支解碼器
不必改就能讀 `FASTCMBT.BIN`。

**九張圖的身分:逐位元組等於那九個 98-byte 檔**(不是「看起來像」)。
把 `FASTCMBT.BIN` 按 92 bytes 切開,每一槽的**前 90 bytes 與對應檔案的
BSAVE 內容完全相同**,九槽九檔一個不差,順序也與
[`61`](61-i-closure-unused-tiles.md) §1 讀到的陣列槽位一致:

| 槽 | 檔案 | 內容 |
|--:|---|---|
| 0 | `EXITSPOT.BIN` | 四向星芒 |
| 1 | `BORDER.BIN` | 實心八角 |
| 2 | `WATER.BIN` | 水面 |
| 3 | `LAVA.BIN` | 岩漿 |
| 4 | `MAZEWALL.BIN` | 磚牆 |
| 5 | `DOOR.BIN` | 拱門 |
| 6 | `WINDSTRM.BIN` | 方形漩渦 |
| 7 | `HAILSTRM.BIN` | 青色斜線 |
| 8 | `FIRESTRM.BIN` | 洋紅斜線 |

**所以 `FASTCMBT.BIN` 是那九個檔的打包本** —— 迷宮那一支模組逐檔載入九次,
`CMBT` 一次載完。⚠ 這修正 [`61`](61-i-closure-unused-tiles.md) §2 的
「`FIRESTRM`/`HAILSTRM`/`WINDSTRM.BIN` 遊戲從不載入」:**那三個檔本身**確實沒被
開啟過,但**它們的內容有被載入**,就在這個打包本裡。

施法那一段(`CMBT 0x15946` / `0x15970` / `0x15994`)按法術編號把第 6/7/8 槽
逐 word 複製進 `ds:7AC4` 的 92-byte 暫存區再畫:

```
法術 3(FIRE STORM) → 來源 ds:7E00 = 7B20 + 92×8 → 槽 8 = FIRESTRM
法術 8(TEMPEST)   → 來源 ds:7D48 = 7B20 + 92×6 → 槽 6 = WINDSTRM
法術 12(HAIL STORM)→ 來源 ds:7DA4 = 7B20 + 92×7 → 槽 7 = HAILSTRM
```

**每個複製迴圈跑 0…45 = 46 word = 92 bytes**,正好一槽 ——
這反過來確認了「一張 92 bytes、基底 `ds:7B20`」的切法。
三個名字與三個法術逐一對上,是這條證據鏈的獨立佐證。

**載入端**:`CMBT.EXE 0x10753`,與世界地圖那三個檔同一個形狀
([`132`](132-world-tile-dispatch-corrected.md) §2):

```
mov bx, 7B20h  / INT 3F:57   ; ★ 載入位址 ds:7B20
mov bx, 9368h  / INT 3F:55   ; `fastcmbt.bin` 的描述子 + 路徑前綴
mov dx, 1Ah    / INT 3E:1A   ; 載入
```

**九張圖載進 `ds:7B20`,佔 828 bytes,到 `ds:7E5C` 為止。**
全套執行檔掃過一遍,`fastwrld` 只出現在 `WRLDMOVE` / `WSIO`,
`fastcmbt` 只出現在 `CMBT` —— 兩個檔各屬一支模組,不共用。

## 2. 戰場地形是從**周圍的地圖格**鋪出來的

格陣列在 `ds:6AD4`(31 寬,[`164`](164-board-stride-31-and-base-13.md))。
`0x108E0`–`0x10A60` 是雙重迴圈,把來源地圖的一格展開成戰場上的一塊,
判斷寫在 `0x10998`–`0x10A53`:

```
v = ds:93AE(來源格的地形值,取自 ds:3740 那張表)

v == 2 或 3 或 17 ≤ v ≤ 25      → 格 = ds:9300
7 ≤ v ≤ 12 或 v == 27           → 格 = ds:92FC
v == 5 或 6                      → 格 = v 本身
其餘                             → 格 = ds:9300
```

六個常數在 `0x10406`–`0x10424` 一次設定完,是字面值:

| 變數 | 值 | 用途 |
|---|---:|---|
| `ds:92F6` | 2 → 後來被 `0x10933` 改成 `ds:9300` | **空地**(怪物出場要求這一格,[`186`](186-monster-ai-target-placement-cast.md) §1)|
| `ds:92F8` | 5 | |
| `ds:92FA` | 6 | |
| `ds:92FC` | 7 | |
| `ds:92FE` | 12 | |
| `ds:9300` | 18 | 空地的實際值 |

`0x11000`–`0x110B4` 是一個**平滑化**的後處理:相鄰兩格是 5/6/7、
而第三格是 18 時,把那兩格也改成 18。

⚠ **這一節的算式是逐條讀出來的,但「`ds:3740` 裝的是周圍的地圖格」還沒證實** ——
實測反過來:

| 實測 | 結果 |
|---|---|
| 區域 6,隊伍走在山脈列上、南北兩側是海洋(值 11)| 戰場**上下兩條水面**,中間全黑 |
| 區域 1,把工作複本的地圖改成「上兩列森林(5/6)、下一列山(7)」再開一場 | 戰場**整片全黑**,一張地形都沒有 |

第二筆是為了裁決而做的合成地形(只改 `workplace/dosbox/game/` 的複本,
量完立刻還原;`game/` 全程唯讀)。**它與第一筆矛盾**:同樣走 `7 ≤ v ≤ 12 → 7`
這一條的山脈與海洋,一個畫了一個沒畫。

所以下列兩種可能還沒排除:

1. `ds:3740` 裝的**不是**世界地圖的鄰近格(它由送出戰鬥的模組填,填什麼沒讀);
2. 這段產生器**只在地城戰鬥**走得到,世界地圖戰鬥另有一條路。

⛔ 在裁決之前,不要把 §2 的算式當成「戰場地形怎麼來的」寫進規格。

## 3. 還缺:格值 → 圖塊編號

寫進格陣列的值是 **2 / 5 / 6 / 7 / 12 / 18**,而 `FASTCMBT` 只有 **9 張圖** ——
所以**不是「值 − 1 = 圖塊編號」**(12 與 18 都超出範圍)。中間一定有一層對映,
而那一層還沒讀到。

已知的另一半:`ds:7B20` 是圖塊資料的基底(見上),而畫圖塊的呼叫是
`0x12B56` / `0x18E67` 的 `mov bx, 7B20h / mov dx, 3 / INT 3E:58`
(前面配 `ds:35C0`/`35C2` 與 `INT 3E:89`)—— **`bx` 給的是陣列基底,
不是某一張圖**,所以「用哪一張」是在別處算的,而那一段還沒找到。

⚠ 三條看起來像答案但**不是**的線索,記下來免得下一輪再走一次:

- `0x1729B` 的 `add di, [si+6AD4h]` 配 `[di+7E5C]`,形狀像「用格值查圖」,
  但那是 [`226`](226-monster-cast-invest-and-target.md) §3 的**捲動**常式:
  外圈跑 46 次、跨距 48 word,它在搬螢幕緩衝的一整條,不是在畫一格。
- `0x13CDE` 的 `cmp [di+6AD4h], 20h` 與 `0x140C8` 的 `cmp …, 21h`:
  格陣列裡 32/33 這種值與地形無關(那一段在判單位),
  **同一個陣列裝了兩種東西**。
- `INT 3E:58` 的 `dx`(這裡是 3、施法那一支是 4)看起來像圖塊編號,
  但兩處的 `bx` 是**不同的陣列基底** —— 它多半是繪圖模式(`PSET`/`XOR` 之類),
  依 [`CLAUDE.md`](../../CLAUDE.md) §1.2 不往下追。

**下一步該做的**(留給下一輪,判準先寫下來):先解 §2 的矛盾 ——
去讀 `ds:3740` 的**填入端**(在 `WRLDMOVE` / `MAZEMOVE` 那一側,不在 `CMBT`)。
知道它裝什麼,才知道格值從哪來;在那之前追「格值 → 圖塊」是在追一個
可能根本沒被走到的分支。

⛔ **在裁決之前,引擎的戰場不畫地形。** 湊一個「5→第5張」的表
會在畫面上看起來完全正常,而那是自己發明的地圖。
