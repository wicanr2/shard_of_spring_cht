# 24 — 工具衝突,與 `BLOAD` 為何不留位址常數

日期:2026-08-13
接續:[`23-module-datafile-map.md`](23-module-datafile-map.md)

## 1. ⚠ `trace_module.py` 會洗掉 `unlock_module.py` 的成果

兩支腳本都寫同一個 `.i64`,而 `trace_module.py` 開頭做
`ida_bytes.del_items(整段)`。所以**後跑的那支會覆蓋前一支**。

實測:對 `CMBT.EXE` 先 unlock(15,722 bytes 指令)再 trace 之後,
資料庫只剩 1,973 bytes;此時任何掃描(如 `find_imm.py`)都會**在不知情的狀況下
只掃到 12% 的程式碼**,而輸出看起來完全正常。

發現方式:`find_imm` 回報「掃了 2,804 條指令」,
而解鎖後應該有一萬六千多條 —— **是那個數字不對,不是命中數不對**。

### 規則

| 情況 | 做法 |
|---|---|
| 要掃描／查 xref | 先跑 `unlock_module.py`(上界),再掃 |
| 要「哪些位址一定是程式碼」 | 跑 `trace_module.py`(下界),但**跑完要重新 unlock** |
| 任何掃描結果 | **先看「掃了幾條指令」這個數字**,與預期不符就重跑 unlock |

**判準:工具回報的分母比分子重要。** 命中 0 處可能是真的沒有,
也可能是掃描範圍被前一個工具改小了 —— 兩者的輸出長得一樣
(同 [`01`](01-inventory.md) §5「零命中與不存在長得一模一樣」)。

## 2. `0x27FF` 在 `CMBT.EXE` 裡零命中 —— 而這是合理的

`MONST*.BIN` 的 BSAVE 標頭記著 segment `0x27FF`([`19`](19-bsave-container.md) §1.1),
所以本來預期 `CMBT` 的程式碼裡會有那個立即數。

**重新解鎖後掃 16,553 條指令,仍然 0 處。**

原因是 `BLOAD` 的語意:**載入位址寫在檔案自己的 BSAVE 標頭裡**,
呼叫端只要給檔名。所以模組**不需要**知道 `0x27FF`,程式碼裡當然找不到。

這也解釋了 [`23`](23-module-datafile-map.md) §2 的觀察 ——
模組只需要組出檔名字串,其餘由執行期處理。

**教訓:預期某個常數會出現在程式碼裡之前,先問「這個值是誰決定的」。**
由資料檔決定的值不會出現在程式碼裡。

## 3. `MONST*` 尺寸的下一步

`0x27FF` 這條線索作廢,改用:

1. `CMBT.EXE` 裡 `monst2.bin` / `monst4.bin` 兩個**字面值字串**的引用點
   —— 那是少數寫死的地方,順著它找 `BLOAD` 呼叫與之後的繪製
2. 繪製端比載入端更有用:`PUT` 用的陣列變數會透露尺寸
