# 35 — 派工表的多數進入點是薄包裝,共用實作

日期:2026-08-13
接續:[`34-races-and-char-fields.md`](34-races-and-char-fields.md)
子系統:**B. 執行期介面**

## 結論

派工表的相鄰進入點**不是各自獨立的實作**。
它們是**薄包裝**:每個進入點 `call` 同一支常式,並在 `call` 之後
擺 **2 bytes 的內嵌參數**;被呼叫的常式從**程式碼流**裡讀走那兩個 byte。

這把 ~130 個進入點收斂成**少得多的真實操作數**。

## 1. 形狀

`BRUN30` `0x199B3`–`0x199CC` 這一段:

```
0199B3  call sub_199CC
0199B6  <2 bytes 參數>
0199B8  call sub_199CC
0199BB  <2 bytes 參數>
0199BD  call sub_199CC
0199C0  <2 bytes 參數>
0199C2  call sub_199CC
0199C5  <2 bytes 參數>
0199C7  call sub_199CC     ← 派工表 3F:6E 指到這裡
0199CA  <2 bytes 參數>
0199CC  sub_199CC:
          pop  word ptr ds:10D8h    ← 取回返回位址 = 參數的位置
          …
          mov  si, ds:10D8h
          lods word ptr cs:[si]     ← 從程式碼流讀走參數
          mov  ds:10D8h, ax
          cmp  al, 3 / cmp al, 2    ← 依參數分派
```

`sub_199CC` **有 13 個呼叫端**,全部是這個形狀。

**信心等級:已確認**(`pop` + `lods cs:[si]` 是「呼叫後接內嵌參數」的標準寫法,
而 13 個呼叫端的排列完全一致)。

## 2. 對 API 對照表的意義

[`12`](12-api-3f61.md)、[`13`](13-api-3e42.md)、[`14`](14-brun-unlock-param-buffer.md)
把每個派工索引當成一支獨立常式去讀。**那個前提要修正**:

- 部分索引確實是獨立實作(`3F:61` 的描述子複製、`3E:42` 的緩衝區附加)
- 但**相鄰索引常常只是同一支實作的不同參數**

[`13`](13-api-3e42.md) §3 觀察過「派工表的相鄰索引常對到相鄰的實作」,
當時標「可當線索,不能當規則」。**現在知道成因了** ——
相鄰不是巧合,是因為它們本來就是同一組包裝。

### 修正後的解表策略

不要逐個索引讀。改成:

1. 找出所有「被多個派工進入點共用」的實作(像 `sub_199CC`)
2. 解那支實作 + 它的參數語意
3. **一次解開一整族索引**

這比逐個讀快一個量級,而且**參數本身就是分類資訊** ——
`sub_199CC` 收到的參數第二個 byte 只有 1 或 2,第一個 byte 有 2/3/4/8,
形狀像「操作類別 + 子類」。

## 3. 這是第三次遇到「參數藏在程式碼流裡」

| 出處 | 形式 |
|---|---|
| [`06`](06-runtime-int-abi.md) | `INT 3Dh/3Eh/3Fh` 後接 1–3 bytes 內嵌參數 |
| [`06`](06-runtime-int-abi.md) §3 | `INT 3Dh` 的 5-byte 形式會自我改寫成 far call |
| **本文** | **`call` 後接 2 bytes,被呼叫端用 `pop`+`lods` 取走** |

**這個技術棧大量使用「參數寫在呼叫點後面」的慣例。**
判準:看到 `pop <變數>` 出現在函式開頭,那個變數就是**參數指標**不是返回值 ——
而且該函式的每個呼叫端後面都會有資料,**線性反組譯到那裡一定會錯位**
([`15`](15-chain-filename-and-misalignment.md) §2 踩過)。

## 4. ⚠ 兩種不同的慣例,不要混為一談

掃「開頭是 `pop <記憶體>`」的函式,`BRUN30` 有 **5 支、合計 122 個呼叫端**:

| 函式 | 呼叫端 | 做什麼 |
|---|---:|---|
| `sub_11F6B` | **87** | **trampoline**(見下)|
| `sub_11EC3` | 16 | 同 `sub_11F6B` 的變體(存到同一個 `ds:0A60h`)|
| `sub_199CC` | 13 | **讀內嵌資料**(§1)|
| `sub_1D162` / `sub_1D16E` | 各 3 | 未解 |

### `sub_11F6B` 是 trampoline,不是讀參數

```
pop  word ptr ds:0A60h      ; 取回返回位址
mov  ds:0A08h, sp
push bp/si/di/ax/cx/dx/bx   ; 全部暫存器存起來
call word ptr ds:0A60h      ; ★ 呼叫「呼叫點後面那段」
pop  bx/dx/cx/ax/di/si/…    ; 還原
```

它把 `call` 之後的位元組當成**程式碼去執行**,執行前後保存／還原所有暫存器。
**那不是內嵌參數。**

### 對反組譯的實際差別

| 共用實作 | `call` 之後的位元組 | 線性反組譯 |
|---|---|---|
| `sub_199CC` | **資料** | **會錯位** |
| `sub_11F6B` / `sub_11EC3` | **程式碼** | 正確 |

⚠ 本文第一版把兩者都寫成「內嵌參數」。**`pop <變數>` 只說明它拿到了返回位址,
沒說明它拿去做什麼** —— 要看後面是 `lods`(讀資料)還是 `call`(執行程式碼)。

**判準:同一個開場指令不代表同一種慣例。** 這與
[`33`](33-quiz-validates-columns.md) §2.2(同一個欄位在不同型別上語意不同)
是同一個形狀。

## 4.5 `sub_199CC` 的參數是一個 4 × 3 網格

倒出每個呼叫端後面的 2 bytes:

| | 第二 byte `00` | `01` | `02` |
|---|---|---|---|
| 第一 byte `04` | `0x19990` | `0x199A4` | `0x199B8` |
| `08` | `0x19995` | `0x199A9` | `0x199BD` |
| `02` | `0x1999A` | `0x199AE` | `0x199C2` |
| `03` | `0x1999F` | `0x199B3` | `0x199C7` |

**十二個呼叫端剛好填滿 4 × 3,一格不多一格不少。**
第一 byte 取值 `{02, 03, 04, 08}`,第二 byte 取值 `{00, 01, 02}`,
而且呼叫端的位址順序與網格順序完全一致(每列間隔 5 bytes = `call` 3 + 參數 2)。

**信心等級:已確認**(結構完全規律,無例外)。

### 語意線索

`sub_199CC` 讀進參數後 `cmp al, 3` / `cmp al, 2` 分派,
之後走 `mov si, bx` / `mov di, 1Eh` / `sub di, ax` / `mov cx, ax` /
`shr cx, 1` / `rep movsw` —— **搬移量由第一個參數決定**。

所以形狀是「**一種操作 × 四種大小 × 三種模式**」。
`{2, 3, 4, 8}` 像是**位元組寬度**,`{0, 1, 2}` 像是**方向或型別**。
⚠ 兩者都是形狀推測,**未驗證**。

### 這一次解開了十二個派工索引的「族」

不必逐個讀 —— 它們是同一支實作的十二種參數組合。
**這印證了 §3 提出的解表策略。**

⚠ `find_inline_param.py` 報 13 個呼叫端,實際只有 12 個 ——
第 13 個(`0x199CA`)落在第 12 個的參數位元組上,是**線性反組譯把資料讀成指令**的假陽性。
症狀:它的「參數」`8f 06 d8 10` 正好是 `sub_199CC` 開頭那條 `pop ds:10D8h` 的機器碼。
**判準:呼叫端數目要對得上結構;多出來的那個通常是錯位。**
