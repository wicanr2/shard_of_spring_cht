# 38 — 高頻 API 是 BASIC 的語言基本操作,不是遊戲功能

日期:2026-08-13
接續:[`37-api-3e79-3e83.md`](37-api-3e79-3e83.md)
子系統:**B. 執行期介面**

## 結論

再讀兩個高頻 API 之後,派工表的性質變清楚了:
**呼叫量最高的那幾支是 BASIC 的語言基本操作(指派、加法),不是遊戲功能。**

這解釋了為什麼它們的呼叫次數是數百到上千 ——
每一行 BASIC 敘述都會用到。

## 1. `3F:55` → `0x19DE5`(263 次):**字串相加**(`A$ + B$`)

```
mov  ds:0A08h, sp        ; API 共同開場白(docs/re/37 §3)
push cx/dx/si/di
mov  si, ax              ; ax = 字串 A 的描述子
mov  di, bx              ; bx = 字串 B 的描述子
mov  bx, [si]
add  bx, [di]            ; 兩個**長度**相加
jo   <字串太長>
call sub_1A08B           ; 配置 bx 個 byte 的字串空間
xchg di, dx / push bx
call sub_19E0B           ; ★ rep movsw:把 A 的內容複製過去
mov  si, dx
call sub_19E0B           ; ★ 再複製 B 的內容
pop  bx / pop … / retf   ; bx = 新字串的描述子
```

`sub_19E0B` 是 `bx = si;cx = [si];si = [si+2];shr cx,1;rep movsw` ——
**用描述子的長度欄與指標欄搬資料**。所以相加的是長度,搬的是內容:
這是 BASIC 的**字串串接**。

**信心等級:已確認**(整支讀完)。

⚠ 這一節第一版寫「兩數相加」,而那是**讀到 `call sub_1A08B` 就停了**的結果 ——
前六條指令看起來確實像整數加法。判準:**一支 API 在 `call` 之後還有指令時,
那些指令往往才是它真正在做的事**;`retf` 之前的每一行都要讀完再命名。

實際用法看得最清楚的是組檔名:

```
CMBT 0x1075B   bx = 9368h(`fastcmbt.bin` 的描述子)/ ax = 37A0h(路徑前綴)
               INT 3F:55                      → 路徑 + 檔名
CMBT 0x11126   bx = 9448h(`rndmonst.bin` 的描述子)/ ax = 37A0h
```

## 2. `3F:BC` → `0x19B6D`(588 次):重設狀態

```
mov  byte ptr ds:0EB6h, 0
mov  word ptr ds:0A3Ah, 0     ; ★ 見 §3
call sub_11B09
mov  byte ptr ds:0EB7h, 0
call sub_19B84                ; 搬 7 個 word 到 ds:0EBAh
retf
```

清掉三個全域、搬一小塊資料。**信心等級:已確認**(指令完整)。

## 3. 兩支 API 之間的直接連結

`3F:BC` 把 **`ds:0A3Ah` 清成 0** ——
而 [`37`](37-api-3e79-3e83.md) §2 的 `3E:79`(624 次)第一道閘門
正是「`ds:0A3Ah` 為 0 就什麼都不做」。

**所以 `3F:BC` 會關掉 `3E:79` 的鉤子。** 兩支高頻 API 在同一個全域上互動。

⚠ 這是**兩支常式的機制關係**,不是語意定案 ——
那個鉤子做什麼(`sub_13BB8`)仍未解。

## 4. 重新理解整張派工表

| 索引 | 次數 | 內容 |
|---|---:|---|
| `3F:61` | 1,019 | 4 bytes 描述子複製 → **指派** |
| `3E:79` | 624 | 條件式鉤子 |
| `3F:BC` | 588 | 重設狀態 |
| `3E:44` | 520 | trampoline 包裝 |
| `3E:42` | 502 | 附加 word 到緩衝區 |
| `3F:6E` / `3F:6A` | 719 | `sub_199CC` 的 4×3 網格(搬移,大小×模式)|
| `3E:83` | 374 | 存 SP + `retf` |
| **`3F:55`** | **263** | **字串相加**(`A$ + B$`)|
| `3F:62` | 252 | 未解(位址 `0x9E1F`,緊接 `3F:55` 之後)|

**指派、加法、搬移、堆疊管理** —— 這是**語言執行期**的形狀,
不是「畫圖」「讀檔」這種遊戲 API。

⚠ **`3F:62` 的位址 `0x9E1F` 只比 `3F:55` 的 `0x9DE5` 大 `0x3A`** ——
[`35`](35-shared-impl-wrappers.md) 已確認相鄰索引常對到相鄰實作。
`3F:55` 是**字串**串接,所以旁邊那幾支多半也是字串操作(比較、取子字串),
不是數值運算。⚠ 推測,未驗證。

## 5. 這對專案的意義

**壞消息**:派工表的高頻端解出來多半是 BASIC 語言基本操作,
對「這個遊戲怎麼算傷害」沒有直接幫助。

**好消息**:正因為它們是通用操作,**讀模組程式碼時可以把它們當成
已知的算式符號**(`3F:61` = 指派、`3F:55` = 字串串接),
剩下的低頻索引才是遊戲功能所在。

**所以下一步的方向要改**:不是繼續往高頻走,
而是去看**只有少數模組用、次數不高**的索引 ——
那些才可能是「畫怪物」「讀存檔」這類遊戲層的東西。
