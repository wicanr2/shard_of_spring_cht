# 39 — `ds:0A3Ah`:執行期最中心的那個全域,與 xref 的結構性盲點

日期:2026-08-13
接續:[`38-api-are-basic-primitives.md`](38-api-are-basic-primitives.md)
子系統:**B. 執行期介面**

## 結論

兩件事:

1. **`ds:0A3Ah` 是執行期的「目前物件」指標**,62 處存取,
   有三個特殊常數(`0`、`0x0BE8`、`0x0B8E`、`0x10F0`)代表不同的未啟用/內建狀態。
2. **IDA 的 xref 看不到 `ds:xxxx` 這類存取** —— 因為它不知道 DS 的基底。
   這讓 `CLAUDE.md` §2.1 條件 2 在 16-bit DOS 的全域變數上**結構性地做不到**,
   必須換方法。已補工具 `tools/ida/find_dsref.py`。

## 1. 先講方法上的坑(這條比結論重要)

想確認 `ds:0A3Ah` 的讀寫端點,直覺做法是對它下 xref:

```
$ tools/ida.sh run tools/ida/range_xref.py BRUN30.EXE out/x.json 0x10A3A 0x10A3C
[{"target":"0x10A3B","from":"0x10A38","dis":"mov ax, 44B3h"}]
```

**一筆,而且是假的** —— `0x10A38` 那條指令的立即數位元組剛好蓋到 `0x10A3B`。

原因不是位址算錯([`40`](40-brun30-identity-and-ds-base.md) 證實 `0x10A3A` 就是對的),
而是 **IDA 根本沒為這種運算元建資料參考**:

```
0x13C9C  mov si, ds:0A3Ah
   op1 type=2(o_mem) value=0xA3A      ← 運算元有解析出來
   DataRefsFrom = []                  ← 但沒有任何 xref
```

運算元被解析成 `o_mem` 且位移正確,**xref 仍然是空的** ——
段相對位移要接成線性位址得靠段暫存器的值,IDA 不會替 16-bit 目標自動接。

**判準:xref 為空要先問「這種存取形式會不會產生 xref」,不要直接讀成「沒人用」。**
(這正是 `~/diagnosis-notes/docs/02-query-returned-empty/` 講的
「自己的過濾器有洞」那一型 —— 查詢工具的能力邊界,不是資料的性質。)

換成掃運算元文字(`tools/ida/find_dsref.py`),同一個位址**命中 62 處**。
0 → 62,不是程度差別,是有無差別。

### 這對 `CLAUDE.md` §2.1 的影響

條件 2 原文是「用 xref 確認讀寫端點」。對 DS 相對的全域**這條做不到**,
不是偷懶,是工具在這個目標上沒有這個能力。
已在 `CLAUDE.md` §2.1 加註替代做法:**改用運算元文字掃描,並附上掃描的分母**
(掃了幾條指令 —— 見 [`24`](24-tooling-conflict.md) 的教訓:分母比分子重要)。

## 2. `ds:0A3Ah` 的三支 API

| API | 只有誰用 | 位址 | 動作 |
|---|---|---|---|
| `3F:C0` | **CAMP**(14 次) | `0x19AF6` | `ds:0A3Ah ← 0x0BE8` |
| `3F:BC` | 全部(588 次) | `0x19B72` | `ds:0A3Ah ← 0` |
| `3E:79` | 全部(624 次) | `0x13C9C` | 讀出來判斷 |

`3E:79` 的完整判斷([`37`](37-api-3e79-3e83.md) §2 只讀到一半,這裡補齊):

```
si = ds:0A3Ah
if si == 0        → 什麼都不做
if si == 0x0BE8   → 什麼都不做          ★
if !(byte[si+0x31] & 0x80) → 什麼都不做
else              → call sub_13BB8
```

**`0x0BE8` 是哨兵值,不是常式位址。** 它與 `0` 並列在同一組跳過條件裡 ——
兩個不同的值代表兩種不同的「未啟用」。
⚠ 我一度把 `0x0BE8` 當成 `BRUN30` 段內位移去 dump `0x10BE8`,讀到的是別的函式的中段。
**看到一個數值像位址,先確認它被當位址用過再去 dump。**

`si+0x31` 有一個旗標位元組(bit 7)—— 所以 `ds:0A3Ah` 指向的是**結構**,
而且結構至少 0x32 bytes。**信心等級:已確認**(指令直接讀出)。

## 3. 62 處存取的形狀

| 形狀 | 處數 | 意義 |
|---|---:|---|
| `mov word ptr ds:0A3Ah, 0` | 24 | 清除 |
| `mov si, ds:0A3Ah` | 14 | 取出當指標用 |
| `mov ds:0A3Ah, si` / `, bx` | 9 | 設定 |
| `cmp word ptr ds:0A3Ah, 0` | 9 | 測試 |
| `push` / `pop` / `xchg` | 5 | **存救後還原** |
| `mov word ptr ds:0A3Ah, <常數>` | 4 | `0x0BE8`×2、`0x0B8E`×2、`0x10F0`×1 |

**`push ds:0A3Ah` … `pop ds:0A3Ah`(`0x1944A`/`0x19469`、`0x1C685`/`0x1C6A4`)
說明它是「目前正在處理的東西」** —— 巢狀操作要先存起來,做完還原。
這是 current-object 指標的典型用法,不是單純的旗標。

**信心等級:已確認**(62 條指令逐條列出,掃描分母 28,462 條)。

### 三個內建常數是什麼:未解

`0x0BE8`、`0x0B8E`、`0x10F0` 三個值被直接指派進去。
**假設**:它們是內建裝置的結構位址(BASIC 的 `SCRN:`/`KYBD:`/`LPT1:` 這一類),
理由是「數量少、寫死、與 0 並列當成特殊狀態」。

**⚠ 這個假設已被降級。** [`40`](40-brun30-identity-and-ds-base.md) §3 在
`DS = CS` 之下查了那三個位址,落點是程式碼與字串中段,`+0x31` 毫無規律 ——
**是反證不是佐證**。目前兩種讀法都還活著:執行期的 DS 另有基底,
或者這三個值根本不是指標(`3E:79` 對它們正好是**不解參考**)。

## 4. 順帶解出的:只有兩支模組用的 API

[`38`](38-api-are-basic-primitives.md) §5 說方向要改往低頻索引。
125 個索引依「被幾支模組用」分類(七支主要模組):

| 用的模組數 | 索引數 |
|---:|---:|
| 7(全部) | 32 |
| 3–6 | 45 |
| 2 | 24 |
| **1** | **24** |

**最乾淨的訊號是 `3E:36` 與 `3E:55` —— 只有 `MAZEMOVE` + `WRLDMOVE` 用**,
正好是迷宮與世界地圖這兩支移動模組。

而且五個候選的目標位址全部落在 `BRUN30` 的 `0xEA00`–`0xF300`,
算術族則在 `0x99xx`–`0x9Exx` —— **分區本身就是證據**,
不同功能族的常式在執行期裡是分開擺的。

`3E:5E` / `3E:5F`(只有 CMBT 用)共用另一對全域 `ds:1144h` / `ds:1146h`,
後者是一個 4 bytes 的描述子(`movsw` ×2),`+3` 是型別標籤
(拿來跟 `0` 和 `0x90` 比),`+2` 的 bit 7 另有意義。**語意未解。**
