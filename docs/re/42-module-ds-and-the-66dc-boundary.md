# 42 — 模組的 `ds:` 位移,與 `0x66DC` 其實是真位址

日期:2026-08-13
接續:[`41-ds-base-solved.md`](41-ds-base-solved.md)
子系統:**B. 執行期介面** / **A. 執行檔架構**

## 結論

把 [`41`](41-ds-base-solved.md) 的位移分布法套到遊戲模組,得到兩件事:

1. **模組的資料段是執行期配置的,遠大於檔案映像** —— 位移最大到 `0xA0B4`(CMBT),
   `MAZEMOVE` 有 571 個位移超出自己的整份映像。所以**大半是 BSS,靜態讀不到初始值**。
2. **`bz` 標頭 `+0x12` 的門檻 `0x66DC` 是真的位址,不是記號值。**
   三支模組共同存取的位移在 `0x66C8`–`0x66DA` 連續排列,**正好停在門檻前一個 word**。

## 1. ⚠ 先講一個污染(否則下面的數字會被讀錯)

掃描涵蓋 `.i64` 裡的**所有節區**,包含 `seg005` 那份 loader stub。
**stub 的 DS 與模組的 DS 不是同一個** ——
stub 是 `CS = SS = <stub 基底>`(三支的 `SP` 都是 `0xBE7`,正好是 stub 的長度 3,047)。

所以位移 `≤ 0xBE7` 的那些(`0x10`、`0x937`…`0x9BD`)是 **stub 的變數**,
不是模組的。它們在三支裡完全相同,因為[十一支共用同一份 stub](01-inventory.md)。

**判準:同一個資料庫裡有多個段暫存器情境時,位移統計要先按節區分開。**
這一次沒分,是靠「`0x945` 對得上 `docs/re/02` §1 的 `word_10AC5`」才發現的。

扣掉 stub 之後,三支模組**共同**的位移只有 17 個:

```
0x34F8  0x3518  0x351A  0x352C
0x66C8  0x66CA  0x66D0  0x66D2  0x66D4  0x66D6  0x66D8  0x66DA
0x67F0  0x67FC  0x6808  0x680A  0x6818  0x681A
```

## 2. `0x66DC` 是真位址

[`03`](03-bz-module-header.md) §3 讀出 `bz` 標頭 `+0x12` 是重定位的分類門檻,
六支主要模組的值是 `0x66DC`。當時寫的是:

> `0x66DC` 遠大於任何模組的實際大小 —— 所以那不是模組內的位址,是 linker 給執行期保留的記號值。

**那個推論不成立。** 上面 §1 的清單裡,`0x66C8` 起連續八個 word
(`C8 CA` … 中間跳過 `CC`/`CE`,再 `D0 D2 D4 D6 D8 DA`)**停在 `0x66DA`**,
下一個位移要到 `0x67F0`。

```
0x66C8 0x66CA … 0x66D8 0x66DA │ 0x66DC ← 門檻
                              └─ 之後 0x6700 區間整段沒有存取
```

門檻正好落在這段連續存取的**結尾外一格** —— 那是「區域結束位址」的形狀,
不是隨便挑的記號值。

**錯在哪:**「這個值大於模組的大小」推得出「它不是模組內的位移」,
但**推不出「它不是位址」** —— 我把「模組檔案的大小」當成了「位址空間的大小」。
模組的資料段是執行期配置的,可以比檔案大得多(這正是 §3 的結論)。

**信心等級:證據充分。** 兩個來源獨立 ——
左邊是**標頭裡的位元組**,右邊是 **1,702 + 853 + 421 個指令運算元的分布**。

## 3. 資料段遠大於檔案映像

| 模組 | seg000 結束 | 整份映像 | `ds:` 位移最大 | 超出映像的位移 |
|---|---|---|---|---:|
| `CMBT` | `0x8FD0` | `0xAE97` | `0xA0B4` | 0 |
| `MAZEMOVE` | `0x41A0` | `0x5A77` | `0x966A` | **571** |
| `TOWN` | `0x2650` | `0x46F7` | `0x7D10` | **384** |

`MAZEMOVE` 與 `TOWN` 的存取有一大半落在自己映像之外 ——
**那些位址在檔案裡根本不存在**,是 BASIC 執行期配置 DGROUP 之後才有的。

`CMBT` 的 0 個超出是巧合:它最大,映像剛好蓋住那個範圍
(1,325 個位移落在 `0x9000`–`0x9FFF`,對到它的 `seg004`)。
**不要把 CMBT 的 0 讀成「模組資料都在檔案裡」。**

### 這對 §2.1 條件 2 的意義

[`23`](23-module-datafile-map.md) §5 記的結構性阻礙(從模組程式碼掃不到陣列索引)
現在多了一個成因:**模組的變數大半不在檔案裡**,靜態分析看得到存取、看不到內容。

要拿到那些值只有兩條路:解出執行期的配置佈局,或 DOSBox 動態觀察
([`32`](32-dosbox-oracle.md))。
