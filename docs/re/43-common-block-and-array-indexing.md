# 43 — 找到陣列索引的指紋,與跨模組的 COMMON 區

日期:2026-08-13
接續:[`42-module-ds-and-the-66dc-boundary.md`](42-module-ds-and-the-66dc-boundary.md)
子系統:**D–L 的共同基礎**(遊戲狀態怎麼存)

## 結論

[`23`](23-module-datafile-map.md) §5 說「從模組程式碼掃不到陣列索引,所以 §2.1 條件 2 做不到」。
**那個結論是錯的 —— 我掃錯指紋了。**

BASIC 的 word 陣列索引長這樣,**沒有乘法**:

```
mov di, [bp-8]        ; 迴圈變數
add di, 2Dh           ; + 45   ← 欄位位移
shl di, 1             ; × 2    ← word 陣列
mov ax, [di+6822h]    ; ★ 陣列元素
```

當時掃的是 `mul <stride>`,16,553 條指令 0 命中,於是寫成結構性阻礙。
改掃 `[reg+XXXXh]` 之後,光 `CMBT` 就有 **558 處、39 個相異基底**。

## 1. 主陣列 `ds:6822h`

`CMBT` 用了 **317 次**(占全部 `[reg+disp]` 的 57%),`MAZEMOVE` 22 次。

抽出索引前的 `add` 常數(169 處抓得到):

```
15  30  45  60  75  90  105  120  135  150  165  180  195  210  225  240  255  270  285
```

**19 個值全部是 15 的倍數。**(另有 `128`、`164` 兩個例外,是回溯 `add` 時抓到別的指令,共 2 處。)

所以:

```
A(列, 欄)  的位址 = 0x6822 + (欄 × 15 + 列) × 2
```

**元素是 word,每列 15 格。信心等級:已確認**(19 個獨立的常數都落在同一個模數上)。

⚠ **標籤已訂正**:15 是**寬度**不是列數 —— `[`52`](52-world-map-reader-and-shared-grid.md) §4`。
`ds:6822` 是「當前地圖」陣列,`WRLDMOVE` 用 103 欄、`CMBT` 用 15 欄。
所以這裡是 **15 欄 × 至少 20 列的戰鬥格**。

## 2. 列的用途:隊伍在第 9–13 列

`sub_17001`(`CMBT`)的迴圈:

```
017001  mov  ax, ds:34F8h
017004  add  ax, 8
017007  mov  ds:9DA8h, ax        ; 上界 = ds:34F8 + 8
01700A  mov  ax, 9               ; 下界 = 9
   …
017053  add  di, 2Dh             ; 欄 3
017056  shl  di, 1
017058  mov  ax, [di+6822h]
   …
01712C  cmp  ax, ds:9DA8h
017130  jg   <結束>
```

而 `ds:34F8h` 是什麼:

| 模組 | 對 `ds:34F8h` 的動作 |
|---|---|
| `MENU` | `mov word ptr ds:34F8h, 0` / **`cmp word ptr ds:34F8h, 5`** |
| `CMBT` | 16 處,**全部是讀** |
| `CAMP` | 8 處,全部是讀 |

**`ds:34F8h` 是隊伍人數,上限 5。** 在 `MENU`(建隊)初始化與檢查上限,
其他模組只讀不寫 —— 這正是「一處寫、多處讀」的形狀。
**信心等級:證據充分**(初始化為 0、與 5 比較、跨模組只讀,三項互相支持)。

於是迴圈 `9 … (人數+8)`,人數 5 時是**第 9–13 列** ——

```
列 0–8   ?        (9 格)
列 9–13  隊伍     (5 格)
列 14    ?        (1 格)
```

⚠ **「列 0–8 是敵人」是推測**,只有「戰鬥模組、9 格、與隊伍分開」這三個間接理由。
未驗證,不得當結論用。

## 3. 名字是另一個陣列:`ds:34E0h`,stride 4

同一個迴圈裡:

```
01710F  add  bx, 0FFF8h      ; − 8
017112  shl  bx, 1
017114  shl  bx, 1           ; × 4
017116  add  bx, 34E0h
```

`(迴圈變數 − 8) × 4 + 0x34E0` —— **stride 4**。
而 `INT 3F:61`([`12`](12-api-3f61.md):複製 4 bytes 的描述子,全模組呼叫量第一名 1,019 次)
緊接著就對它動作。

**4 bytes = BASIC 的字串描述子。** 所以 `ds:34E0h` 是一個**字串陣列**,
索引 1–5 對到隊伍的五個成員 —— **隊員名字**。
**信心等級:證據充分**(stride、描述子大小、`3F:61` 的語意、索引範圍四項吻合)。

## 4. COMMON 區:七支模組共用的位移

把七支主要模組的 `ds:` 位移取交集(扣掉 loader stub 的 `≤ 0xBE7`):

| 被幾支用到 | 個數 | 範圍 |
|---:|---:|---|
| **7** | 14 | `0x66C8`–`0x681A` |
| 6 | 2 | `0x3518`–`0x351A` |
| 5 | 3 | `0x34F8`–`0x353A` |
| 4 | 8 | `0x3534`–`0x379E` |
| 1 | **681** | `0x2693`–`0xD014` |

**每一支模組 `> 0xBE7` 的最低位移都是 `0x34F8` 或 `0x3516`**,而且七支共用的那 14 個
全部落在 `0x66C8`–`0x681A`。

**這是 BASIC 的 COMMON 區**:`CHAIN` 換模組時保留的變數。
681 個只有單一模組用到的位移則是各模組的私有變數。

**信心等級:已確認。** [`47`](47-source-filenames-and-master-inc.md) §1 找到了原因 ——
那八支模組**全部 include 同一份 `MASTER.INC`**,COMMON 宣告必須逐字相同才能 `CHAIN`。
統計(指令運算元)與檔名(檔案裡的字串)兩條證據互相獨立。

### 已解出語意的 COMMON 變數

| 位移 | 語意 | 信心等級 | 證據 |
|---|---|---|---|
| `ds:34F8h` | **隊伍人數(上限 5)** | 證據充分 | §2 |
| `ds:34E0h` | **隊員名字**(字串陣列,stride 4) | 證據充分 | §3 |
| `ds:6822h` | **「當前地圖」陣列**(`CMBT` 用 15 欄的戰鬥格;`WRLDMOVE` 用 103 欄的世界地圖) | 已確認([`52`](52-world-map-reader-and-shared-grid.md) §3)| §1 |
| `ds:681Ah` | **鍵盤字元** | 證據充分 | 與 `0Dh`(CR)、`1Bh`(ESC)、`08h`(BS)、`20h`、`7Eh` 比較 |
| `ds:6818h` | 字元處理暫存 | 假設 | 與 `61h`(`a`)、`7Ah`(`z`)比較,另設為 `3E7h`(999) |
| `ds:66DAh` | 迴圈計數器 | 證據充分 | `inc`/`dec`/`cmp`/歸零,無其他用途 |
| `ds:352Ch` | 上限 99 的計數 | 假設 | 與 `63h` 比較、設為 `63h` |

## 5. 這一輪的教訓

`23` §5 的錯誤不是「找不到」,是**用一個不會出現的樣式去找,然後把 0 命中讀成「不存在」**。

編譯器對 `A(i)` 這種 word 陣列產生的是 `add` + `shl`,
只有元素大小不是 2 的冪次時才會有 `mul`。
**掃描前要先問「這個樣式在這個編譯器/元素大小下會不會出現」。**

這與 [`39`](39-ds0a3a-and-xref-blind-spot.md) §1(xref 對 `ds:` 全域無效)是同一型錯誤:
**工具回空,先查工具的能力邊界,再談資料的性質。**
兩次都不是資料不存在,是我問錯問題。
