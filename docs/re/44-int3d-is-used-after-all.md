# 44 — 遊戲模組其實有用 `INT 3Dh`:一個過濾器造成的假結論

日期:2026-08-13
接續:[`43-common-block-and-array-indexing.md`](43-common-block-and-array-indexing.md)
子系統:**B. 執行期介面**

## 結論

[`07`](07-dispatch-tables.md) §2 以**已確認**寫著「遊戲模組不使用 `INT 3Dh`」。
**那是錯的。** 七支模組合計 **909 處 `INT 3Dh` 呼叫、24 個相異索引**。

連帶:`07` §2 撤掉的那個「346」也**撤錯了** —— 它是對的。

## 1. 錯在哪:助憶碼過濾器

`07` §2 的清點是這樣寫的:

```python
if idc.print_insn_mnem(head) != "int":
    continue
```

而 **IDA 不把 `CD 3D` 叫做 `int`**:

```
0x10052  cd3d 0a 90 90    wait; (emulator call)
0x10063  cd3f 55 90 90    int  3Fh; Overlay manager interrupt
0x10138  cd3e ...         int  3Eh; Borland languages - Floating Point emulation
```

`INT 3Dh` 在 Microsoft 的語言產品裡是**浮點模擬器**的向量,IDA 認得這個慣例,
把它顯示成 `wait`(協處理器等待)。於是 `mnem != "int"` 這個過濾器
**把 227 處全部濾掉**,清點結果是 0。

直接數位元組(不看助憶碼):

| | `CD 3D` | `CD 3E` | `CD 3F` |
|---|---:|---:|---:|
| **是指令起點** | **227** | 804 | 941 |
| 位元組層出現 | 241 | 821 | 1,016 |

**227 個 `CD 3D` 全部都是指令起點。**

⚠ 更難堪的是:`07` §2 自己的表格裡就寫著「其中落在程式碼區的位址 227」,
下一句卻寫「**卻沒有一個是指令的起點**」。
**同一節裡兩個數字互相矛盾,而我沒有察覺** —— 因為 227 那一列是位元組掃描算的,
0 那一列是助憶碼過濾算的,我把兩個不同方法的結果並排放進同一張表,
沒問「這兩個數怎麼會同時成立」。

## 2. 撤錯的那個 346

`06` §4 的表格有一欄「`3D` far 形式」,合計 **346**。
`07` §2 把它撤掉,理由是「線性掃描的中間計數,最終資料庫裡一個都不成立」。

修掉過濾器之後重數:

```
3D:00   346 次   7 支模組全部用到
```

**一模一樣的 346。** 而這兩個數字來自不同方法 ——
左邊是解鎖腳本掃描時的計數,右邊是從已建好的資料庫逐條指令取出。

`3D:00` 就是 [`06`](06-runtime-int-abi.md) §3 講的那個 **5 bytes 自我改寫形式**
(`CD 3D 00 oo oo` → `9A oo oo ss ss`),參數為 `0` 走的正是那條路。
**它是延遲繫結的 far call,346 處。**

**教訓:撤回一個結論,和下一個結論一樣需要證據。**
`07` §2 撤掉 346 時沒有重新測量,只是推論「中間產物不是結論」——
這句話本身沒錯,但它不構成「那個數字是錯的」。

## 3. 修正後的呼叫量

| 中斷 | 呼叫次數 | 相異索引 |
|---|---:|---:|
| `INT 3Dh` | **909** | **24** |
| `INT 3Eh` | 2,548 | 45 |
| `INT 3Fh` | 3,879 | 80 |

`INT 3Dh` 用得最多的幾個(七支模組全部用到):

| 索引 | 次數 | 形式 |
|---|---:|---|
| `3D:00` | 346 | 5 bytes,延遲繫結 far call |
| `3D:0A` | 144 | 3 bytes |
| `3D:05` | 59 | 3 bytes |
| `3D:03` | 53 | 3 bytes(6 支)|
| `3D:0B` | 47 | 3 bytes |
| `3D:0D` | 45 | 3 bytes |
| `3D:34` | 42 | 3 bytes |
| `3D:1B` | 32 | 3 bytes |

派工表 `cs:0x171`(105 筆)因此**重新回到待解清單**,而且是高優先 ——
[`38`](38-api-are-basic-primitives.md) 說「高頻端是 BASIC 基本操作,遊戲功能要往低頻找」,
但那個結論是在 `3Dh` 被誤判為「沒人用」的前提下下的。

## 4. 工具已修

`tools/ida/scan_calls.py` 改成直接看位元組:

```python
b = ida_bytes.get_bytes(head, 2) or b""
if len(b) != 2 or b[0] != 0xCD or b[1] not in (0x3D, 0x3E, 0x3F):
    continue
vec = b[1]
```

**判準:過濾條件本身要有正對照。** 這一次只要對任何一支模組數一下
「三個向量的指令起點合計」對不對得上位元組層的數量,就會立刻發現 `3Dh` 那一欄是 0。
成本是一行程式碼。
