# 46 — 模組的字串表:格式看出來了,DS 對應沒解出來

日期:2026-08-14
接續:[`45-int3d-family.md`](45-int3d-family.md)
子系統:**L. 中文化落點盤點**

## 結論

模組裡的文字以「**三個 4-byte 描述子 + 文字本體**」成組排列,描述子是
`<長度:2><DS 指標:2>`。**格式已確認**;
但**檔案位移與 DS 指標之間的對應沒解出來** —— 試過的線性對應被否證(§3)。

所以這一輪對中文化的貢獻是:**知道文字在檔案裡怎麼排**(可以定位與替換),
**還不知道改完之後指標要怎麼跟著改**。

## 1. 格式(`CAMP.EXE`,角色表)

```
004AF0  08 00 96 79     ; 長度 8,  DS 指標 0x7996
004AF4  0b 00 9a 79     ; 長度 11, DS 指標 0x799A
004AF8  10 00 9a 79     ; 長度 16, DS 指標 0x799A
004AFC  "Level:     "   ; 11 bytes
004B07  6e              ; 分隔
004B08  08 00 a8 79     ; 下一組
        …
```

連續五組完整重現這個形狀:

| 文字 | 長度 | 三個描述子的長度欄 |
|---|---:|---|
| `Skills:` | 7 | 8 / 7 / 12 |
| `Items:` | 6 | 8 / 6 / 10 |
| `Level:␣␣␣␣␣` | 11 | 8 / 11 / 16 |
| `Hit Pts.␣␣␣` | 11 | 8 / 11 / 16 |
| `Spell Pts.␣` | 11 | 8 / 11 / 16 |
| `Experience` | 10 | 8 / 10 / 14 |
| `Status␣␣␣␣␣` | 11 | 8 / 11 / 16 |

**第二個描述子的長度 = 文字長度**(7/7、6/6、11/11、10/10),七組全中。
第一個固定 8。第三個是文字長度 + 5 或 + 4,規則未定。

**信心等級:已確認**(格式);**未解**(第一與第三個描述子的用途)。

## 2. DS 指標確實是 DS 空間的位址

`CAMP` 的程式碼實際存取 `ds:7990`、`ds:7992`、`ds:7994`、`ds:79A6` ——
與上表的指標(`0x7996`、`0x799A`、`0x79A8`…)在同一個小範圍。

**所以那兩個位元組是真的 DS 位址,不是別的東西。信心等級:證據充分。**

## 3. ⚠ 被否證的假設:線性對應

若檔案位移與 DS 位址差一個常數,由 `0x7990 − 0x48F0 = 0x30A0` 可得對應。
拿另一個已知的程式碼存取點 `ds:79A6` 回推:`0x79A6 − 0x30A0 = 0x4906`,
而檔案 `0x4B06`(= 段內 `0x4906`)的內容是文字中間的一個空白,不是描述子。

**線性對應不成立。** 可能的原因:模組載入時資料是**分段搬移**的,
或描述子本身在載入時被重定位過([`03`](03-bz-module-header.md) §3 的機制)。

⚠ 這一節到此為止。再往下猜位元組就是打地鼠
(`rulebook/41`),要解得從**使用端的程式碼**走,不是從檔案佈局走。

## 4. 對中文化的實際意義

| 能做 | 不能做 |
|---|---|
| 定位每一段文字在檔案裡的位移與長度 | 改長度(指標要跟著改,而對應未知)|
| **等長替換**(中文佔 2 bytes,英文 1 byte → 字數減半) | 加長或縮短 |
| 盤點總文字量 | 自動化重排 |

**等長替換這條路現在就可行** —— 長度欄不用動,指標不用動。
代價是中文字數只有原文的一半,`Level:␣␣␣␣␣`(11)只能放 5 個中文字。
