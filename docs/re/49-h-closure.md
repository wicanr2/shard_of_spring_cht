# 49 — 子系統 H 收尾:讀取端、CGA 調色盤、`.PIC`

日期:2026-08-14
接續:[`48-monst-deinterleave.md`](48-monst-deinterleave.md)
子系統:**H. 圖形格式(只解位元佈局)**

## 結論

三個缺口一次補完:

1. **讀取端佐證**(`CLAUDE.md` §2.1 條件 1)—— `MIO2.EXE` 是當年產生 `MONST*.BIN`
   的**開發工具**,它的迴圈直接寫著交錯公式 `j×8 + i`。
2. **CGA 調色盤** —— 遊戲寫 `0x3D8 = 0x0E`,而 `0x3D9`(調色盤暫存器)
   **全套程式一次都沒碰**。
3. **`.PIC`** —— 不是點陣圖,是 **BASIC `DRAW` 巨集字串**(向量)。

## 1. `MIO2.EXE`:出貨時忘了拿掉的開發工具

它的字串:

```
load picture file #
now saving monst??.bin files
verify your pictures
```

模組本體只有 1,760 bytes、551 bytes 程式碼 —— 小到可以整份讀完。

### 交錯公式的直接證據

```
01013C  mov  di, ax           ; ax = 迴圈變數 j
01013E  shl  di, 1            ; ×2 → word 索引
010140  mov  bx, [di+4F16h]   ; ★ 來源陣列(載入的圖)第 j 個 word

010144  mov  si, ax
010146  shl  si, 1
010148  shl  si, 1
01014A  shl  si, 1            ; ★ ×8
01014C  add  si, ds:52C6h     ; ★ + 圖號 i
010150  shl  si, 1            ; ×2 → word 索引
010152  mov  [si+4F72h], bx   ; ★ 目標陣列第 (j×8 + i) 個 word

010156  inc  ax
01015A  cmp  ax, 2Dh          ; j 跑到 45
01015D  jle  short loc_1013C
```

**目標索引 = `j × 8 + i`** —— 與 [`48`](48-monst-deinterleave.md) 從資料側推出的公式**逐字相同**。

而且 `j` 跑 0–45 = **每張圖 46 個 word**,
與去交錯後實測「前七張各 46 words」完全吻合(46 = 2 標頭 + 44 資料,
44 words = 88 bytes,而 17 列 × 5 bytes = 85,餘 3 bytes 是陣列的尾巴)。

### 目標陣列的位址就是 BSAVE 標頭裡的那個

`MONST1.BIN` 的 BSAVE 標頭:`seg=0x27FF`,**`off=0x4F72`**。
而上面那條指令寫的是 **`[si+4F72h]`**。

**兩個 `0x4F72` 來自完全不同的地方** —— 一個是資料檔的標頭位元組,
一個是程式碼裡的立即數。這是 §2.1 條件 2 與條件 3 同時滿足。

## 2. CGA 調色盤

### 事實

| 埠 | 誰寫 | 值 |
|---|---|---|
| `0x3D8`(模式控制) | `MENU`、`CMBT`、`MAZEMOVE`、`WRLDMOVE`、`MIO2` 各一處 | **`0x0E`** |
| `0x3D9`(調色盤選擇) | **沒有任何模組或 `BRUN30` 碰它** | — |

`0x3D9` 是掃全部十一支模組 + `BRUN30` 的立即數得到的 **0 命中**;
`0x3D8` 在同一次掃描裡命中 5 處 —— **同一個過濾器下有正對照**,
所以這個 0 不是 [`39`](39-ds0a3a-and-xref-blind-spot.md) 那種工具盲點。

### 判讀

`0x0E` = `0b00001110`:

| 位元 | 值 | 意義 |
|---|---|---|
| 0(`0x01`) | 0 | 非 80 欄文字 |
| 1(`0x02`) | **1** | **圖形模式** |
| 2(`0x04`) | **1** | **黑白 / 關色彩載波** |
| 3(`0x08`) | **1** | 視訊輸出開啟 |
| 4(`0x10`) | 0 | 非 640×200 高解析 |

在 320×200 四色下,**位元 2 選的是第三組調色盤:黑 / 青 / 紅 / 白**
(對應 BIOS 的 mode 5)。這也是 `0x3D9` 不需要被寫的原因 ——
位元 2 一設,`0x3D9` 的調色盤選擇位元就不生效。

**信心等級:證據充分。** 條件 1 是那五條 `out` 指令;
條件 3 是 CGA 硬體的公開規格(外部獨立來源)。

⚠ **界線**:這裡只解「程式設定了哪一組調色盤」。
真實螢幕上的顏色還受顯示器型別影響(合成視訊 vs RGB),
依 `CLAUDE.md` §1.2 **不往下追**。

## 3. `.PIC` 是向量,不是點陣

三個檔(`MAZEITEM.PIC`、`WALKDRAW.PIC`、`WRLDITEM.PIC`)是**純文字**,
每行一段 BASIC `DRAW` 巨集:

```
BM+8,-8S8C3R4G1U2F1BL4TA90C3R4G1U2F1BL4TA180R4G1U2F1BL4TA270R4G1U2F1BL4TA0S4
C1R16U16L16D16BE1P1,1C3R2BE1R2BM+2,-4L2...
```

| 指令 | 意義 |
|---|---|
| `U D L R` | 上下左右畫線 |
| `E F G H` | 四個斜向 |
| `B` 前綴 | 只移動不畫 |
| `N` 前綴 | 畫完回原點 |
| `M±x,±y` | 相對移動 |
| `C n` | 顏色(檔案裡只出現 `C0`–`C3`,對得上四色)|
| `S n` | 縮放 |
| `TA n` | 旋轉角度(`TA90`/`TA180`/`TA270` —— 迷宮物件的四個朝向)|
| `P f,b` | 填充 |

**信心等級:已確認。** 語法完全符合 `DRAW` 的定義,
而且 `C` 的值域(0–3)與 `TA` 的四個角度都與遊戲內容自洽。

⚠ `MAZEITEM.PIC` 以 `0x0A` 結尾、另兩個以 `0x1A` 結尾 —— 差異未解,不影響判讀。

## 5. 這一輪的方法

解開最後三個缺口靠的都不是更用力地分析主要檔案:

- 讀取端 —— **出貨包裡有一支開發工具**(`MIO2.EXE`),而它比遊戲模組小 20 倍
- 調色盤 —— **查「誰沒有寫這個埠」**,而不是找誰寫了
- `.PIC` —— **先看檔案是不是文字**,再談容器格式

三個都是「換一個地方看」,不是「同一個地方看更久」。
`MIO2.EXE` 在 [`01`](01-inventory.md) 就列出來了,擺了一整天沒被當回事 ——
**清單裡最小的那個檔案,常常是最好讀的那份文件。**
