# 65 — `USERLIB` 的完整匯出表,與主要常式的判讀

日期:2026-08-14
接續:[`64-userlib-call-mechanism.md`](64-userlib-call-mechanism.md)
子系統:**C. 原生輔助程式庫**

## 結論

**匯出表就在 `USERLIB.EXE` 的檔案裡,可以整張讀出來** ——
63 個槽、每個一組 far 指標。找到它靠的是 **MZ 重定位表**。

## 1. 用重定位表找到匯出表

[`30`](30-userlib-family.md) 記過 `USERLIB` 有 **114 個重定位項**,但「指向哪」未解。

依 segment 分組:

| segment | 項數 | 相鄰間距 |
|---:|---:|---|
| **1822** | **69** | **60 個是 8** |
| 0 | 25 | 雜亂 |
| 388 | 16 | 雜亂 |
| 306 | 4 | 雜亂 |

**segment 1822 的位移是 `0x6D`、`0x75`、`0x7D`、`0x85`…,間距 8。**

而模組呼叫用的索引是 `0x6B`、`0x73`、`0x7B`…([`64`](64-userlib-call-mechanism.md) §2)——
**正好各差 2**,也就是 far 指標的**節區字**(`offset:segment` 的後半,只有它需要重定位)。

**兩個來源完全獨立**:一邊是 `USERLIB.EXE` 的 MZ 重定位表,
一邊是七支遊戲模組的指令立即數。**8-byte 格線與 +2 的偏移同時吻合。**

## 2. 完整匯出表(63 個槽)

檔案位移 `0x200 + 1822×16 = 0x73E0` 起,每 8 bytes 一筆,far 指標在 `+3`:

| 槽 | 指標(檔案裡的原始值)| 槽 | 指標 |
|---:|---|---:|---|
| 13 | `0000:03D9` | 30 | `0000:0C3F` |
| 14 | `0000:0C8A` | 31 | `0000:0B54` |
| 15 | `0000:040A` | 32 | `0000:0303` |
| 16 | `0000:0437` | 33 | `0000:0CB6` |
| 17 | `0000:1040` | 34 | `0000:07EF` |
| 18 | `0000:0F07` | 35 | `0000:05B4` |
| 19 | `0184:015C` | 36 | `0000:12F6` |
| 20 | `0132:0128` | 37–49 | `020D:00xx` |
| 21 | `0000:1243` | 50–51 | `0000:0000` |
| 22 | `0000:0C0B` | 52–58 | `0132:0000` |
| 23 | `0000:0346` | 59–67 | 各節區的 `:0000` |
| 24 | `0000:07AB` | 68–75 | `0519`–`071E` |
| 25 | `0000:0B27` | | |
| 28 | `0000:0FF5` | | |
| 29 | `0000:0B78` | | |

**遊戲用到的 19 個槽全部是 `0000:xxxx`** —— 指向 `USERLIB` 的第一個節區(IDA `0x10000`)。
槽 37 以上指向別的節區、偏移多為 0,形狀不像函式進入點(可能是資料或未使用)。

## 3. 主要常式的判讀

`USERLIB` 解鎖後(線性掃描,36% 判成指令、10 個函式、60 處 `INT 3Dh`):

| 槽 | 次數 | 進入碼 | 判讀 | 信心 |
|---:|---:|---|---|---|
| **35** | **113** | `call far 0x1040A`(=槽 15)/ `mov bx, 310Eh` / `int 3F:62`(比較)| **先畫視窗再比對輸入** —— 訊息框 + 等待按鍵 | 證據充分 |
| **15** | 48 | `bx=0AEh(174) dx=4Fh(79) int 3E:84` / `bx=138h(312) dx=0B7h(183) int 3E:85` | **畫視窗框**:`(174,79)–(312,183)`,在 320×200 裡是右下方的訊息框 | 證據充分 |
| **32** | 74 | `mov di,[bp+6]` / `3F:57` / `mov di,3040h` / `3F:7D` / `mov si,3102h` / `3F:6F` | 字串處理 | 假設 |
| **23** | 34(七支全用)| `bx=30F8h dx=304Ch 3F:61`(指派)/ `3F:62`(比較)| 字串指派 + 比較 | 假設 |
| 24 | 10 | `bx=17h(23) 3E:42` / `bx=18h(24)` | 文字列 23/24 —— 25 列螢幕的最後兩列 | 假設 |
| 22 | 4 | `bx=ds:35B8h dx=ds:35BAh 3E:87` | 對全域做算術 | 未解 |
| 21 | 2 | `bx=3400h dx=30B6h 3F:61` | 字串指派 | 未解 |

**槽 35 呼叫槽 15** —— 那是唯一一處匯出常式互相呼叫的直接證據,
也解釋了為什麼這兩支的呼叫量是第一與第三名:**訊息框是遊戲最常做的事**。

⚠ 其餘 12 個槽只有進入碼、沒有判讀。**未解。**

## 4. ⚠ 工具上的事故:連續開關 `.i64` 會弄壞它

要 dump 19 個位址時,我跑了 19 次 `idat`,結果第 5 次之後資料庫壞掉
(`Failed to initialize IDA as library (error code 4)`)。
**這是本專案第三次踩到同一個失敗模式**,前兩次都是 `BRUN30.EXE.i64`,
而且都發生在一連串快速的循序執行之後。

修法:`tools/ida/dump_many.py` —— **一次執行 dump 多段**。
19 次縮成 1 次,而且快很多。

**判準:對同一個 `.i64` 的批次操作要合併成單次 `idat` 執行。**
已補進 `~/.claude/knowledge-base/retro/ida-pro-9.4.md`。
