# 68 — 子系統 B 收尾:三張派工表的容量

日期:2026-08-14
接續:[`67-a-closure-module-handoff.md`](67-a-closure-module-handoff.md)
子系統:**B. 執行期模組的呼叫介面**

## 結論

[`07`](07-dispatch-tables.md) §3 掛著「表的容量至今沒有被量到」。量到了:

| 表 | 位址 | 容量 | 索引範圍 | 實際用到的最大索引 | |
|---|---|---:|---|---:|:-:|
| `INT 3Dh` | `cs:0x171` | **105** | 0–104 | 98(`0x62`)| ✅ 在容量內 |
| `INT 3Eh` | `cs:0x243` | **165** | 0–164 | **165(`0xA5`)** | ⚠ **超出一格** |
| `INT 3Fh` | `cs:0x38D` | **204** | 0–203 | 201(`0xC9`)| ✅ 在容量內 |

## 1. 邊界怎麼定的

前兩張靠**下一張表的起點**:

```
3Dh:  (0x243 − 0x171) / 2 = 105
3Eh:  (0x38D − 0x243) / 2 = 165
```

第三張沒有「下一張表」,改用**表後面接什麼**:

```
3F[204] 起讀到的值不再像位址,而像指令位元組
而 cs:0x526 是 INT 21h AH=25h 的向量安裝碼(docs/re/06 §1)
   (0x526 − 0x38D) / 2 = 204
```

**所以 `3Fh` 表最多 204 筆,而實際用到的最大索引是 201 —— 剛好塞得下。**

⚠ 這是**上界**:表可能更短,後面補了未使用的填充。
但既然最大用到 201,「至少 202 筆」是確定的,而上界 204 ——
**區間只剩 3 筆的不確定性。**

## 2. `3Eh` 的索引 165 落在 `3Fh` 的第 0 筆

`3E[165]` 的位址 = `0x243 + 165×2 = 0x38D` = **`3Fh` 表的基底**。

所以 [`07`](07-dispatch-tables.md) §3 記的觀察「`3E[165]` 與 `3F[0]` 讀到同一個 word(`0x9580`)」
**不是巧合,是必然** —— 兩張表相鄰,前一張的「第 166 筆」就是後一張的第 1 筆。

而 [`08`](08-code-data-separation.md) §3 確認 `3E:A5` 在線性掃描與流程追蹤下**都會出現**,
所以那是真的呼叫點。

**結論:遊戲確實會呼叫 `3E:A5`,而它等價於 `3F:00`。**
⚠ 是編譯器的刻意共用,還是溢出後恰好可用,**未解**。
但**行為是確定的**:兩者跳到同一支常式。

## 4. 方法

容量這題卡了很久,是因為一直想從**處理常式**裡找上限 ——
[`07`](07-dispatch-tables.md) §3 寫「處理常式只給了基底沒給上限」,那是對的,
**而且永遠會是對的**:8086 的派工常式沒有理由做範圍檢查。

解法是換一個問法:**不問「表到哪裡結束」,問「表後面是什麼」。**
`3Fh` 表的後面是向量安裝碼,那段碼的位址早在 [`06`](06-runtime-int-abi.md) §1 就記下來了 ——
**答案在自己兩個月前寫的筆記裡。**

判準:**上界問不到時,去問下一個東西的下界。**
