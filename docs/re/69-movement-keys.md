# 69 — 移動畫面的按鍵:八個字串的三角驗證

日期:2026-08-14
接續:[`68-b-closure-dispatch-capacity.md`](68-b-closure-dispatch-capacity.md)
子系統:**K. 輸入語意**

## 結論

`WRLDMOVE` 與 `MAZEMOVE` 各有一組**完全相同**的八個單字元字串常數:

```
C   P   S   Q   1   2   3   4
```

`WRLDMOVE` 在 `ds:0xCD6E`–`0xCD98`、`MAZEMOVE` 在 `ds:0x8E02`–`0x8E2C`,
**兩邊的順序與間距(6)完全一致**。

**這兩支模組是全遊戲唯二沒有任何畫面按鍵提示的** ——
移動鍵不印在螢幕上,寫在說明書裡。

## 1. 為什麼認為那是按鍵

| 字元 | 判讀 | 佐證 |
|---|---|---|
| `C` | **Camp** | 兩支模組都有 `CAMP` 這個 `CHAIN` 目標字串 |
| `S` | **Save** | `USERLIB` 槽 34(存檔)**只被這兩支模組呼叫**([`66`](66-userlib-slot-semantics.md) §3)|
| `Q` | **Quit** | `WRLDMOVE` 有 `Thank you for visiting Islandia. Good Hunting.` |
| `1`–`4` | **四個方向** | 與 `MAZEDATA` 欄 4 的朝向同一套編號(`1=北 2=東 3=南 4=西`,[`57`](57-g-closure.md) §3,**從程式碼確認過**)|
| `P` | 未解 | — |

**三個獨立的佐證**(`CHAIN` 目標、`USERLIB` 呼叫者分布、朝向編號)
分別支持 `C`、`S`、`1`–`4`,而它們來自三個不同的地方。

**信心等級:證據充分**(`C`/`S`/`Q`/`1`–`4`);`P` 未解。

## 2. ⚠ 缺的是程式碼側的連結

`CLAUDE.md` §2.1 條件 1 要求在 IDA 裡讀到原始指令。**這一項沒有做到。**

試過的三條路都不通:

| 做法 | 結果 |
|---|---|
| 掃 `ds:xxxx` 的按鍵比較([`58`](58-key-dispatch-mechanism.md) §1)| 只找到共用輸入常式的 `08h`/`0Dh`/`1Bh`/`20h`/`7Eh` |
| 掃 ASCII 立即數(`cmp al, 'S'`)| `TOWN` 只有 loader stub 解析路徑的 `:` 與 `\` |
| 掃字串描述子位址(`0xCC00`–`0xCF00` **全範圍**)| **0 命中** |

**第三條最有說服力**:整個 `0xCC00`–`0xCF00` 區間,
`WRLDMOVE` 的 2,885 條指令裡**沒有任何一個立即數**落在裡面。

所以那八個字串**不是被個別引用的**,而是**整組讀進一個字串陣列**
(`DATA "C","P","S","Q","1","2","3","4"` + `READ`),再用索引比對。
⚠ 這是推論;陣列的基底沒有找到。

**對照組**:`CAMP` 的主選單就是逐個引用的
(`mov bx, 703Ch` / `mov bx, 7042h` …,[`58`](58-key-dispatch-mechanism.md) §2),
所以「同一個遊戲裡兩種按鍵派工寫法」是成立的。

## 3. K 的現況

| # | 條件 | 狀態 |
|---|---|---|
| 1 | IDA 讀原始指令 | **部分** —— `CAMP` 主選單 ✅([`58`](58-key-dispatch-mechanism.md) §2);移動鍵 ❌(§2)|
| 2 | 讀寫端點 | 部分 |
| 3 | 獨立資料印證 | `CAMP` 10/10 ✅、移動鍵三角驗證 ✅(§1)|
| 4 | 筆記 | ✅ |

**K 仍不標 RE-DONE**,缺口就是 §2 的那一項:**找到那個字串陣列的基底**。

不卡外部條件,但三條直覺路線都試過了 —— 要換方法
(例如從 `READ` 的執行期 API 反查,或從陣列描述子區找)。

## 4. ⚠ 工具:第四次資料庫損毀

`WRLDMOVE.EXE.i64` 在連續掃描後壞掉(`error code 4`),
**本專案第四次**。[`65`](65-userlib-export-table.md) §4 已把「批次合併成單次執行」寫進 kb,
但這次是**不同腳本的連續執行**(`find_dsref` → `imm_range`),不在原本的模式裡。

**修正後的判準:對同一個 `.i64` 的任何連續執行都要當成風險**,
不只是同一支腳本的迴圈。重建成本低(`analyze` + 解鎖約 30 秒),
但要記得重跑解鎖,否則後續掃描的分母會少一截([`24`](24-tooling-conflict.md) 的教訓)。
