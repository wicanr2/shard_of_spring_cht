# 70 — 按鍵語意:小鍵盤轉譯層 + 七支模組的完整比對鏈

日期:2026-08-14
接續:[`69-movement-keys.md`](69-movement-keys.md)
子系統:**K. 輸入語意**

## 結論

移動鍵解開了。[`69`](69-movement-keys.md) §1 的三角驗證**結論成立**
(`C` = Camp 由推論升為**已確認**,`1`–`4` = 四個方向亦然);
錯的是 §2 的「找不到程式碼側連結」——連結一直都在,是工具看不到(§6)。

多出來的一層是:那八個字元除了可以直接打,還是**小鍵盤方向鍵轉譯後的內部代碼**。

`WRLDMOVE` 的轉譯層(`0x105C3`–`0x10679`)把 BIOS 擴充掃描碼翻成字元,
排出來就是小鍵盤的實體佈局:

```
   7 Home = 'S'      8  ↑  = '1' 北     9 PgUp = 'P'
   4  ←  = '4' 西    5                  6  →  = '2' 東
   1 End  = 'C'      2  ↓  = '3' 南     3 PgDn = 'Q'
```

**四支方向鍵給方向,四個角落給指令。** 之後的比對鏈只認字元,
所以直接打 `C`/`P`/`S`/`Q`/`1`–`4` 效果一樣 —— 轉譯層只是替小鍵盤補了捷徑。

## 1. 轉譯層的程式碼

```
010594  mov  bx, 3794h        ; A$(INKEY$ 的結果)
010597  mov  dx, bx
010599  int  3Fh; BA          ; LEN(A$)
01059C  cmp  bx, 2            ; 擴充鍵是兩個位元組
0105A4  mov  bx, dx / mov dx, 1
0105A9  int  3Dh:0C / 3Fh:BB  ; ASC(MID$(A$,2,1)) → 掃描碼
0105B1  mov  ds:0CD66h, ax
0105B7  mov  word ptr ds:0CD66h, 3E7h   ; 不是擴充鍵 → 999
0105BD  mov  ax, ds:0CD66h / mov ds:0CD68h, ax
0105C3  cmp  word ptr ds:0CD68h, 4Fh    ; End
0105CD  mov  bx, 0CD6Ah                 ; ← 'C' 的描述子
0105D0  mov  dx, 3794h
0105D3  int  3Fh; 61                    ; A$ = "C"
        …(共八組)…
010673  cmp  word ptr ds:0CD68h, 3E7h   ; 999 → 不是擴充鍵,原樣往下走
```

| 掃描碼 | 小鍵盤 | 描述子 | 字元 |
|---|---|---|---|
| `0x4F` | End(1) | `0CD6Ah` | `C` |
| `0x49` | PgUp(9) | `0CD70h` | `P` |
| `0x47` | Home(7) | `0CD76h` | `S` |
| `0x51` | PgDn(3) | `0CD7Ch` | `Q` |
| `0x48` | ↑(8) | `0CD82h` | `1` |
| `0x4D` | →(6) | `0CD88h` | `2` |
| `0x50` | ↓(2) | `0CD8Eh` | `3` |
| `0x4B` | ←(4) | `0CD94h` | `4` |

**信心等級:已確認**(逐條指令讀出)。

## 2. ⚠ 訂正:描述子位址是「文字位址 **− 4**」,不是 `+2`

[`58`](58-key-dispatch-mechanism.md) §2 寫「程式碼引用的是文字位址 +2」。**那是錯的。**

執行期的字串常數區塊是 `[len:2][ptr:2][文字]`,`ptr` 指向文字,
**程式碼引用的是區塊起點 = 文字位址 − 4**。

單字元字串的間距剛好是 6,所以 `文字+2` 與「下一個文字 −4」**是同一個位址** ——
兩條規則在整段單字元字串裡完全無法區分,
只有在**字串長度改變的邊界**才會分岔。三個獨立的邊界證據:

| 證據 | 內容 |
|---|---|
| `mov bx, 0CDBAh` | `0xCDBA+4 = 0xCDBE` = `'CAMP'`(4 字元,`+2` 會落在 `'P'` 的中間)|
| `mov bx, 0CD6Ah` | `+2` 會指到 `ds:0CD68h` —— 那是**轉譯層自己的整數變數**,不可能 |
| `MAZEMOVE 0x8E50` | `+4 = 0x8E54` = `'CAMP'`,與 `WRLDMOVE` 同形 |

**[`58`](58-key-dispatch-mechanism.md) §3 的「`CAMP` 主選單 10/10」不受影響** ——
整條鏈一起位移一格,字母集合不變(§3 重跑後仍是 `S C R T E H I D U P`)。
受影響的只有 §2 那段程式碼摘錄裡「哪個位址對哪個字母」的標註。

> **判準**:等距排列的資料上,**任何「差一格」的規則都驗不出來**。
> 要驗就得找**間距改變的邊界**。整段 1 字元字串裡做一百次核對,證據強度還是零。

## 3. 移動的方向:從程式碼確認

```
0106A2  mov bx, 0CD82h   ; '1'
0106A5  int 3Fh; 62      ; 字串比較
0106AD  cmp word ptr ds:3520h, 1      ; 目前朝向
0106B7  mov ax, ds:3518h              ; x 不變
0106BD  mov bx, ds:351Ah / dec bx     ; y − 1   → 北

0107B8  mov ax, 0CD9Ah   ; '2' 的比較
0107C3  cmp word ptr ds:3520h, 2
0107CD  mov ax, ds:3518h / inc ax     ; x + 1   → 東
```

**`1` = 北、`2` = 東**,與 [`57`](57-g-closure.md) §3 從 `MAZEDATA` 欄 4 解出的
`1北 2東 3南 4西` 一致。⚠ 兩邊**來源獨立**(一邊是指令、一邊是資料檔)。

`ds:3520h` 是隊伍目前的朝向:**朝向不同時不會直接位移**(先轉身)。

## 4. 指令鍵對到什麼

| 鍵 | `WRLDMOVE` | `MAZEMOVE` |
|---|---|---|
| `C` | `CHAIN "CAMP"`(`mov bx,0CDBAh` → `'CAMP'`,`call sub_11595`)| 同形(`0x8E50` → `'CAMP'`)|
| `P` | `INT 3Dh:00` 索引 `0x010B` | `INT 3Dh:00` 索引 `0x010B` |
| `S` | `INT 3Dh:00` 索引 `0x0113` | `INT 3Dh:00` 索引 `0x0113` |
| `Q` | `INT 3Dh:00` 索引 `0x00AB` | `INT 3Dh:00` 索引 `0x00AB` |
| `J` | 另有處理(`0xCDC2` → `'J'`)| **無** |

**兩支模組的三個 `USERLIB` 進入點索引完全相同**,而它們是分開編譯的兩份原始碼 ——
這是「按鍵綁定在兩個畫面一致」的獨立佐證。

`C = Camp` 已確認(`CHAIN` 目標字串直接寫在程式碼裡)。
`S = Save` 仍是**推論**:[`66`](66-userlib-slot-semantics.md) §3 的存檔槽只被這兩支模組呼叫,
但 `0x0113` 這個索引還沒對回槽號。`P`、`Q`、`J` 未解。

## 5. 七支模組的比對鏈(全數抽出)

`tools/scan_key_chains.py`,結果存成
[`generated-key-chains.json`](generated-key-chains.json):

| 模組 | 鏈 |
|---|---|
| `CAMP` | `S C R T E H I D U P` + 子選單 `A I G Y / : H T D E G` |
| `CHARUTIL` | `N J F D I R C E A H D T E G H A B …` |
| `CMBT` | `1 1 1 1 2 3 4 D ? / C S A U Y N …` + 兩字元碼 `BP HT HK BR DD PS FL` |
| `MAZEMOVE` | `1 2 3 4 S P C Q` |
| `MENU` | `L C L A B L R A Y B Y Y I E 1 2 M Y F T Q Y Q P A B C Z` |

每條鏈的開頭都有 `0` 和 `9` —— 那是共用輸入常式的**數字範圍檢查**
(`IF A$ >= "0" AND A$ <= "9"`),不是按鍵,已從上表剔除。

拿 [`28`](28-input-semantics.md) 的 `X)` 提示慣例去比:

| 模組 | 提示有、鏈沒有 | 判讀 |
|---|---|---|
| `CAMP` | `3`–`9` | 數字選角色,走範圍檢查 |
| `TOWN` | `3`–`9`、**`N`** | 數字同上;`N` 未解 |

⚠ **反過來的方向不對稱**:鏈裡有而提示沒有的字母**很多**,那是正常的
(隱藏鍵、子選單、非選單輸入),不能當成缺口。

## 6. ⚠ 為什麼這次要繞開 IDA

[`69`](69-movement-keys.md) §2 用 `tools/ida/imm_range.py` 掃 `0xCC00`–`0xCF00`
得到 **0 命中**,而那些 `mov bx, 0CD70h` **就在那裡**。

原因:`imm_range.py` 只看 `ida_bytes.is_code()` 為真的位址,
而解鎖腳本只把模組區的 **~40%** 判成程式碼([`06`](06-runtime-int-abi.md) §4)。
落在另外 60% 的指令,對這支工具是**不存在的**。

> **判準**:**以 IDA 的判定為前提的工具,回「0 命中」時不能當成「不存在」。**
> 先問「這支工具的分母是什麼」。這一輪的分母是「已判成程式碼的 2,885 條指令」,
> 不是「模組裡的全部指令」。純位元組掃描沒有這個分母問題,
> 代價是要自己處理指令邊界 —— 用 `mov r16, imm16` 這種**定長且有明確前導位元組**的
> 形狀就避開了。
