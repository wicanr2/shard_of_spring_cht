# 72 — 規則資料表:三個格式從**讀取端**解出來

日期:2026-08-14
接續:[`71-k-closure.md`](71-k-closure.md)
子系統:**E. 規則資料表**

## 結論

`CMBT.EXE` 裡三段 `OPEN` + 迴圈,把 `SPELLS.DAT`、`ITEMS.DAT`、`MONSTERS.DAT`
的**欄數、型別、列數、記錄長度**全部定死。三個檔的**位元組大小各自獨立驗證通過**。

| 檔 | 格式 | 列數 | 欄 |
|---|---|---:|---|
| `SPELLS.DAT` | 逗號分隔文字 | **33** + 1 列哨兵 | 字串, 整數×4, 字串 |
| `ITEMS.DAT` | 逗號分隔文字 | **57** | 字串×2, 整數×4 |
| `MONSTERS.DAT` | **定長隨機存取,每筆 36 bytes** | **74** | 名稱 16 bytes + 整數×10 |

## 1. 怎麼認出型別:元素大小

BASIC 的整數陣列每格 2 bytes、**字串陣列每格 4 bytes**(長度 + 指標的描述子)。
迴圈裡的位址算術直接透露元素大小:

```
0107CE  shl bx, 1 / shl bx, 1     ; i × 4  → 字串陣列
0107D4  add bx, 7274h
0107D8  int 3Fh; B8               ; INPUT# 一格

0107DF  shl dx, 1                 ; i × 2  → 整數陣列
0107E3  add dx, 72FCh
0107E9  int 3Fh; B8
```

⚠ **4 bytes 不代表單精度浮點。** 兩者同樣是 4 bytes,分不出來 ——
是資料檔那一欄放的是文字(`COLUMN OF FIRE`、`Burnt for`)才定案的。
**元素大小給的是「幾個位元組」,不是「什麼型別」。**

## 2. `SPELLS.DAT`:6 欄 33 列

`CMBT 0x10797`(檔號 `#2`):

| 欄 | 陣列基底 | 元素 | 內容 |
|---:|---|---:|---|
| 1 | `ds:7274h` | 4 | 法術名 |
| 2 | `ds:72FCh` | 2 | 整數 |
| 3 | `ds:7340h` | 2 | 整數 |
| 4 | `ds:7384h` | 2 | 整數 |
| 5 | `ds:73C8h` | 2 | 整數 |
| 6 | `ds:740Ch` | 4 | 命中訊息 |

**間距自洽**:`0x72FC−0x7274 = 0x88 = 34×4`,其餘四段都是 `0x44 = 34×2` ——
**六個陣列一致都是 34 格**(索引 0–33)。

迴圈 `cmp ax, 21h; jle` → 讀索引 **1–33**。
檔案有 **34 列**,最後一列是 `ET CETERA,0,0,0,0,0` —— **哨兵列,不讀**。
**33 = 33,零誤差。**

## 3. `ITEMS.DAT`:6 欄 57 列

`CMBT 0x1082D`(檔號 `#3`):

| 欄 | 目的 | 元素 | 內容 |
|---:|---|---:|---|
| 1 | `ds:7494h` | 4 | 物品名(`Dagger`)|
| 2 | `ds:7590h` | 4 | 第二個名稱(`knife`)|
| 3 | `ds:9396h` | — | **純量,不是陣列** |
| 4 | `ds:7684h` | 2 | 整數 |
| 5 | `ds:7702h` | 2 | 整數 |
| 6 | `ds:7780h` | 2 | 整數 |

間距 `0x7590−0x7494 = 0xFC = 63×4`、`0x7702−0x7684 = 0x7E = 63×2` ——
**陣列開到 63 格**,比實際列數多,是 `DIM` 開寬的。

⚠ **欄 3 讀進一個純量而不是陣列**,每一輪覆蓋掉上一輪。
`CMBT` 用不到這一欄;它的內容要從別的讀取端(`TOWN 0x11C87`、`CAMP 0x12EB3`)去找。

迴圈上界 `cmp ax, 38h` = 56。起始值來自 `cx` 不是常數,
所以 **0-based(0–56 = 57 列)是推論** —— 支持它的是列數剛好 57,零誤差。

## 4. `MONSTERS.DAT`:36 bytes 定長記錄 × 74

`CMBT 0x17E82`(檔號 `#1`):

```
017E8F  mov bx, 1          ; #1
017E92  mov cx, 24h        ; ★ 記錄長度 36
017E95  int 3Eh; 1E        ; OPEN
017E9A  int 3Fh; B3        ; 隨機存取設定
017EA1  mov bx, 9F7Ch
017EA4  int 3Fh; B4        ; FIELD
```

讀一筆(`0x17F3E` 起,`dx = 怪物型別 + 1` 當記錄號):

```
017F47  mov bx, 1 / int 3Eh; 26        ; GET #1, dx
017F5B  mov bx, 9F7Ch / mov dx, 1 / mov cx, 10h
017F64  int 3Dh; 0A                    ; MID$(緩衝區, 1, 16)  → 名稱
017F7A  mov word ptr ds:66D0h, 11h     ; 位移 17
017F83  call loc_10083                 ; CVI
017F89  mov [di+77FEh], ax
        …
```

`ds:66D0h` 被設十次:**17, 19, 21, 23, 25, 27, 29, 31, 33, 35** ——
間距全是 2,涵蓋到第 36 個位元組。

```
1–16   名稱(16 bytes,空白補齊)
17–36  十個 2-byte 整數
```

**三個獨立的印證:**

| 來源 | 數字 |
|---|---|
| `mov cx, 24h` | 記錄 36 bytes |
| 十個欄位起點 17…35 | 16 + 10×2 = **36** ✅ |
| `MONSTERS.DAT` 檔案大小 | 2,664 ÷ 36 = **74.0** ✅ 整除 |

十個目的陣列基底 `0x77FE`、`0x7810`、…、`0x78A0`,間距全是 `0x12 = 9 words` ——
**每個陣列只有 9 格**,因為這裡讀的不是全部 74 種,是**本場戰鬥出現的最多 9 群**。
`MONSTERS.DAT` 是照怪物型別**隨機存取**的,不整批載入。

前三筆的內容,用上面的格式直接讀出來:

```
#0 'Lvl  1 Fighter'  (7, 7, 7, 8, 2, 1, 1, 33, 1, 0)
#1 'Lvl  1 Wizard'   (7, 6, 6, 5, 0, 3, 0, 33, 1, 5)
#2 'Orc'             (6, 9, 7, 2, 2, 12, 2, 38, 2, 0)
```

## 5. E 還缺什麼

| 條件 | 狀態 |
|---|---|
| 1 IDA 讀原始指令 | ✅ 三個 `OPEN` + 三段迴圈逐條讀出 |
| 2 讀寫端點 | **部分** —— 讀端有了;**每一欄的消費端還沒追**(欄位語意就卡在這) |
| 3 獨立印證 | ✅ 三個檔的大小與列數各自零誤差 |
| 4 筆記 | ✅ |

**E 不標 RE-DONE。** 缺口是**欄位語意**:

- `SPELLS` 四個整數欄、`ITEMS` 三個整數欄、`MONSTERS` 十個整數欄分別是什麼
- `ITEMS` 欄 3(`CMBT` 讀進純量)要從 `TOWN` / `CAMP` 的讀取端補
- `SPELLS.DAT` 在 `CAMP 0x12CCD` 另有讀取點,尚未比對是否同一組欄位

做法明確:從上表的陣列基底反查**使用端**(`[reg+基底]` 的讀取點),
看它被拿去乘什麼、比什麼 —— 和 [`70`](70-key-chains-all-modules.md) 同一套位元組掃描。
不卡外部條件。
