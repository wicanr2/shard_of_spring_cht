## 結論

把 `INT 3Fh` 派工表裡幾個算術索引的目標讀出來,
認出 `BRUN30` 的 **MBF 單精度浮點常式**。有了這張表,
模組裡任何一段運算都可以照著讀 —— 這是 J 卡住的真正原因,不是找不到程式碼。

| 索引 | `BRUN30` | 語意 | 認出來的依據 |

| `3F:57` | `0xA880` | **整數 `bx` → 浮點累加器** | `mov ax, 9000h`(指數 `0x90` = 2¹⁶)+ `or al, bh` |

## 1. 為什麼四支長得像卻分得開

`0xB359`、`0xB369`、`0xB36E` 三個進入點擠在 21 個位元組內,
各自 `mov si, 1Ah` 或 `call sub_11EC3` 之後跳進**同一段尾巴** `0xB37A`。

**每個運算有兩個進入點**:一個是「第二個運算元已經在累加器裡」,
另一個是「要先去取」。`0x1A` 就是累加器的位址。

分辨運算的關鍵在**指數怎麼處理**:

```
加/減  0x1B394  or ch, ch / cmp ch, ah / sub ah, ch   ; 對階
乘     0x1B4C9  add ah, ch / sub ah, 81h              ; 指數相加
除     0x1B544  sub ah, ch                            ; 指數相減
```

減法與加法共用主體,差別只在進入時 `xor al, 80h` 把符號位翻掉。

> **判準:一組長得幾乎一樣的常式,要從「它對哪個欄位做了不同的事」分辨**,
> 不是從長度或位置。這裡的分辨點是指數位元組,只有三行。

## 2. 已經可以回頭讀的東西

[`76`](76-to-hit-formula.md) §1 的命中公式是用純整數指令算的
(`sub` / `add` / `shl`),所以當時讀得出來。
但**傷害那一段走浮點**,整段是 `CD 3F xx` 的序列 —— 之前只能看到運算元。

`CMBT 0x13842` 起的傷害計算,已知的運算元:

| 來源 | 值 |
|---|---|
| 取整 | `mov bx, 1Ah`(**累加器位址**,見 §1)+ `INT 3D:03` = `INT()`([`152`](152-experience-settlement-formula.md) §3);亂數是 `3D:34` |
| 防禦者屬性 17 | `[di+6822h]`,`di = 防禦者 + 255`(255 ÷ 15 = 17)|
| 防具值 | `ds:9788h` = 防具的 `ITEMS` 欄4([`76`](76-to-hit-formula.md) §2)|
| 武器傷害 | `[di+7684h]` = 武器的 `ITEMS` 欄4 |
| 赤手空拳 | 武器項換成常數 `1` |

`0x13857`–`0x1385B` 是純整數的 `1 − 屬性17[防] − 防具值`,結果進 `ds:9786h`。

⚠ **完整的傷害公式還沒寫出來** —— 運算元與運算子都有了,
但要把 `0x13842`–`0x139E4` 整段的 API 序列排出來才算數,還沒做。
**不要把「工具備齊」當成「已經解出」。**

### 1.1 查表比猜快

派工表在 `BRUN30.EXE` 的檔案位移 **0x58D**,每個索引兩個 byte。
[`tools/brun_api.py`](../../tools/brun_api.py) 直接翻,並用兩個已知索引自我回驗。

⚠ **相鄰的索引不代表相關的運算。** `3F:8F` 夾在 `3F:8D`(除)與 `3F:91`(乘)之間,
一度被當成除法的另一序 —— 查表才看到它指向 `0xB4AB`,落在**乘法**本體內。

## 3. 工具:`tools/int_seq.py`

IDA 在這些區段**對不齊**(`0x13864` 的 `81 cd 3f 57` 被讀成 `or bp, 573Fh`,
把 `INT 3F:57` 吃掉了)。`CD 3D/3E/3F nn` 是定長形狀,直接掃位元組不會錯:

```
python3 tools/int_seq.py game/sharspri/CMBT.EXE 0x13842 0x139E4
```

這是 [`70`](70-key-chains-all-modules.md) §6 那條判準的第二次應用:
**以 IDA 的指令邊界為前提的讀法,在只解開 40% 的模組區裡會漏東西。**
