# 78 — 傷害計算的運算序列(形狀已排出,配對有保留)

日期:2026-08-14
接續:[`77-runtime-arithmetic-api.md`](77-runtime-arithmetic-api.md)
子系統:**J. 戰鬥規則**

## 結論

用 [`77`](77-runtime-arithmetic-api.md) 的算術 API 表把 `CMBT 0x1387D`–`0x13918`
(有武器的分支)排出來,**運算的形狀確定**,但**其中三個運算元的配對不可靠** ——
成因見 §3,那是一個還沒解開的位元組對齊問題。

## 1. 序列

```
0x13890  mov bx, [di+7684h]     ; 武器的 ITEMS 欄4 = 傷害值
0x13894  INT 3F:57              ; 累加器 ← 武器傷害
0x13899  mov di, 9782h
0x1389C  INT 3F:91              ; 累加器 × ds:9782h
0x138A1  mov bx, 1Ah            ; 26
0x138A4  INT 3D:03
0x138B3  mov bx, [di+6822h]     ; 屬性 17[防禦者]
0x138B7  INT 3F:71
0x138BD  INT 3F:57
0x138C2  INT 3F:9D              ; 累加器 − 屬性17[防]
0x138C8  mov bx, ds:9788h       ; 防具的 ITEMS 欄4
0x138CC  INT 3F:71
0x138D2  INT 3F:57
0x138D7  INT 3F:9D              ; 累加器 − 防具值
0x138EB  INT 3F:71
0x138F1  INT 3F:57
0x138F6  mov di, 9460h
0x138F9  INT 3F:91              ; × ds:9460h
0x138FE  mov bx, 1Ah            ; 26
0x13901  INT 3D:03
0x13906  INT 3F:85              ; 加
0x1390C  mov di, 9464h
0x1390F  INT 3F:81              ; + ds:9464h
0x13914  INT 3F:77              ; → 整數
0x13919  mov ds:9786h, ax
```

**形狀**:

```
傷害 = 武器傷害 × R₁ − 屬性17[防] − 防具值        (前半)
       … × ds:9460h + R₂ + ds:9464h              (後半)
```

`ds:9782h` 在 `0x13723` 被一個 `INT 3D:34` 之後寫入 —— **是亂數**。
`mov bx, 1Ah`(26)出現兩次,每次都緊接 `INT 3D:03`,形狀像**擲骰的面數**。

赤手空拳分支(`0x13842`)把武器項換成常數 `1`,其餘相同。

## 2. 已經可以說的

| 結論 | 信心 |
|---|---|
| 傷害的輸入是:武器傷害、防禦者屬性 17、防具值、兩個亂數 | **已確認**(運算元逐個讀出)|
| 防具**直接減傷**,不是減命中 | **已確認**(`3F:9D` 減法,運算元是 `ds:9788h`)|
| 屬性 17 也直接減傷 | **已確認** |
| 武器傷害先乘一個亂數再扣防禦 | 證據充分 |

**防具在這個系統裡是減傷不是減命中**,而命中那一邊扣的是**防具的欄5(加值)**
([`76`](76-to-hit-formula.md) §1)—— 兩欄各管一件事,不重疊。

## 3. ⚠ 為什麼說配對不可靠

`0x138C7`、`0x138D1`、`0x138DC`、`0x138F0`、`0x1390B` 各有一個**落單的位元組**
(`0x81` / `0x82` / `0x83`),夾在 `INT` thunk 的 `90 90` 填充與下一條指令之間。

把它當指令起點,`82 CD 3F` 會被讀成 `or ch, 3Fh`,**把後面的 `INT 3F:57` 吃掉**
—— 這正是 IDA 在這一段的讀法。把它當填充,前後就都通順。

**兩種讀法都自洽,而我沒有證據選邊。** 試過的路:

- 間距(10, 11, 20, 27)沒有規律 → 不是固定對齊
- 不是 `INT 3Eh` 的索引(前面兩個位元組是 `90 90` 不是 `CD 3E`)
- 不是有效的單位元組指令

所以 §1 那些 `mov` 的位址**可能整體偏移**。
`INT` 的序列本身不受影響(`CD 3F nn` 是定長形狀,
[`77`](77-runtime-arithmetic-api.md) §3 的工具直接掃位元組)。

> **判準:序列與配對是兩件事。**「哪些運算照什麼順序發生」已經確定;
> 「每個運算吃的是哪個運算元」還壓在一個未解的對齊問題上。
> **把兩者寫成同一個信心等級,就是把不確定性藏起來。**
