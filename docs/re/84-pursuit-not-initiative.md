# 84 — 屬性 0 / 1 是戰場座標,那段不是先攻

日期:2026-08-14
接續:[`83-hp-is-attribute-3.md`](83-hp-is-attribute-3.md)
子系統:**J. 戰鬥規則**

## 結論

去找先攻,找到的是**追擊移動**。`CMBT 0x13F87`–`0x14018` 反覆比較兩個單位的
**屬性 1**,依大小分別呼叫 `sub_14195` 或 `sub_143E5` —— 那是「往哪個方向走」,
不是「誰先動」。

**先攻仍然未解**,但這一輪把屬性 0 / 1 的身分推進了一步。

## 1. 那段程式碼

```
013F87  mov di, ds:93A6h       ; 單位 A
013F8B  add di, 0Fh            ; + 15 = 屬性 1
013F90  mov bx, [di+6822h]
013F94  mov si, ds:6818h       ; 單位 B
013F98  add si, 0Fh
013F9D  cmp bx, [si+6822h]
013FA1  jl  → call sub_14195
013FC6  jg  → call sub_143E5
```

**同一組形狀重複四次**,而且緊接著在 `0x14028`–`0x140AF` 換成**屬性 0** 再來一輪。

**兩個屬性、各有「大於走一邊、小於走另一邊」的分派** ——
這是二維平面上的追擊:先比一軸再比另一軸。

## 2. ⚠ 本節已被 [`85`](85-scanner-conflated-zero-with-unknown.md) 推翻

> 屬性 0 的那一半來自掃描器的**預設值**(找不到 `add` 就當 imm=0)。
> **[`86`](86-scanner-fixed-conclusion-restored.md):工具修好後重判,本節結論恢復成立** ——
> 屬性 0 真的有 62 處存取、真的有三組成對比較。**但原本的證據不成立**,
> 下面的內文是靠壞工具寫出來的,保留是為了留下形狀。

## 2.(已推翻)為什麼判斷屬性 0 / 1 是座標

| 證據 | 內容 |
|---|---|
| 用法 | 只在單位之間**互相比較**,沒有進任何算術公式 |
| 成對 | 屬性 0 與屬性 1 的比較段**結構完全相同、緊鄰**,像 x 與 y |
| 分派 | 比較結果只決定**呼叫哪一支**,不產生數值 |
| 陣列形狀 | BASIC 行主序 `A%(單位, 屬性)` 的位址是 `屬性 × 15 + 單位` → **最多 15 個單位**,與 [`43`](43-module-ds-layout.md) 的「戰鬥時 15 欄」一致 |

**信心:證據充分。** **已升級為已確認**:[`96`](96-facing-and-action-points.md) §1 ——
兩支子常式在屬性 1 上比大小之後把朝向設成 `3`(南)或 `1`(北),
**朝向值直接指認了軸向**。

## 3. ⚠ 這讓 [`81`](81-chars-record-to-combat-attributes.md) 的一條配對變可疑

[`81`](81-chars-record-to-combat-attributes.md) 把 `CHARS.DAT` 位移 41 配給屬性 1。
**但戰場座標不可能存在存檔裡** —— 那是每場戰鬥現排的。

回頭看那張表:位移 41 → 屬性 1 的配對距離是 **33 bytes,是 12 筆裡最大的**
(其餘落在 19–29)。**它是唯一的離群值,而現在有語意上的理由懷疑它。**

> **判準:機械配對的離群值要當成待查,不是當成雜訊。**
> [`81`](81-chars-record-to-combat-attributes.md) §2 用兩個錨點驗證了規則,
> 那證明**規則大體正確**,不證明**每一筆都正確** ——
> 而最該懷疑的那一筆,當時就已經用距離把自己標出來了。

`位移 41 → 屬性 10` 的那一筆(距離 20)不受影響。
