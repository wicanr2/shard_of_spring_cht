## 結論

依 [`85`](85-scanner-conflated-zero-with-unknown.md) §4 把掃描器修好
(`tools/attr_scan.py`,失敗值單獨列出、再用「緊接 `shl reg,1`」認出真正的屬性 0),
重跑 `CMBT`:

| | 舊 | 新 |
|---|---:|---:|
| 判定 | 220(含 97 筆假的屬性 0)| **289** |
| 判不出來 | 0(全被吞掉)| **30** |
| 屬性 0 | 97(全是假象)| **62(真的)** |

**[`84`](84-pursuit-not-initiative.md) §2 的結論成立,但它原本的證據不成立。**

## 1. 修正後的屬性使用次數

```
屬性 0:62   1:38   2: 9   3:18   4:15   5:10   6: 6   7:12   8:19   9: 5
     10:28  11: 9  12: 6  13: 3  14: 6  15:15  16: 3  17: 5  18:15  19: 1
```

屬性 0 仍然是最多的 —— 但這次 62 筆每一筆都通過了明確的判準
(前面緊接 `shl reg, 1`,索引 ×2 之後沒有加任何位移)。

## 2. 追擊那一段重判

| 位址 | 舊判定 | 新判定 |
|---|---|---|
| `0x14028` / `0x14032` | 屬性 0 | **屬性 0** ✅ 一樣 |
| `0x14047` / `0x14051` | 屬性 0 | **屬性 0** ✅ |
| `0x1407B` / `0x14085` | 屬性 0 | **屬性 0** ✅ |
| `0x14097` | 屬性 0 | **屬性 10** ❌ 舊的錯了 |
| **`0x13F48`** | 屬性 0 | **屬性 18** ❌ 舊的錯了 |

所以 [`84`](84-pursuit-not-initiative.md) §1 的形狀是真的:
**屬性 0 有三組 `mov` + `cmp` 的成對比較,和屬性 1 那四組結構完全相同、位置緊鄰。**

「兩個屬性各有大於/小於的分派,像 x 與 y」這個論證**恢復成立**,
`屬性 0 / 1 = 戰場座標` 回到**證據充分**。

## 3. 舊掃描器不只是漏判,還誤判

`0x13F48` 與 `0x14097` 被記成屬性 0,實際是屬性 18 與屬性 10。

失敗值撞號的後果**不只是多出一堆假的屬性 0** ——
它還讓**別的屬性的真實用量被低估**(屬性 10 少算一筆、屬性 18 少算一筆)。

> **判準:一個把失敗吞進某個類別的分類器,會同時「灌水那一類」和「掏空其他類」。**
> 我只想到前者,所以 [`85`](85-scanner-conflated-zero-with-unknown.md) §1 那張
> 「哪些結論受影響」的表列得太窄 —— 凡是引用過**次數**的結論都該重看。
> 所幸 [`73`](73-monster-columns-to-combat-array.md)/[`81`](81-chars-record-to-combat-attributes.md)
> 用的是**位址**不是次數,不受影響。

## 4. 這一輪真正的收穫

**結論沒變,證據全換。** 這種情況很容易被寫成「本來就是對的」而跳過 ——
但原本那個結論站在一個 31% 是雜訊的分佈上,**它當時就不該被相信**,
即使它後來被證明是對的。

> **判準:結論正確不等於推理正確。** 一個靠壞工具得到的正確答案,
> 和一個錯答案有同樣的問題 —— 下一次同樣的推理會給出錯的東西。
