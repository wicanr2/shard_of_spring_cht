# 87 — 職業碼、種族碼,與屬性 17 的算法

日期:2026-08-14
接續:[`86-scanner-fixed-conclusion-restored.md`](86-scanner-fixed-conclusion-restored.md)
子系統:**D. 角色資料** × **J. 戰鬥規則**

## 結論

屬性 17(傷害公式裡直接減傷的那一項,[`79`](79-alignment-resolved-damage-formula.md) §3)
是**條件式**的:只有當角色記錄位移 15 的字元等於 `'1'` 時才取值,否則為 0。

追下去同時定出 `CHARS.DAT` 三個新欄位。

## 1. 程式碼

```
011C10  mov bx, 94C8h / mov dx, 0Fh / mov cx, 1
011C1B  INT 3D:0A              ; MID$(角色記錄, 15, 1)
011C23  mov bx, 94CCh          ; 常數字串 '1'
011C26  INT 3F:62              ; 字串比較
011C2B  jz  → 0x11C30
011C2D  jmp → 0x11C55

011C30  mov dx, 30h            ; 位移 48
011C35  INT 3D:0A              ; MID$(角色記錄, 48, 1)
011C3A  INT 3D:13 / INT 3F:78  ; 轉成數值
011C4E  mov [di+6822h], bx     ; → 屬性 17(位移 0FFh = 255 = 17 × 15)

011C55  mov word ptr [di+6822h], 0    ; 否則 屬性 17 = 0
```

屬性 16(`0x11C0A`,位移 `0F0h` = 240 = 16 × 15)是同一個形狀的另一支。

## 2. 資料對得上

`CHARS.DAT` 前五筆(出貨的預設角色):

| # | 名稱 | 位移 14 | 位移 15 | 位移 48 起 |
|---:|---|:-:|:-:|---|
| 0 | `Segrono` | `H` | `1` | `1100` |
| 1 | `Hard Axe` | `D` | `1` | `1100` |
| 2 | `Grod` | `T` | `1` | `1100` |
| 3 | `Fire Hawk` | `E` | `2` | `0100` |
| 4 | `Richtatha` | `G` | `2` | `0001` |

- **位移 15 = 職業碼** —— 程式碼直接拿它比 `'1'`;五筆的值是 `1,1,1,2,2`
- **位移 14 = 種族碼** —— **五個角色五個不同的字母**(`H D T E G`),
  而職業只有兩種。⚠ 字母對應哪個種族**沒有證據**,不要猜。
- **位移 48 起 = 一串 `0`/`1` 旗標字元**,屬性 17 取的是**第一個**

職業 `1` 的三筆旗標第一位都是 `1`,職業 `2` 的兩筆都是 `0` ——
**與程式碼的條件完全一致**(職業 2 就算旗標是 1 也會被判成 0,而資料裡本來就是 0)。

**94 bytes 裡有語意的位置從 4 個增為 8 個。**

## 4. 順帶:屬性 17 在傷害裡的角色

[`79`](79-alignment-resolved-damage-formula.md) §3 的傷害公式裡,
屬性 17 與防具值一起**從傷害裡減掉**。而它只有職業 `'1'` 才非零。

**形狀上是「某個職業專屬的減傷」**,而且來源是一個 0/1 旗標而非數值 ——
⚠ 但「哪個職業」「這個旗標代表什麼能力」都**沒有證據**。
`'1'` 這三筆的名字(`Segrono` / `Hard Axe` / `Grod`)看起來像戰士,
**但那是從名字猜的,不算**。

## 5. 還缺

- 位移 48 那串旗標的其餘位元
- 屬性 16 的來源位移(§1 只讀到「另一支同形狀的分支」)
