## 1. 順序與理由

```
A 遊戲外殼   →  B 自己的存檔  →  C 場景架構  →  D 戰鬥 AI
                                       ↓
                              E 補完指令  →  F 中文化剩餘  →  G 打包
```

**A 先做**,因為在它做完之前「玩一輪」這件事不存在,而**沒有可玩的整輪就沒有回饋迴路**
（`rulebook/60`：先建可重跑的 pass/fail loop）。現在要驗一條規則得用旗標與參數硬跳進去。

**B 緊接著 A**,因為 A 的「讀取進度」需要一個格式;而且現在的存檔**寫回原版 `.DAT`**,
與 [`03`](03-engine-plan.md) §2「寫自己的格式」相矛盾 —— 這一條放越久,綁上去的東西越多。

**C 在 A/B 之後**才有意義:場景邊界要等「開頭 → 遊戲 → 結尾」的完整路徑存在了,
才知道該切在哪。⛔ 先重構再補流程會照著現在的形狀切,把旗標式的結構固化成介面。

**D 獨立**,可以與 E/F 並行 —— 它只動 `internal/combat`。

## 4. C. 場景架構

`Scene` 介面在 `engine/scene.go`(C1 已完成)。**輸入整格只收一次**
(`Input`),再交給 `inputChain()` —— 誰吃這一格按鍵從控制流變成一張**看得見的表**。
繪圖另有一張 `drawOrder()`:輸入是優先序、繪圖是圖層,兩者本來就不同
(戰鬥吃鍵最優先,但畫在迷宮之上、覆蓋層之下)。

⚠ **狀態還在 `*Game` 上**,場景結構體只握一個 `*Game` —— 把狀態切進各自的
套件是 C2。⛔ 不要因為「介面已經在了」就當成已經分層。

| | 項目 | 說明 |
|---|---|---|
| [x] | C1 抽出 `Scene` 介面 | `Handles` / `Update(Input) Transition` / `Draw`,16 個場景 + 兩張順序表(`engine/scene.go`)。⚠ 規劃時寫的是 `Update(*GameState)`,但 `GameState` 這個型別不存在也不該現在生 —— 狀態切分是 C2,先造一個空殼型別只會多一層要維護的間接 |
| 暫緩 | C2 切成 vertical slice | 一個場景一個套件。**這個規模還沒有痛點**:11 個檔在同一個套件裡沒有造成過一次「找不到東西」,而切套件會逼出一個 `GameState` 型別來搬狀態。**重啟的判準**:改一個場景時不小心動到另一個場景的狀態(或想不起某個欄位是誰的)—— 出現那個訊號就做,在那之前它是為了規劃書上的一行去生一層間接。**判準已量過一次(見下),未達成** |

### 4.1 C2 的判準量過了:沒達成

`tools/field_owners.py` 量「`*Game` 的每個欄位被幾個非測試檔碰」——
判準寫的是「不小心動到別的場景的狀態」,而那要**已經出事**才觸發;
能事先量的是它的前置條件:**一個欄位散在幾個檔案裡**。

66 個欄位、24 個檔,跨檔數中位數 **3**、最大 **14**。分布的形狀比數字重要:

| 跨檔數 | 欄位 | 是不是問題 |
|---:|---|---|
| 14 | `panel` `members` | **不是**。`panel` 是共用的繪圖元件,`members` 是隊伍本身 |
| 11 | `party` `group` | **不是**。隊伍狀態與座標,每個場景都合法地讀 |
| 9 | `warnings` `level` `field` | **不是**。前兩個是全域紀錄與所在樓層;`field` 是戰場,碰它的是施法/用道具/檢視 —— 那些**就是戰鬥中的子場景** |
| 1–2 | `castPage` `castSP` `inspect` `skillAlloc` `saveAs` `healPay` `campPotion` … | **場景自己的狀態,沒有外流** |

關鍵在 1–2 那一層:19 個跨兩檔的欄位裡,**18 個的第二個檔案是
`main.go`(開場載入)或 `scene.go`**,而 `scene.go` 碰它們的形式一律是
派工表的 `Handles()`:`s.g.inspect != nil` —— 問「你在不在」,不是改它。
唯一真的跨兩個場景檔的是 `campPotion`(`camp_actions.go` + `use_item.go`),
而那兩支是同一個功能。

**所以散開的都是本來就該全域的,場景自己的狀態一個都沒散出去。**
切套件現在買不到東西,只會多一個 `GameState` 型別要維護。

> **判準:「這個重構該不該做」要拿分布去問,不是拿總量。**
> 66 個欄位掛在一個結構上,聽起來就該切;但真正該切的訊號是
> **屬於 A 的欄位被 B 改到**,而那在數字上長成「低跨檔數的欄位卻散在多個場景檔」。
> 這裡沒有那個形狀。量之前只有「感覺很多」,量完才知道多的是哪一種。
| [x] | C3 覆蓋層與提示列收斂 | 訊息面板收斂成 `engine/message.go` 三個函式(先前城鎮/名冊/迷宮/戰鬥四份逐字相同的迴圈、施法/道具兩份「先黑色蓋掉」);指令提示列改由 `Scene.Prompt()` 提供,畫的時候問**實際會接手按鍵的場景**(`activeScene()`)|

⚠ **C 是重構,不是新功能。** 判準:做完之後**行為要一模一樣**。
C1 的驗收是三層:73 個既有測試 + T1/T2 端到端 + **六張截圖逐位元組相同**

修法:結算收攏成 `g.settle()`(`engine/combat_scene.go`),三個入口(最後一擊、

### 12.2 第二輪:兩個「全綠的失敗」

第二輪查到的十一條裡,有兩條的共通點是**測試全綠而東西是壞的**,

|---|---|---|
| 版控裡的 `assets/` 沒有人形圖 | 截圖測試讀 `workplace/assets2`,整合測試讀版控的 `assets/` —— 而**新輸出只進了前者**。clone 下來跑看到白框,而每一支測試都綠 | `TestCommittedAssetsAreComplete` 逐類數檔;截圖與推廣片預設改讀版控那份,兩份不再分家 |

### 12.1 戰場 sprite:阻礙已排除([`re/220`](../re/220-sprite-group-to-monst-file.md))

擋住的是「圖組編號 → `MONST` 檔」。讀出來的是:

```
圖組(屬性 11) = 檔號 × 8 + 25        →   怪物的檔號就是 MONSTERS.DAT 欄6
```

三條互相獨立的證據:載入迴圈每載完一個檔做 `ds:9494 += 8`(步長 8);
`CMBT` 字串表裡**寫死** `monst2.bin` / `monst4.bin`,而隊員的圖組
41 / 57 是立即數讀出來的(41→檔2、57→檔4,差 16 = 兩檔 × 8);
內容對照**七項全中**(檔 15 蝙蝠、16 蛇、17 火焰、18 劍身、20 幽靈、
21 旋風、22 龍)。

⚠ **這同時訂正了一條規則。** [`re/188`](../re/188-dispell-undead.md) §3.1 推的
`檔號 = 欄6 + 1` 有兩個破綻:欄6 最大 22 → 檔 23 而只有 22 個檔;
以及憑空多出一個「沒有任何怪使用」的空組(那其實是隊員巫師的檔)。
不死生物因此從 `{4,5,6}` 訂正成 **`{5,6,7}`** —— 骷髏 / 骷髏巫師 / **幽靈**。

⚠ 舊版還替那個差一位寫了一句解釋:「幽靈不算不死,本作把它們歸成靈體」。
**那是替一個錯誤的數字編出來的說法,而它讀起來完全合理。**

> **判準:一個推論產生「剛好有一組是空的」或「剛好差一個」時,
> 多半是偏移錯了,不是資料真的有洞。** ⛔ 更不要回頭替那個洞編一套說法。

> **判準:對應表拿「內容」驗比拿「算術」驗強。**
> 算術可以差一位而仍然自洽;火元素長得像火焰不會。
